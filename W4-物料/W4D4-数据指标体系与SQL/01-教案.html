二、教学目标（可测量）

  1. 能完整说出 AI 产品五大核心指标（采纳率 / 解决率 / 幻觉率 / 留存 / 单次成本）的定义与公式，并指出每个指标至少 1 个常见误读（对应基础层习题 1–4）。
  2. 能用「三标准」（绑价值 / 可影响 / 可拆解）为自己的主项目选定北极星指标，并配齐护栏指标，填完三层看板设计表（对应课堂产出与进阶层习题 8）。
  3. 能独立写出含 SELECT、WHERE、GROUP BY、JOIN 的查询，在 SQL 教学数据集上算出「按渠道分组的采纳率」（对应课堂练习第 3 题与上机题）；零编程学员的达标口径为「能读懂这四类查询在算什么、分母是谁、结论能不能信」，不要求成为开发。
  4. 能按「整体 → 切片 → 归因」三步，用一条查询结果讲一个 30 秒的数据故事（对应求职挑战层习题 9）。
  5. 【术语目标】 能对本日 12 个核心术语逐条说出「一句话定义 + 一个易混辨析」，并重点辨析采纳率、幻觉率、留存等「率类指标的分子分母」——当堂术语小测 12 题答对 ≥10 题为达标（对应《03-导学案》术语自测表、《06-分层习题》第 0 层）。
  6. 【面试目标】 能用 60 秒标准答法回答「AI 产品看什么指标」「采纳率怎么定义」「整体涨了分组跌了怎么解释」「SQL 不会写产品能不能做」四类高频题，每题至少命中 3 个踩分点、能接住 2 层追问（对应《03-导学案》面试模拟记录表、对应板块两两模拟自评分 ≥3 分）。
  7. 能把本日 5 件产出物（术语自测表 / 五大指标笔记表 / 三层看板设计表 / SQL 三题 / 面试模拟记录表）按《本日作品集积木》完成归档，当堂验收清单逐项打勾（对应对应板块作品集归档动作）。

三、教学重难点

  • 重点一：AI 产品特有指标——采纳率、解决率、幻觉率、留存、单次成本。它们与传统 DAU/UV 的本质区别：衡量「用得值不值」，而不是「来了多少人」。
  • 重点二：北极星指标设计三标准 + 护栏指标防「指标做歪」。
  • 重点三（新增·术语）：率类指标的分子分母与口径。同一个「采纳率」，分母按次还是按会话、修改后采纳算不算，答案完全不同；「幻觉率」的分母是抽检回答总数而非全部回答，「留存」的分母是当日新增而非全部活跃。
  • 难点一：指标口径。学员容易背公式不带口径，跨版本比对时数字对不上。
  • 难点二：SQL 对零基础学员的门槛。用「四关闯关」降低压力：每关只加一个关键字，关关有小胜利；整数除法陷阱（SUM/COUNT）必须在现场暴露一次。本课把 SQL 定位为「产品要懂的读法与口径」，不写成开发教程。
  • 难点三（新增·术语混淆）：DAU 与留存、聚合与分组、指标口径与幻觉率口径、北极星指标与一级指标、看板与报表等相邻概念易被混为一谈；英文缩写 DAU（Daily Active Users，日活跃用户数）、SQL（Structured Query Language，结构化查询语言）需先给全称与中文再使用。
  • 难点四（新增·面试失分）：学员面试时容易「背指标名不给口径」「整体涨了就下结论不看分组」「被追问两层就卡住」「把不会写 SQL 说成硬伤」。对应板块用「踩分点 + 追问链 + 失败答法 + 60 秒标准答法」逐题防御。

六、AI 产品五大核心指标：逐个教学设计

每个指标按「定义 → 公式 → 健康线怎么定 → 常见误读」四段教学。健康线一律标注「示例值，需按业务校准」，并教「基线对比法」而非背数字。本节对应对应板块核心原理讲授 A，率类指标的分子分母须与对应板块术语卡口径完全一致。

指标 1 · 采纳率（Acceptance Rate）

维度 教学内容
定义 用户对 AI 生成结果「接住了」的比例——AI 产品的「价值时刻」发生在用户采纳的那一刻
公式 采纳率 = 被采纳的生成次数 / 总生成次数。必带口径：采纳动作 = 复制、点「采纳」、原样发布还是修改后发布？分母按「次」还是按「会话」
健康线怎么定 不背行业数字，用「基线法」：以上线首周为基线，看环比；同类产品公开数据只做量级参考。写作辅助类产品常见区间约 30%–60%（示例值，需按业务校准）
常见误读 ① 认为越高越好——用户重试 10 次才采纳 1 次，单次质量其实很差；② 口径不统一导致跨版本不可比；③ 把「未采纳」全归为质量差——也可能是用户只是试试看

指标 2 · 问题解决率（Resolution Rate）

维度 教学内容
定义 用户带着问题来，最终不需要人工介入、自然结束的比例（客服 / 问答类产品的核心指标）
公式 解决率 = 无人工介入且自然结束的问题会话数 / 总问题会话数
健康线怎么定 先量「人工坐席的解决率」做基线，AI 至少追平才开始谈替代；客服场景公开参考约 60%–80%（示例值，需按业务校准）
常见误读 把「用户没再说话」当解决——用户可能是骂骂咧咧走了。必须用转人工率、满意度评分、重复进线率做交叉验证

指标 3 · 幻觉率（Hallucination Rate）

维度 教学内容
定义 生成内容中与事实或给定资料不符的比例——AI 产品区别于传统产品的特有指标
公式 幻觉率 = 被判定为幻觉的回答数 / 抽检回答总数（分层抽样 + 人工判定，或基于评测集回归）。分母是「抽检回答总数」，不是「全部回答数」
健康线怎么定 按场景风险分层定门槛：对外金融 / 医疗 / 法律场景从严，内部工具可放宽；常见对外知识问答要求抽检幻觉率 <2%（示例值，需按业务校准）。没有金标准 ≠ 不管理
常见误读 ① 「自动检测不准、人工标注主观，所以干脆不量化」——正确做法是分层抽检 + 关键场景（金额 / 政策 / 医疗）从严 + 评测集回归；② 把「拒答」算成幻觉——拒答是好行为，单独统计

指标 4 · 留存（Retention）

维度 教学内容
定义 一段时间后仍回来使用的用户比例。AI 产品常用次日 / 7 日留存，工具类产品更要看「周活跃频次」
公式 N 日留存 = 第 N 天仍活跃的新增用户数 / 当日新增用户数。分母是「当日新增用户数」，不是「全部活跃用户数」
健康线怎么定 分产品形态差异巨大，工具类 7 日留存常见约 20%–40%（示例值，需按业务校准）；AI 产品更该盯「习惯用户」占比——每周使用 ≥3 次的用户比例
常见误读 ① 只看 DAU 涨跌——AI 产品尝鲜用户多，DAU 天然虚高；② 把「打开 App」当「用了核心功能」——留存要按核心行为（生成、采纳）算

指标 5 · 单次成本（Cost per Query）

维度 教学内容
定义 每一次有效请求的平均推理成本——AI 产品独有的「边际成本」视角
公式 单次成本 = 当期 token 用量 × 单价之和 / 有效请求次数；或 = 当月 API 账单 / 当月有效请求次数
健康线怎么定 不跟别人比，跟「单次价值」比：单次成本必须显著小于单次收益（营收贡献或替代的人力成本），用毛利倒推上限
常见误读 ① 只看总账单不看单次——总量随增长必然涨，失控的是单次；② 为省成本砍上下文 / 换小模型导致质量崩，采纳率掉得更贵；③ 忽略重试与缓存的隐性账

七、北极星指标选择三标准

标准 含义 自检问句
① 绑价值 用户获得核心价值的那一刻，就在贡献这个数字 「这个数字涨，用户是真的多得到了价值吗？」
② 可影响 团队能通过本周的工作推动它，而不是只靠市场行情 「下个迭代我们做什么，能让它动？」
③ 可拆解 能拆成一级指标，出问题时能定位到环节 「它跌了，我能查到是哪个环节跌的吗？」

教学示例（教学案例，非真实公司）：某 AI 写作工具把北极星从 DAU 改成「每周生成并被采纳 ≥3 次的用户数」，团队动作立刻从拉新转向留存——因为新用户的「采纳」上不来，这个数字不动。 为什么 DAU 不能当北极星（三标准逐条拆）：不绑价值（打开 ≠ 得到价值）；会被廉价动作推高（推送、签到）；跌了查不出原因（不可拆解到价值环节）。

护栏指标：北极星往上的同时，防止被「歪」着做上去的约束指标。典型组合：采纳率↑ 时盯重试率、单次成本↑ 时盯采纳率、增长↑ 时盯幻觉率。

八、SQL 教学设计：四关闯关（原「环节三」，现深化至对应板块）

教学数据集：AI 写作助手「小笔」的模拟数据（教学示例数据），两张表，见附录 A。学员提前一天已在导学案预习中完成环境安装并跑通第一条 SELECT。

本课 SQL 定位（面向零编程 5/6 的学员）：SQL 部分只讲「产品要懂的读法与口径」，不写成开发教程。达标口径是「能读懂一条查询在算什么、分母是谁、结论能不能信」，而非独立开发复杂查询。四关的每一关都先讲「这个关键字在业务上回答了什么问题」，再给读法，最后才是可运行语句；示例数据一律标注「教学示例」，健康线一律「示例值，需按业务校准」。

关卡 关键字 教学要点（产品读法优先） 现场查询 学员练习（导学案）
第一关 SELECT 从整表取数、选列（投影）——业务上回答「要看哪几列」 SELECT gen_id, is_accepted, cost_yuan FROM gen_records; 跑通 / 读懂 SELECT * FROM users;
第二关 WHERE 行过滤；= / > / AND / OR——业务上回答「只看哪一部分数据」，分母从这里开始变 SELECT * FROM gen_records WHERE is_accepted = 0 AND gen_date >= '2026-09-03'; 练习 1：查 2026-09-03 当天的生成记录
第三关 GROUP BY 分组聚合；COUNT / SUM / AVG / 别名 AS——业务上回答「按什么维度切、每组算几个」；「分组」与「聚合」辨析见对应板块术语卡 SELECT user_id, COUNT(*) AS gen_cnt, SUM(is_accepted) AS acc_cnt FROM gen_records GROUP BY user_id; 练习 2：统计每个用户的生成与采纳次数
第四关 JOIN 两表连接；ON 条件；整数除法陷阱（SUM×1.0）——业务上回答「跨表的两个事实怎么对上」 按渠道算采纳率（见附录 B 查询 3） 练习 3：按渠道算采纳率并说结论

讲师现场跑数 3 条递进查询（讲课稿对应板块「现场跑数」用，完整语句见附录 B）： 1. 整体：今天的采纳率和单次成本健康吗（一条查询算总览）。 2. 切片：按日期分组，哪天的采纳率掉了。 3. 归因：按渠道 JOIN，掉的那部分来自哪个渠道。

递进逻辑 = 用数据讲故事的三步：整体 → 切片 → 归因。面试讲数据时同样用这三步。

必讲的两个坑：① 整数除法——SUM(is_accepted)/COUNT(*) 在 SQLite 里恒为 0，要乘 1.0；② 聚合列要加 AS 别名，看板命名直接用别名。两个坑都归到「口径」：分子分母对不对、比率算没算出来，比语法更影响结论。

九、课堂提问设计（20 问：术语辨析 7 + 面试追问 7 + 原有核心 6）

类型标注：【术语】= 术语辨析，【面试】= 面试追问，【核心】= 原有核心内容提问。术语辨析 ≥6、面试追问 ≥6 已满足。

# 类型 提问 提问时机 预设答案 / 引导方向
1 【核心】 「你怎么知道你的 AI 产品是好是坏？看 DAU 够吗？」 对应板块导入 不够——DAU 只知道来了多少人，不知道用得值不值；引出「价值指标」
2 【术语】 「采纳率的分母是什么？修改之后才采纳，算不算采纳？」 对应板块 / 对应板块指标 1 分母=总生成次数；修改后是否算采纳必须先定义口径——口径不统一，指标跨版本不可比
3 【核心】 「用户没再说话，等于问题解决了吗？」 对应板块指标 2 不一定，可能放弃或不满离开；要交叉验证：满意度、转人工率、重复进线
4 【核心】 「幻觉率没有金标准，我们是不是就不用管了？」 对应板块指标 3 不是。不量化不等于不管理：分层抽检+评测集回归+关键场景从严
5 【核心】 「DAU 涨了 30%，能说明产品变好了吗？」 对应板块指标 4 / 北极星 不能。打开不等于得到价值；可用推送等廉价手段拉高；要看核心行为留存
6 【核心】 「采纳率涨了 5 个点，但重试次数翻倍，发生了什么？」 对应板块护栏指标 单次生成质量在降，用户多试几次才命中；护栏指标报警——北极星要配护栏一起看
7 【核心】 「SELECT 和 WHERE 各管什么？」 对应板块 SQL 第一、二关 SELECT 管列（投影），WHERE 管行（过滤）；先筛行再选列
8 【核心】 「为什么算采纳率要乘 1.0？」 对应板块 SQL 第四关 整数除法陷阱：SUM 和 COUNT 都是整数，相除恒为 0；乘 1.0 转浮点
9 【术语】 「『幻觉率』和『幻觉率口径』是同一个东西吗？」 对应板块术语精讲 不是。幻觉率是数值结果，幻觉率口径是「怎么抽检、谁判定、拒答算不算」的定义；换口径数字就变
10 【术语】 「DAU 和留存的分子分母各是谁？为什么不能互相代替？」 对应板块术语精讲 DAU 是当日活跃用户数（计数，无分母）；N 日留存=第 N 天仍活跃新增 / 当日新增。DAU 是存量快照，留存是 cohort 比例
11 【术语】 「『聚合』和『分组』谁先谁后？只分组不聚合行不行？」 对应板块术语精讲 先分组（GROUP BY 定维度）后聚合（COUNT/SUM/AVG 算每组）；只分组不聚合等价于去重列表，语法允许但没算出指标
12 【术语】 「『指标口径』和『基线』有什么关系？」 对应板块术语精讲 口径定义「这个数怎么算」，基线定义「拿谁当参照」；口径不统一，基线就不可比
13 【术语】 「『北极星指标』和『一级指标』是包含关系还是并列关系？」 对应板块术语精讲 拆解关系：北极星是唯一抬头看的数，一级指标是把它拆开后的支撑项；护栏是并列约束，不是拆解
14 【术语】 「『看板』和『一条 SQL 查询结果』差在哪？」 对应板块术语精讲 查询结果是一次性切片，看板是按三层结构组织、带口径注释、可持续复用的指标集合
15 【术语】 「『漏斗』在今天的『整体 → 切片 → 归因』里对应哪一步？」 对应板块术语精讲 漏斗是「生成 → 采纳」这类逐步流失的转化视角；切片/归因是定位漏斗哪一步掉了
16 【面试】 「面试官问『AI 产品看什么指标』，你第一句先说什么？」 对应板块面试题 1 先给结构（三层）+ 价值视角（用得值不值），再报五指标，不直接背名词
17 【面试】 「『采纳率怎么定义』被追问『修改后算不算』，你怎么接？」 对应板块面试题 2 承认没有唯一答案，但必须给出口径并说明理由：分母按次、采纳动作含原样与修改后发布，且全程一致
18 【面试】 「『整体采纳率涨了，但某渠道跌了』，面试官追问『那到底好不好』？」 对应板块面试题 3 先复述辛普森式结构，再按切片定位、看样本量、给动作；不急着下整体结论
19 【面试】 「『SQL 不会写，产品能不能做』，被追问『那你怎么不被分析师糊弄』？」 对应板块面试题 4 能。产品要懂的是读法与口径：核对分母、识别整数除法、要求口径注释；复杂查询交给分析师
20 【面试】 「被连追两层『你怎么证明这个结论不是小样本碰巧』，怎么答？」 对应板块追问链 先看次数再看比率（referral 1.00 只有 3 次样本），标注「待观察」，提出扩样本或按日期继续切片

十一、课堂练习参考答案（SQL 三题 + 术语小测 + 面试评分示例）

完整数据集见附录 A（教学示例）。

练习 1（SELECT + WHERE）：

SELECT gen_id, user_id, is_accepted
FROM gen_records
WHERE gen_date = '2026-09-03';

预期 2 行：gen_id 107（user_id 4，采纳）、gen_id 109（user_id 5，未采纳）。

练习 2（GROUP BY）：

SELECT user_id,
       COUNT(*) AS gen_cnt,
       SUM(is_accepted) AS acc_cnt
FROM gen_records
GROUP BY user_id
HAVING COUNT(*) >= 3;

结果：仅 user_id 3（共生成 3 次、采纳 2 次）。讲师可现场让学员去掉 HAVING，看全员分布：user_id 1 生成 2 次、user_id 3 生成 3 次，其余各 1–2 次。

练习 3（JOIN + GROUP BY）：参考附录 B 查询 3。预期结果（按采纳率降序）：referral 生成 3 次 / 采纳 3 次 / 采纳率 1.00；search 生成 7 次 / 采纳 3 次 / 采纳率 0.43；social 生成 3 次 / 采纳 1 次 / 采纳率 0.33。必须提醒学员：referral 样本只有 3 次，样本量小时先看 gen_cnt 再看比率，避免得出「推荐渠道必然 100% 采纳」的过强结论。

【面试失分】整体涨了就下结论、不会做分组解释 被问「整体采纳率涨了但某渠道跌了」只答「整体是好的」；把「SQL 不会写」说成硬伤 练「整体 → 切片 → 归因」三步 + 「先看次数再看比率」；给「SQL 不会写」的标准答法：产品要懂读法与口径，复杂查询交分析师

附录 B · 讲师现场跑数 3 条递进查询（参考答案）

查询 1 · 整体：产品健康总览

SELECT COUNT(*)                                                        AS gen_cnt,
       ROUND(SUM(is_accepted) * 1.0 / COUNT(*), 2)                     AS acc_rate,
       ROUND(AVG(cost_yuan), 4)                                        AS avg_cost
FROM gen_records;

查询 2 · 切片：按日期看采纳率趋势

SELECT gen_date,
       COUNT(*)                                    AS gen_cnt,
       SUM(is_accepted)                            AS acc_cnt,
       ROUND(SUM(is_accepted) * 1.0 / COUNT(*), 2) AS acc_rate
FROM gen_records
GROUP BY gen_date
ORDER BY gen_date;

查询 3 · 归因：按渠道看采纳率（JOIN）

SELECT u.channel,
       COUNT(*)                                    AS gen_cnt,
       SUM(g.is_accepted)                          AS acc_cnt,
       ROUND(SUM(g.is_accepted) * 1.0 / COUNT(*), 2) AS acc_rate
FROM gen_records g
JOIN users u ON g.user_id = u.user_id
GROUP BY u.channel
ORDER BY acc_rate DESC;
