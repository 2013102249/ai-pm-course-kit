# 讲课稿 · W4 周四《数据指标体系与 SQL 实战》

## 术语精讲与零层入口

大家好，今天是第四周周四。先说清楚今天的节奏：这是一个 **完整教学日**，不是过去那种讲完就走。今天的内容是这样排的——我们先把名词讲透；讲 AI 产品特有的五个核心指标和北极星；从零开始读懂 SQL、把指标装进看板；你自己动手做；我们把今天所有知识变成面试能拿分的话；复盘、归档、当堂验收。

先给零基础的同学吃一颗定心丸。我知道你们六个人里有五个不写程序，一听「SQL」就紧张。今天对 SQL 的要求，我重新定一下：**不要求你成为开发，不要求你背语法，只要求你读懂一条查询在算什么、分母是谁、这个结论能不能信。** 后面你会看到四条查询，你的任务是能指着它说「这条在算按渠道分组的采纳率，分母是每个渠道的生成次数」——会读、会核对口径，就够了。复杂查询交给数据分析师，产品经理的责任是「别被糊弄」。这一段请记在导学案第一页，它是今天 SQL 全部内容的达标线。

那我们从哪儿开始？从名词开始。为什么先讲名词？因为这两天的状态是——大家产品定义写得很清楚，但一说到「指标」「口径」「聚合」就各说各话。术语不统一，后面讲原理就会卡。今天术语精讲这段，我们讲透 12 个词，每个词给五样东西：一句话定义、一个生活类比、一个最容易混的相邻概念、一句面试能直接说出口的话、再加一张术语卡。英文缩写第一次出现，我一定先给全称和中文。

**术语 1 · 北极星指标**
- 一句话定义：全公司唯一抬头看、用来对齐方向的那个数。
- 生活类比：夜里一队船各走各的，谁也不看里程表，只认天上那颗北极星定方向——里程是各船自己的，方向是全员共用的。
- 易混辨析：最容易和「KPI」混。KPI 用来考核、可以有很多个；北极星用来对齐、只有一个，而且不该被当成考核指标往下压。
- 面试说法：「我理解北极星不是 KPI，它是全团队争论不下时唯一抬头看的那个数，用来对齐方向。」
- 术语卡：`03-配图素材/术语卡/01-北极星指标卡.png`（12 张待制，已在 05-配图清单登记）。

**术语 2 · 采纳率**
- 一句话定义：AI 生成结果被用户接住的比例，分母是总生成次数。
- 生活类比：餐厅端上十道菜，客人真正夹走吃掉的是几道——不是端上几道，是被接住几道。
- 易混辨析：最容易和「点击率」「使用率」混。点开生成按钮不算采纳，用户复制、点采纳、发布出去才算；而且「修改后发布算不算」必须先定义，这是口径不是公式。
- 面试说法：「采纳率我一定带口径说：分子是被采纳的生成次数，分母是总生成次数，采纳动作和统计周期先写死。」
- 术语卡：`03-配图素材/术语卡/02-采纳率卡.png`。

**术语 3 · 幻觉率**
- 一句话定义：抽检回答中被判与事实不符的比例，分母是抽检回答总数。
- 生活类比：老师从一摞作业里随机抽一百本批改，数出几本把史实写错了——分母是「抽到批的那一百本」，不是全班交的全部。
- 易混辨析：最容易和「准确率」「错误率」混，也最容易把分母写成「全部回答数」。幻觉率靠抽检和判定，不是全量自动统计；另外「拒答」不是幻觉，得单独算。
- 面试说法：「幻觉率的分母是抽检回答总数，不是全量回答；因为判定没有金标准，我们用分层抽检加评测集回归来管。」
- 术语卡：`03-配图素材/术语卡/03-幻觉率卡.png`。

**术语 4 · 幻觉率口径**
- 一句话定义：幻觉率怎么抽检、谁判定、拒答算不算的规则定义。
- 生活类比：体检套餐先写清楚「查哪几项、谁看片子、什么算异常」，否则两家医院给出的异常率没法比。
- 易混辨析：最容易和「幻觉率」本身混。幻觉率是一个数，幻觉率口径是「这个数怎么来的」；口径一换，数字就变，跨版本就不能直接比。
- 面试说法：「我先对齐幻觉率口径——抽检比例、判定人、拒答是否计入，再看数字，不然两个版本比不出结论。」
- 术语卡：`03-配图素材/术语卡/04-幻觉率口径卡.png`。

**术语 5 · 指标口径**
- 一句话定义：一个指标的分母、统计周期、数据来源的定义。
- 生活类比：菜谱里写「盐一勺」，得先定死这勺多大、算不算配菜里的盐，不然两个厨师做出来不是一个味。
- 易混辨析：最容易和「指标公式」混。公式是「分子除以分母」，口径是「分子分母各指什么、算哪段时间、从哪张表来」。同一个公式、不同口径，数字能对不上。
- 面试说法：「我写看板时每个指标都带口径注释：分母定义、统计周期、数据来源，三样缺一不可。」
- 术语卡：`03-配图素材/术语卡/05-指标口径卡.png`。

**术语 6 · DAU**
- 一句话定义：DAU 是 Daily Active Users 的缩写，中文「日活跃用户数」，当日活跃用户的计数。
- 生活类比：今天进过这家店的人数，不管进来看了一圈就走，还是买了东西，都算一个。
- 易混辨析：最容易和「留存」混，也最容易被当成一个「率」。DAU 是计数、没有分母；留存是比例、分母是当日新增。DAU 涨不等于产品变好，推送和签到就能把它推高。
- 面试说法：「DAU 只回答来了多少人，不回答用得值不值；AI 产品我不会拿它当北极星。」
- 术语卡：`03-配图素材/术语卡/06-DAU卡.png`。

**术语 7 · 留存**
- 一句话定义：N 日留存是第 N 天仍活跃的新增用户，除以当日新增用户数。
- 生活类比：年初办卡的一百人里，月底还来锻炼的有几个——分母是「那天新办卡的人」，不是全健身房的人。
- 易混辨析：最容易把分母写成「全部活跃用户」。是「当日新增」这一批人（cohort）过 N 天还剩多少；而且「活跃」要按核心行为算，生成过、采纳过，光打开不算。
- 面试说法：「7 日留存的分母是当日新增用户，且按完成过核心行为算活跃，AI 产品我还会额外看习惯用户占比。」
- 术语卡：`03-配图素材/术语卡/07-留存卡.png`。

**术语 8 · 漏斗**
- 一句话定义：用户从第一步走到最后一步、逐层流失的转化视角。
- 生活类比：商场一楼进来一百人，上到三楼剩四十，进试衣间剩十五，最后买单剩五个——每一层都在掉人。
- 易混辨析：最容易和「看板」混。漏斗是「一条路径上的流失」，看板是「一组指标的陈列」；也别和后面「整体→切片→归因」混，那三步是在漏斗里定位哪一层掉了。
- 面试说法：「AI 产品的关键漏斗是『生成→采纳』，传统指标看不见这一步，所以采纳率才是价值时刻。」
- 术语卡：`03-配图素材/术语卡/08-漏斗卡.png`。

**术语 9 · SQL**
- 一句话定义：SQL 是 Structured Query Language 的缩写，中文「结构化查询语言」，用来向数据库要数据的读法。
- 生活类比：给图书管理员递一张借书单，写清「要哪几本书、只看哪一排、按什么归类」——你不用自己进书库，把需求说清楚就行。
- 易混辨析：最容易和「数据库」「编程」混。SQL 只是「提问的语言」，不是数据库本身；产品经理学它是为了读懂和核对，不是为了写程序。
- 面试说法：「SQL 我不做开发，但能读懂查询、核对分母、判断结论可不可信，这是我要求的边界。」
- 术语卡：`03-配图素材/术语卡/09-SQL卡.png`。

**术语 10 · 聚合（含分组辨析）**
- 一句话定义：聚合是按分组用 COUNT、SUM、AVG 把多行算成一个值。
- 生活类比：班长收完全班作业，按小组数「每组交了几本、总分多少」——先分小组，再算每组的数。
- 易混辨析：**这是今天最该辨的一组**——「分组」和「聚合」不是一回事。GROUP BY 是分组，负责「按什么维度切」；COUNT / SUM / AVG 是聚合，负责「每组算几个」。顺序是先分组、后聚合；只分组不聚合，语法允许，但只是把维度去重列出来，并没有算出指标。面试常考这个区分。
- 面试说法：「GROUP BY 定维度、聚合函数算值，先分组后聚合；聚合列我都会加 AS 别名，看板直接用别名。」
- 术语卡：`03-配图素材/术语卡/10-聚合与分组卡.png`。

**术语 11 · 基线**
- 一句话定义：拿上线首周全量数据当参照，之后逐版比较的起点。
- 生活类比：装修前先给屋子拍一张照片，之后才好说「到底改好没有」，而不是听别人家装修得怎么样。
- 易混辨析：最容易和「行业健康线」「目标值」混。基线是「自己过去的起点」，健康线是「别人或行业给的量级参考」，目标是「想够到的数」；AI 产品形态差异大，我用基线对比法，不背行业数字。
- 面试说法：「健康线我不背行业数字，用基线对比法：以上线首周为基线，看每个版本的环比，公开数据只当量级参考。」
- 术语卡：`03-配图素材/术语卡/11-基线卡.png`。

**术语 12 · 看板**
- 一句话定义：按三层结构组织、带口径注释、可持续复用的指标集合。
- 生活类比：体检报告单，一堆指标按系统分好组，每一项都带参考范围和单位——不是一张孤零零的化验数值。
- 易混辨析：最容易和「一条 SQL 查询结果」混。查询结果是一次性切片，看板是「北极星 / 一级 / 护栏」三层齐备、每项带口径、能天天抬头看的东西。
- 面试说法：「我交付的不是一条查询，是三层看板：北极星一个、一级指标支撑、护栏防做歪，每项都写口径。」
- 术语卡：`03-配图素材/术语卡/12-看板卡.png`。

好，12 个词讲完了，现在把今天最要命的一件事单独拎出来：**率类指标的分子分母**。请大家翻到导学案《术语自测表》，看这张对照表，我逐格念，你们跟着填。

| 指标 | 分子 | 分母 | 最容易写错的分母 |
|---|---|---|---|
| 采纳率 | 被采纳的生成次数 | 总生成次数 | 写成「活跃用户数」 |
| 解决率 | 无人工介入且自然结束的问题会话数 | 总问题会话数 | 写成「全部会话数」 |
| 幻觉率 | 被判定为幻觉的回答数 | **抽检回答总数** | 写成「全部回答数」 |
| 留存 | 第 N 天仍活跃的新增用户数 | **当日新增用户数** | 写成「全部活跃用户数」 |
| 单次成本 | 当期成本之和 | 有效请求次数 | 写成「全部请求次数」含无效 |

记一句口诀，面试和写看板都靠它：**凡是「率」，先问分子是谁、分母是谁。** 分母一换，数字就变；分母不写，跨版本就没法比。DAU 是个例外，它是计数、根本没有分母，所以千万别把「DAU 涨了 30%」当成「某个率涨了」来分析。

现在做 10 分钟辨析练习：导学案第 0 层有连线和改错两类题，把「幻觉率」连到「抽检回答总数」、把「留存」连到「当日新增用户数」，再把三句写错分母的话改对。做完同桌互查。

最后的小测，12 题，答对 10 题算达标。第 2、3、7 题是率类三题，答错的同学别急，到讲五大指标那部分时我会再回扣一遍。

## 核心原理讲授 A

上节我们把名词对齐了，这节回答一个真问题：**没有指标，你的产品是死是活，你根本不知道。**

先讲个场景。教学示例：两个 AI 产品团队，产品几乎一样。A 团队每天开早会看三个数字：DAU、账单、老板心情。上个月 DAU 涨了，大家很高兴；这个月账单涨了，大家很紧张。有人提议砍模型换便宜的，有人提议加推送拉活，吵了一个月，谁也说服不了谁，因为每个数字都只反映「发生了什么」，不反映「该干什么」。B 团队的早会只盯一个数字：每周生成并被采纳至少三次的用户数。上个月这个数字跌了，他们顺着指标拆下去，发现是新用户的采纳率低——用户第一次生成的结果不好，用两次就走了。团队当周就改了新用户的默认模板。两周后数字回来了。

A 团队不是不努力，是没有仪表盘，在黑盒里开飞机——不知道高度、不知道油量、不知道方向。B 团队有一块仪表盘，跌了知道去哪查，涨了知道为什么。

我问一下大家：你怎么知道你的 AI 产品是好是坏？看 DAU 够吗？

对，不够。DAU 只告诉你「来了多少人」，不告诉你「用得值不值」。AI 产品的用户行为和传统产品不一样——用户来了，把你的生成结果扔掉一半，这个产品在用户心里其实已经死了。所以今天的第一个任务，就是给大家装一块 AI 产品专属的仪表盘。

我们进入五大核心指标。

看这张指标体系图，先记结构：最上面一层是北极星指标，全公司只看一个数；中间一层是一级指标，把北极星拆成几块，出问题能定位；最下面一层是护栏指标，防止北极星被「歪」着做上去。中间这一层的五个格子，就是今天要讲透的五大核心指标：采纳率、解决率、幻觉率、留存、单次成本。大家先把导学案上的「五大指标笔记表」翻出来，我一个一个讲，你们跟着填。上节小测里率类三题错的同学，重点听分母。

**第一个，采纳率。** 定义：AI 生成结果被用户接受的比例。公式：采纳率 = 被采纳的生成次数除以总生成次数。注意——分母是总生成次数，这正是上节对照表第一格。

听起来很简单，但这里有个面试官最爱挖的坑。

采纳率的分母是什么？用户改了三个字才采纳，算不算「采纳」？

分母是总生成次数，这个大家都能答对。第二个问题才是关键——修改后采纳算不算，没有标准答案，但**必须有答案**。你的产品把「原样发布」定为采纳，还是「采纳或修改后发布」都算，两种口径算出来的数字可能差一倍。所以采纳率这个指标，永远要带着口径说话：分母怎么算、采纳动作怎么定义、统计周期多长。口径不统一，指标就没法跨版本比较，这是新人写数据报告最常犯的错。

健康线怎么定？我教大家一个通用方法：**基线对比法**。不要背「行业采纳率是多少」，AI 产品的形态差异太大，没有放之四海的数字。正确做法是：上线第一周的全量数据就是你的基线，之后每个版本和基线比、和上一版比。写作辅助类产品常见区间大概在百分之三十到六十——这是示例值，需按业务校准，只能当量级参考。

常见误读有两条。第一，以为采纳率越高越好。如果一个用户重试十次才采纳一次，他的采纳率是百分之十——这个数字低是对的，因为它如实反映了「单次生成质量差」。第二，把「未采纳」一律归因为质量差。有可能用户只是进来试试看，根本没有真实任务。所以采纳率下降时，先查样本构成，再下结论。

**第二个，解决率。** 这是客服类、问答类产品的核心指标。定义：用户带着问题来，最终不需要人工介入、自然结束的比例。公式：解决率 = 无人工介入且自然结束的问题会话数，除以总问题会话数。分母是「总问题会话数」，不是全部会话——上节对照表第二格。

健康线怎么定？这里基线很好找——**你公司人工坐席的解决率**。AI 至少要追平人工，才谈得上替代，这是一条很硬的参照。客服场景公开参考值大概百分之六十到八十，示例值，需按业务校准。

这里有个隐蔽的坑：用户没再说话，等于问题解决了吗？

不一定。他可能是骂骂咧咧走了，可能是觉得「问这个破机器人不如自己查」。所以解决率必须交叉验证：看满意度评分、看转人工率、看重复进线率——同一个用户三天内为同一件事又来了，前一次的「自然结束」就是假解决。单一指标都会说谎，交叉验证才接近真相。

**第三个，幻觉率。** 这是 AI 产品区别于传统产品的特有指标。定义：生成内容中与事实或给定资料不符的比例。公式：幻觉率 = 被判定为幻觉的回答数，除以**抽检回答总数**。请把「抽检」两个字圈起来——分母不是全部回答，这是上节小测错得最多的一格。

注意，这个公式背后是「抽样 + 人工判定」或者「评测集回归」——为什么不能全自动统计？因为幻觉判定本身没有金标准，自动检测工具会漏也会误报，人工标注又贵又有主观性。

那我顺着问一句：幻觉率没有金标准，我们是不是就不用管了？

我听到有同学犹豫了。答案是：**不量化，不等于不管理**。没有金标准，我们做三件事：第一，分层抽检——按场景风险分配抽检比例，金额、政策、医疗这类高风险内容从严甚至全查，闲聊内容抽查即可；第二，评测集回归——每次改模型、改提示词，跑一遍固定评测集，防止「改好了 A 坏了 B」；第三，拒答单独统计——用户问超出范围的问题，模型说「我不知道」，这不是幻觉，这是好行为，混在一起算会惩罚诚实。

健康线按场景风险定门槛：对外知识问答类常见要求抽检幻觉率低于百分之二——示例值，需按业务校准；内部工具可以放宽，金融、医疗、法律对外场景要严格得多。

**第四个，留存。** 定义：一段时间后仍回来使用的用户比例。常用次日留存、七日留存，工具类产品还要看周活跃频次。公式：N 日留存 = 第 N 天仍活跃的新增用户数，除以**当日新增用户数**。分母又是「当日新增」这一批人，不是全部活跃——上节对照表第四格，请对齐。

AI 产品的留存有个特殊现象：尝鲜用户特别多。热点一来，注册一波，用一次就走的比例天然偏高。所以除了传统的留存率，AI 产品更要盯一个数：**习惯用户占比**——每周使用三次以上的用户占活跃用户的比例。三次是个经验阈值，示例值，需按你的产品校准。留存要按核心行为算，也就是「生成过」的用户，而不是「打开过 App」的用户。

那我问大家：DAU 涨了百分之三十，能说明产品变好了吗？

不能。三个理由：打开不等于得到价值，可能只是推送把你叫回来的；DAU 可以被廉价手段拉高，签到、积分、每日弹窗都行；而且 DAU 跌了你查不出原因，因为它不和任何价值环节挂钩。记住上节说的——DAU 是计数、没有分母，别把它当率来分析。这个问题我们马上在北极星部分展开，它是今天最重要的一题。

**第五个，单次成本。** 定义：每一次有效请求的平均推理成本。公式：单次成本 = 当期 token 用量乘以单价之和，除以有效请求次数；简单版就是当月 API 账单除以当月有效请求次数。分母是「有效请求次数」，重试、无效的那些怎么算，也是口径。

这是 AI 产品独有的「边际成本」视角——传统互联网产品边际成本趋近于零，AI 产品每回答一次都在花钱。健康线怎么定？不跟别人比，跟自己的「单次价值」比：单次成本必须显著小于单次收益，这个收益可以是营收贡献，也可以是替代的人力成本，用毛利倒推出成本上限。

常见误读三条：只看总账单不看单次——总量随增长上涨是正常的，会失控的是单次；为了省成本砍上下文、换小模型，结果采纳率掉了，省下的钱远不够赔的；忽略重试的隐性账——用户不满意多生成三次，成本翻了四倍，这四次都要算进来。

五大指标讲完了，收一句金句，这句可以写进面试自我介绍：**传统指标回答「来了多少人」，AI 指标回答「用得值不值」——采纳率、解决率、幻觉率、留存、单次成本，缺一个都是在黑盒里飞。**

一级指标有了，接下来是今天最重要的一件事：在五个格子和你的产品之间，选出那个唯一要抬头看的数字——北极星指标。

什么叫北极星指标？全公司所有团队，在所有争论拿不定主意的时候，抬头看的那一个数。它不是 KPI——KPI 是用来考核的，北极星是用来对齐方向的。这正是上节术语 1 的易混辨析，现在落到实处。

选北极星有三条标准，大家记下来，这本身就是一个面试题的标准框架：

第一，**绑价值**。用户获得核心价值的那一刻，就在贡献这个数字。自检问句：这个数字涨的时候，用户是真的多得到了价值吗？

第二，**可影响**。团队能通过本周的工作推动它，而不是只能等市场行情。自检问句：下个迭代我们做什么，能让它动？

第三，**可拆解**。它能拆成一级指标，出问题时能定位到环节。自检问句：它跌了，我能查到是哪个环节跌的吗？

现在用这三条标准，拆一个反面教材——DAU。

用三条标准逐条过一遍：DAU 绑价值吗？

不绑。打开 App 不等于得到价值，尤其是 AI 产品，打开之后甩手走人的比例不低。可影响吗？太可影响了——推送、签到、每日抽奖，都能把它推高，恰恰因为它太容易被廉价手段影响，反而失真。可拆解吗？DAU 跌了，你能查到是「采纳率跌了」还是「留存跌了」吗？查不到，因为它跟价值环节不挂钩。三条全灭，所以 DAU 不能当 AI 产品的北极星。

那正例长什么样？给大家一个教学示例：某 AI 写作工具，原来的北极星是 DAU，团队天天在做拉新和推送；后来把北极星改成了「每周生成并被采纳三次及以上的用户数」。注意这个定义的三个零件：有核心行为——生成；有质量门槛——被采纳；有习惯阈值——每周三次。改完之后，团队动作立刻从拉新转向了留存——因为新用户的采纳率上不去，这个数字就不动，而拉新拉来一堆不采纳的用户，数字反而被稀释。这是教学示例，不是真实公司数据，但结构是真实的：**北极星一换，全团队的动作跟着换**。这就是「北极星」这三个字的含义——它决定船往哪开。

光有北极星还不够，还要配护栏指标。什么是护栏？防止北极星被「歪」着做上去的约束指标。我给大家三个典型组合，可以直接抄进看板：北极星盯采纳，护栏就要盯重试率——采纳率涨了五个点，重试次数翻倍，说明用户是试了三次才成功一次，单次质量其实在降；北极星盯增长，护栏就要盯幻觉率和单次成本——新用户涌入如果让幻觉率和成本失控，增长就是在烧钱买口碑恶化；北极星盯留存，护栏要盯推送退订率——留存如果是靠弹窗弹回来的，退订率会先告诉你真相。注意，护栏和一级指标不是拆解关系、是并列约束关系，这正是上节术语 13 的辨析点，图上用虚线连。

第二句金句：**北极星决定船往哪开，护栏指标防止你为了追星把船开翻。**

现在宣布主项目要求：今天到实操演练那段，你要在导学案的「指标看板设计表」里，为自己的主项目填出完整三层——北极星一个，写明为什么过三标准；一级指标三到五个，从五大核心指标里选；护栏指标至少两个。周五 PRD 评审，「指标」是评委必问章节，今天这张表就是你的底稿。

这里补一个「边界」，请大家记牢：**五大指标不是每个产品都全部要用，也不是都有金标准。** 客服问答类产品，解决率和幻觉率是命门；写作辅助类产品，采纳率和单次成本是命门；工具类产品，留存和习惯用户占比是命门。常见误解是「把五个指标一股脑全塞进看板」——看板越厚，越没人看。正确做法是从北极星倒推：北极星需要哪几个一级指标支撑，就选哪几个，其余当护栏或暂时不量。另一个边界是健康线：我给的所有区间都是示例值、需按业务校准，基线对比法比背数字可靠得多，因为同一个百分比在不同产品形态里含义完全不同。

教学示例：某 AI 客服产品把北极星定为「无人工介入且被用户满意度评为解决的会话数」，一级指标只选解决率和幻觉率两个，护栏配转人工率。因为它从北极星倒推，看板只有两层四格，团队每天真看得过来；上线两周发现解决率追平人工坐席基线，才谈扩大覆盖。这是「少而准」的正例。

教学示例：另一团队把 DAU、注册数、生成次数、采纳率、解决率、幻觉率、留存、单次成本、推送打开率九个数字全堆进看板，还把「采纳率」的分母在两页里分别写成「按次」和「按会话」。结果同一个指标两页数字对不上，早会花半小时吵「哪个数是对的」，没人讨论该做什么动作。这是「指标口径混乱 + 只看北极星不看护栏」之外的第三种典型翻车——看板失焦。反面教训一句话：**没有口径的指标等于没写，堆满数字的看板等于没有看板。**

把今天这部分转成一句面试话：面试官问「你怎么设计 AI 产品指标体系」，你别先背五个名词，先给结构——「我按三层设计：北极星对齐方向、一级指标做支撑拆解、护栏防做歪；选一级指标时从北极星倒推，不堆数字；每个指标都带口径注释，分母、周期、来源写死。」这一句把三标准、口径、看板三个术语全用上了，比背名词高一个档。

## 核心原理讲授 B + 案例

欢迎回来。上半场我们装好了仪表盘，下半场练手艺。先回答一个灵魂问题：产品经理为什么要学 SQL？让数据分析师跑不行吗？

三个理由。第一，不排队：分析师的排期永远比你急，一个「采纳率跌没跌」的小问题，等一天不如自己三十秒——这里我说「自己三十秒」，指的是你能读懂、能核对，不是让你去写复杂联表。第二，不被糊弄：别人甩给你一个结论「数据不好看是正常波动」，你自己把分母和口径对一遍，就没人能糊弄你。第三，会讲故事：面试的时候，能现场说出「我读懂了一条按渠道算采纳率的查询，发现某渠道采纳率特别低，于是建议收窄那个渠道投放」的候选人，比背了十个指标的候选人值钱得多。

今天用的数据集叫「小笔」，一个 AI 写作助手的模拟数据，**教学示例数据**，两张表，特别简单：users 表，用户表，三个字段——user_id、channel 获客渠道、register_date 注册日期，一共八个用户；gen_records 表，生成记录表，六个字段——gen_id、user_id、gen_date、is_accepted 是否采纳、tokens 消耗量、cost_yuan 成本，一共十三条生成记录。两张表靠 user_id 关联。就这两个表，今天所有练习都从里面出，课后十题也是它，所以环境里有了它，等于零成本复习。所有数字都是教学示例，不代表任何真实产品。

再重申一次达标线（上节定的）：**今天 SQL 只讲产品要懂的读法与口径，不写成开发教程。** 下面四关，每一关我都先讲「这个关键字在业务上回答什么问题」，再讲怎么读，最后才给可运行语句。你要带走的是「能指着一条查询说清它在算什么、分母是谁」，不是背语法。

大家在自己设备上确认一下这两张表都能查出来，输入 select star from users，回车，能看到八行，就绪。电脑同学用本地或在线环境；平板同学用浏览器在线平台；手机同学这会儿不用敲，跟着投屏读懂这八行是什么即可，实操演练那段有你的替代动作。没就绪的同学举手，助教一对一处理，我们不等，先往下走。

SQL 就四个关键字：SELECT、WHERE、GROUP BY、JOIN。我们把它做成四关，一关一个字，闯过一关你就能读懂一类的活。

**第一关，SELECT——选列。**

SELECT 管的是「要哪些列」，业务上回答「这次要看哪几列」。看屏幕：

```sql
SELECT gen_id, is_accepted, cost_yuan FROM gen_records;
```

FROM 后面是表名，SELECT 后面是你要的列，逗号隔开。星号表示全要。跑一下——十三条记录，三列。这就是一条完整的 SQL。产品经理日常百分之四十的取数需求，读懂一个 SELECT 就够了。

**第二关，WHERE——筛行。**

SELECT 管列，WHERE 管行，业务上回答「只看哪一部分数据」。这里要提醒一句：**分母从这里开始变**——你一旦加了 WHERE，算出来的比率就只针对筛出来的那部分，口径注释必须跟着改。我只看没被采纳的：

```sql
SELECT * FROM gen_records
WHERE is_accepted = 0;
```

注意三个细节：等号是一个等号，不是两个；字符串要加引号；多个条件用 AND、OR 连接。我加一个日期条件，只看九月三号之后的未采纳记录——WHERE is_accepted = 0 AND gen_date 大于等于单引号 2026-09-03 单引号。跑一下，四条。现在你已经在做「切片」了：从全量数据里切出你关心的那一块。

学员现在做导学案练习 1：查 2026 年 9 月 3 号当天的生成记录，输出 gen_id、user_id、is_accepted 三列。电脑 / 平板同学跑一遍，手机同学读懂这条查询、口头说出它筛的是哪天后打勾。开始。

大部分同学写出来了。标准写法：SELECT gen_id, user_id, is_accepted FROM gen_records WHERE gen_date 等于单引号 2026-09-03。有人把列名和条件里的日期搞混了——记住，SELECT 后面是列，WHERE 后面是条件，日期是条件，不是列。

**第三关，GROUP BY——分组。**

前两关你只能「看」，第三关开始你就能「算」了。问题：每个用户一共生成了几次、被采纳了几次？这里正好用上讲术语那段术语 10 的辨析——GROUP BY 是分组、定维度，COUNT / SUM 是聚合、算每组的值，先分组后聚合。

```sql
SELECT user_id,
COUNT(*) AS gen_cnt,
SUM(is_accepted) AS acc_cnt
FROM gen_records
GROUP BY user_id;
```

GROUP BY user_id 的意思是：按用户分组，每组算一遍。COUNT 星号数行数，SUM 求和——这里有个巧思，is_accepted 是 0 和 1，求和正好等于采纳次数。AS 是起别名，看板上列名直接用别名，养成习惯，这正是术语 10 面试说法里那句。

SELECT 和 WHERE 各管什么？快速抢答。

对，SELECT 管列，WHERE 管行，GROUP BY 管组。三关口诀：先筛行，再分组，后选列。学员做练习 2：统计每个用户的生成次数和采纳次数，只留生成三次以上的。提示：加上 HAVING COUNT 星号大于等于三。HAVING 是分组后的过滤，WHERE 是分组前的过滤，这个区分面试也考。开始。

好，跑出来的同学会看到：只有 user_id 3 满足，生成三次、采纳两次。顺便看一眼全员分布，八个用户里有六个生成次数不超过两次——注意，这本身就是一个留存预警信号，数据会自己说话。

**第四关，JOIN——连表。**

最后的大招。前面所有分析都只有 gen_records 一张表，但我现在问：**哪个渠道的用户质量最高？** 渠道在 users 表，采纳在 gen_records 表，两张表必须连起来。业务上回答的是「跨表的两个事实怎么对上号」。

```sql
SELECT u.channel,
COUNT(*) AS gen_cnt,
SUM(g.is_accepted) AS acc_cnt,
ROUND(SUM(g.is_accepted) * 1.0 / COUNT(*), 2) AS acc_rate
FROM gen_records g
JOIN users u ON g.user_id = u.user_id
GROUP BY u.channel
ORDER BY acc_rate DESC;
```

逐个拆：FROM gen_records g，给表起短名字 g；JOIN users u，把用户表连进来；ON g.user_id = u.user_id，连接条件——两边靠 user_id 对上号；最后 GROUP BY 渠道，ORDER BY 按采纳率降序。注意这条查询算的正是采纳率，分母是「每个渠道的生成次数」COUNT 星号，分子是 SUM is_accepted——把讲术语那段的对照表第一格对上了。

跑之前，我故意先跑一个错误版本给大家抓 bug：

看，采纳率全是 0。为什么？

有同学看出来了——整数除法。SUM 和 COUNT 返回的都是整数，整数除以整数，小数部分直接扔掉，任何小于一的比率都变成零。修正：乘一个 1.0，把它变成浮点除法。这个坑以后你一定会踩，今天踩过一次，以后三秒解决。这也是产品经理最该会抓的一类错：**语法没报错，但数全错了**——比报错更危险。

第三句金句，送给大家贴在工位上：**比率必乘 1.0，口径必写注释——数据报告的两大保命符。**

好，重跑，出结果了。现在进入今天的高潮：**现场跑数**。我不随机讲，我按「用数据讲故事」的标准三步来，这三步你面试讲数据分析题时照用。

**第一条查询，看整体**：产品健康吗？

一条查询出三个数：总共十三条生成，整体采纳率 0.54，平均单次成本 0.039 元（教学示例数据）。30 秒结论：「小笔 13 次生成里 7 次被采纳，采纳率 0.54，每次成本不到 4 分钱。」这是讲故事的第一步——**用一句话给整体下判断**。

**第二条查询，做切片**：整体看着还行，但有没有哪天掉过链子？

按天看，9 月 5 号那天采纳率是 0.00——两次生成，零采纳。这就是切片的价值：**整体健康不代表天天健康**，趋势里的异常日就是你要追的问题。注意这里又一次出现了乘 1.0，以及 gen_cnt 只有 2——样本很小，先标记「待观察」，不要立刻定性。

**第三条查询，做归因**：9 月 5 号的问题到底是什么问题？我们换个维度，按渠道切开看。

结果：referral 渠道三次全采纳，search 0.43，social 只有 0.33。social 渠道的用户生成少、采纳少——假设你的投放预算正在往 social 砸，这条数据就是一句商业判断：「social 渠道来的用户质量偏低，先停投放，做一次落地页和新手引导的排查再说。」注意我刚才全程没有用一个形容词，全是数字加动作。

第四句金句，这是今天的主线：**整体看健康，切片找异常，归因给动作——数据讲故事就这三步。**

再强调一遍刚才那条纪律：referral 是 1.00 的采纳率，但只有三次样本。**样本量小的时候，先看次数，再看比率**——面试官如果追问「你这结论可靠吗」，这一句就是你的加分答案。

现在把两个能力合起来，讲讲「看板」。讲原理配案例那部分我们说看板是「三层结构 + 口径注释 + 可持续复用」，不是一条查询结果（术语 12）。怎么把刚才三条查询装进看板？整体那条出北极星和一级指标的总览；切片、归因那两条是出问题时往下钻的路径；每一层每个指标旁边都要写口径——分母、周期、来源。看板不是把查询截图贴上去，是把「抬头看什么、跌了往哪查、每个数怎么算」三件事固定下来。实操演练那段你们就照这个填自己的三层看板表。

补一个边界：**「整体 → 切片 → 归因」不是万能的，它最怕两件事——小样本和口径漂移。** 小样本刚才说了，先看次数再看比率；口径漂移是指，切片前后如果 WHERE 条件悄悄改了分母，切出来的「下跌」可能只是口径变了，不是真的跌。所以每次切片先问一句「这条查询的分母和整体那条一致吗」。常见误解是把「归因」当成「证明因果」——按渠道切出 social 低，只说明「相关」，要证明是渠道质量还是版本质量，还得按日期再切一刀、关联发版时间，这在习题第 10 题会练。

教学示例：某团队用「整体→切片→归因」发现采纳率整体 0.54、某日掉到 0.00、按渠道切出 social 最低，于是收窄 social 投放并改新手引导，两周后整体回到 0.58。三步每一步都留了查询和口径注释，复盘时能原样重跑——这叫「可复现的数据故事」。

教学示例：另一团队看到「整体采纳率涨了」就发捷报，没切片；实际上涨的原因是低质量渠道被停投、分母变小，而主力渠道的采纳率其实在跌（这正是面试追问那部分要考的「整体涨了分组跌了」）。更糟的是他们换人接手时没留口径注释，后来谁也说不清 0.54 是按次还是按会话算的。反面教训一句话：**不下切片的捷报，最容易把结构变化误读成整体变好。**

转成一句面试话：面试官给一条查询结果问「你怎么讲」，你答「我按三步讲：先用一句话给整体下判断，再切片找异常、并且先确认分母口径没漂，最后归因给一个具体动作；样本量小的地方我先标『待观察』，不会硬下结论」。这句把口径、切片、归因、样本量四个点全占了。

## 实操演练与巡场

现在把两个能力合起来。掏出导学案，翻到「主项目指标看板设计表」和「SQL 课堂练习」，三十二分钟，完成三件事。先说清楚分层达标线，别焦虑：

- **电脑同学**：本地或在线 SQL 环境跑通练习 1–3，看板表电子版填写。
- **平板同学**：浏览器在线平台粘贴运行教学示例数据集，跑 SELECT / WHERE / GROUP BY 三关；JOIN 那关若输入不便，改为「读懂讲师投屏的查询、口头核对分母」，看板表用文档 App 模板填。
- **手机同学**：不敲代码。你的任务是「读 + 核对 + 说」——看导学案上的查询卡，逐行口述它在算什么、分母是谁；用手机录音录一段 30 秒数据故事；与带电脑同学结对当「审稿人」，只提问不代写。

手机同学具体这样做：① 打开导学案实操演练那部分的三张查询卡，用手指指着读，每读完一条在旁边写「分母 = ______」；② 结对时问同伴三句话——「你这行分号呢？」「日期加引号了吗？」「这条的分母和整体那条一致吗？」；③ 用手机录音录 30 秒数据故事，回放自查有没有形容词、是不是「数字 + 动作」；④ 群内打卡交录音和口径批注。平板同学额外可用在线平台做「只读验证」：把讲师给的查询粘进去，看结果是不是 8 行 / 13 行 / 三条渠道，验证「读懂」对不对，不必自己从零敲。

三件产出，逐件说要求：

**任务一 · 主项目三层指标看板设计表**
第一层，北极星。一个指标，必须写出它过了三标准——绑什么价值、团队怎么影响它、能拆成什么。写「DAU」的不许交，除非你能当场反驳我刚才的三条拆解。
第二层，一级指标。三到五个，从五大核心指标里选，每个指标旁边写口径——分母是什么、统计周期多长。没有口径的指标等于没写，这是上节反面案例的教训。
第三层，护栏。至少两个，想清楚你的北极星可能被什么动作「歪」着推高，护栏就防那个动作。
（手机 / 平板同学用纸质导学案直接手写，不需要电子表格。）

**任务二 · SQL 读查询 + 核对口径 3 题**
练习 1（SELECT + WHERE）：查 2026-09-03 当天生成记录；练习 2（GROUP BY）：统计每用户生成与采纳次数，只留 ≥3 次；练习 3（JOIN）：按渠道算采纳率并说结论。电脑 / 平板跑数，手机同学完成「读懂 + 写分母 + 口头核对」。三题全部用同一份「小笔」教学示例数据集，零切换成本。

**任务三 · 30 秒数据故事**
用「整体看健康 → 切片找异常 → 归因给动作」写一句你的故事，句式：「整体采纳率 0.54，其中周 _ 掉到 __，归因是________，建议动作是________」。要求全是数字加动作，不许用形容词。手机同学直接录音。

- 走到卡住的学员旁：「先别急着改，读第一行——它告诉你错在哪一行。九成的错是分号、单引号、表名拼写这三样。」
- 走到写看板的学员旁：「你这个北极星，我用三标准问一句：『这个数字涨了，用户真的多得到价值了吗？』答得上来就过，答不上来我们一起改定义。」
- 走到只写了一个指标的学员旁：「护栏呢？北极星往上的时候，最可能被什么动作『歪』着推高？把那个动作防住。」
- 走到手机结对组旁：「审稿人别代写，只问三句：分号、引号、分母一致吗。教别人的过程本身就是复习。」
- 走到提前做完的学员旁：「觉得快很好，试试用一句 SQL 同时算出三个渠道的采纳率和平均成本——练习集第 10 题是给它的。」

最后两分钟，同桌互换，互相做一件事：拿着对方的北极星问一句「这个数字涨了，用户真的多得到价值了吗」——答不上来的，帮他把定义改到答得上来。好，停笔。

### 常见卡点 3 条（讲师讲评用）

| 卡点 | 表现 | 一句话解法 |
|---|---|---|
| 卡点 1 · 整数除法 | 练习 3 采纳率恒为 0，以为语法错了 | `SUM(is_accepted) * 1.0 / COUNT(*)`，比率必乘 1.0；语法没错、数全错比报错更危险 |

## 面试讲解与追问防御

先给一个通用答题骨架，今天 8 道题都套它：**先结构 → 再口径 → 再切片 → 再动作**。别一上来就背指标名。面试官要的不是你知道多少词，是你能不能把一个模糊问题拆成可验证的判断。四类题型今天都会碰到：技术理解、项目深挖、场景设计、行为题。每题我给五样东西：题目和题型、踩分点、追问链、典型失败答法、60 秒标准答法。两两模拟时，我会抽「面试追问卡」强制追两层，练的就是别卡住。
---

**面试题 1 · 「你怎么衡量一个 AI 产品做得好不好？看什么指标？」**（题型：技术理解 / 场景设计）

- **踩分点（4 条）**：① 先给价值视角——「传统指标回答来了多少人，AI 指标回答用得值不值」；② 给三层结构——北极星 / 一级 / 护栏；③ 报出五大核心指标中至少 4 个；④ 主动点名 DAU 不能当北极星并说一条理由。
- **追问链**：
- 第 1 层「五个指标里哪个最重要？」→ 答「没有通吃的最重要，从北极星倒推：客服看解决率和幻觉率，写作看采纳率和单次成本，工具看留存」。
- 第 2 层「那健康线怎么定？」→ 答「用基线对比法，以上线首周为基线看环比，公开数字只当量级参考，示例值需按业务校准」。
- 第 3 层「指标涨了就一定好吗？」→ 答「不一定，要配护栏看，比如采纳率涨了但重试翻倍，是单次质量在降」。
- **典型失败答法 + 失分原因**：「看 DAU、留存、转化率、增长率。」——全是流量视角，没提 AI 特有指标，也没给结构；失分在「把传统产品那套直接搬过来」，面试官会判定你没想过 AI 产品的价值时刻。
- **60 秒标准答法**：「我分三层看。先说视角：DAU 这类传统指标回答『来了多少人』，AI 产品得回答『用得值不值』，价值时刻在用户采纳生成结果的那一刻。所以顶层我设一个北极星，比如每周生成并被采纳 ≥3 次的用户数，用绑价值、可影响、可拆解三标准选出来；中间一级指标从五大核心指标倒推——采纳率、解决率、幻觉率、留存、单次成本，不是全堆上去，产品形态不同命门不同；底层配护栏，防北极星被歪着做上去。我会主动说一句：DAU 不能当 AI 产品的北极星，因为打开不等于得到价值、还能被推送廉价推高、跌了查不出原因。每个指标我都带口径，分母、周期、来源写死。」（含术语：北极星指标、采纳率、指标口径、DAU）
---

**面试题 2 · 「采纳率怎么定义？用户改了三个字才发布，算不算采纳？」**（题型：技术理解 / 项目深挖）

- **踩分点（4 条）**：① 给公式并说清分子分母（被采纳生成次数 / 总生成次数）；② 主动指出「修改后算不算」是口径问题、没有唯一答案但必须有答案；③ 说清口径三要素（分母按次还是按会话、采纳动作定义、统计周期与来源）；④ 补一句「口径不统一则跨版本不可比」。
- **追问链**：
- 第 1 层「那你们产品当初怎么定的？」→ 答「定为『原样发布或复制即算采纳，修改后发布也计入，分母按生成次数』，写进口径注释，全版本一致」。
- 第 2 层「重试 10 次才采纳 1 次，这个用户采纳率是多少、说明什么？」→ 答「10%，这个低是诚实的，说明单次质量差；所以采纳率要配重试率护栏一起看」。
- 第 3 层「口径后来改过吗，改了怎么办？」→ 答「改过就要重算历史基线并标注断点，不能直接把改前改后的数放一张图比」。
- **典型失败答法 + 失分原因**：「采纳率就是用户用了的比例，改了肯定也算啊。」——没给公式、没给分母、把口径当常识一口咬定；失分在「背结论不带口径」，一被追问「按次还是按会话」就卡住。
- **60 秒标准答法**：「采纳率 = 被采纳的生成次数 / 总生成次数，分母是总生成次数不是活跃用户数。您问的『修改后算不算』，我的回答是：没有唯一正确答案，但必须有答案，而且必须写进口径。我会定义三件事——分母按生成次数还是按会话、采纳动作包含哪些（复制、点采纳、原样发布、修改后发布算不算）、统计周期和数据来源。比如我们定成『原样或修改后发布都计入，分母按次』，全版本一致。为什么这么较真？因为口径一变数字就变，口径不统一，指标跨版本根本没法比。另外我一定配一个护栏：重试率，防止用户试十次才中一次、把低质量刷成好看的采纳率。」（含术语：采纳率、指标口径、基线、护栏）
---

**面试题 3 · 「整体采纳率这个月涨了，但拆开看某个渠道跌了，怎么解释？」**（题型：场景设计 / 项目深挖）

- **踩分点（4 条）**：① 不复述「整体涨了就好」，先承认这是结构变化、要按「整体 → 切片 → 归因」拆；② 指出可能是分母结构变了（低质量渠道停投、样本构成变化），即辛普森式结构效应；③ 先确认切片前后口径一致、看样本量；④ 给一个具体动作（收窄投放 / 排查落地页与新手引导 / 关联发版时间）。
- **追问链**：
- 第 1 层「那到底算好还是不好？」→ 答「先把『涨』拆开：是各分组普遍涨，还是靠分母结构变化涨；主力渠道跌了就不是真的好」。
- 第 2 层「怎么验证是渠道质量还是版本质量？」→ 答「按渠道切一刀，再按日期切一刀关联发版时间；各渠道同步跌更像是版本，单渠道跌更像是流量质量」。
- 第 3 层「某渠道采纳率 1.00，能不能直接加预算？」→ 答「先看次数再看比率，1.00 若只有 3 次样本就标『待观察』，不能直接定性」。
- **典型失败答法 + 失分原因**：「整体涨了说明整体策略有效，个别渠道波动正常，不用管。」——只看大盘就下结论、没切片、没查样本量；失分在「把结构变化误读成整体变好」，这正是讲原理 B 那部分的反面案例，面试官一追就露。
- **60 秒标准答法**：「我不会先说『涨了就好』。第一步按整体→切片→归因拆：整体涨，先确认切片的查询分母和整体那条口径一致，没漂移；第二步看结构——很可能是分母变了，比如低质量渠道停投、样本构成变化，把大盘比率抬上去了，而主力渠道其实在跌，这就是典型的结构效应；第三步给动作，按渠道切完再按日期切一刀关联发版时间，判断是流量质量还是版本质量。还有一条纪律：某个渠道采纳率 1.00 若只有三次样本，我先看次数再看比率，标『待观察』，不会直接建议加预算。结论我给成一句『数字 + 动作』，不加形容词。」（含术语：漏斗、指标口径、聚合与分组、基线）
---

**面试题 4 · 「你不会写 SQL，能做数据方向的产品经理吗？」**（题型：行为题）

- **踩分点（4 条）**：① 不把「不会写」说成硬伤，先划清产品与开发的边界；② 说清产品必须懂的三件事——读懂查询、核对分母与口径、判断结论可不可信；③ 举一个具体能抓的错（整数除法恒为 0、口径漂移、小样本）；④ 给协作方式（复杂查询交分析师，自己提需求并复核）。
- **追问链**：
- 第 1 层「那你怎么保证不被分析师糊弄？」→ 答「我核对三样：分母是谁、WHERE 有没有悄悄改口径、比率有没有乘 1.0；结论要求带口径注释」。
- 第 2 层「举个你真读懂过的例子」→ 答「按渠道 GROUP BY 算采纳率那条，我能说清分子是 SUM is_accepted、分母是每渠道生成次数，且 referral 1.00 只有 3 次样本要标待观察」。
- 第 3 层「如果只能招一个会写 SQL 的产品，为什么不招你？」→ 答「因为产品岗的稀缺能力是把数变成动作，不是写联表；我能提清晰需求、复核口径、讲 30 秒数据故事，复杂实现本来就该由分析师或工程做」。
- **典型失败答法 + 失分原因**：「我确实不会写，但我会努力学。」——把不会当缺陷道歉、没有边界、没有可验证能力；失分在「既没说清产品该懂什么，也没证明自己懂」，面试官会担心你连需求都提不清。
- **60 秒标准答法**：「能，而且我想先把边界说清楚：产品经理不负责写复杂查询，负责的是把数变成动作。SQL 我按『产品要懂的读法与口径』来要求自己——第一，能读懂一条查询在算什么、分母是谁；第二，能核对口径，比如 WHERE 有没有悄悄改分母、比率有没有乘 1.0 避开整数除法；第三，能判断结论可不可信，小样本先看次数再看比率。举个具体的：按渠道分组算采纳率那条，我能说清分子是 SUM is_accepted、分母是每渠道生成次数，referral 1.00 只有三次样本就得标待观察。复杂联表交给数据分析师，我负责把需求提清楚、把结果复核一遍、再讲成 30 秒的数据故事。所以『不会写』不是硬伤，『读不懂、核不了口径』才是。」（含术语：SQL、指标口径、聚合与分组、看板）
---

**面试题 5 · 「DAU 能不能当 AI 产品的北极星指标？」**（题型：技术理解 / 场景设计）

- **踩分点（4 条）**：① 明确说不能；② 用三标准逐条拆（不绑价值 / 被廉价手段推高 / 不可拆解）；③ 给替代公式「每周完成核心行为 N 次的用户数」并说出三零件（核心行为、质量门槛、频次阈值）；④ 补护栏。
- **追问链**：第 1 层「DAU 也有好处吧？」→ 答「有，当规模监控和护栏可以，不能当方向」；第 2 层「换个北极星团队动作会变吗？」→ 答「会，教学示例里从拉新转留存」；第 3 层「怎么防新北极星被刷？」→ 答「配重试率、幻觉率、退订率护栏」。
- **典型失败答法 + 失分原因**：「能啊，DAU 涨说明用的人多，是最直接的指标。」——方向性错误，且没用三标准；失分在「把规模当价值」。
- **60 秒标准答法**：「不能。我用北极星三标准逐条拆：第一，不绑价值，打开 App 不等于得到价值，AI 产品打开后甩手走人的比例不低；第二，表面可影响实则失真，推送、签到、每日弹窗都能把它推高，恰恰因为太容易被廉价手段影响，所以不可信；第三，不可拆解，DAU 跌了，你查不到是采纳率跌了还是留存跌了，它跟价值环节不挂钩。三条全灭。我会换成『每周生成并被采纳 ≥3 次的用户数』——有核心行为『生成』、有质量门槛『被采纳』、有习惯阈值『每周三次』。教学示例里这么一换，团队动作立刻从拉新转向留存。当然还要配护栏：重试率防刷采纳、幻觉率和单次成本防增长失控。DAU 不是没用，它适合当规模护栏，不适合当方向。」（含术语：北极星指标、DAU、采纳率、看板）
---

**面试题 6 · 「幻觉率判定没有金标准，你们为什么还统计它？」**（题型：技术理解）

- **踩分点（4 条）**：① 亮明「不量化不等于不管理」；② 给三种做法（分层抽检 / 评测集回归 / 高风险场景从严）；③ 说清分母是抽检回答总数、拒答单独统计不算幻觉；④ 说不统计的后果（风险不可见、版本改好改坏无从判断）。
- **追问链**：第 1 层「人工标注主观怎么办？」→ 答「制定判定规则 + 多人一致率 + 高风险内容全查」；第 2 层「成本扛得住吗？」→ 答「按场景风险分配抽检比例，闲聊抽查、金额政策医疗从严」；第 3 层「怎么盯版本 regression？」→ 答「每次改模型或提示词跑固定评测集回归」。
- **典型失败答法 + 失分原因**：「既然没标准答案，统计了也不准，不如不统计。」——把「没金标准」等于「不能管理」；失分在放弃管理责任。
- **60 秒标准答法**：「我的立场很明确：不量化，不等于不管理。幻觉率的公式是『被判定为幻觉的回答数 / 抽检回答总数』，分母是抽检总数不是全量回答，因为判定本身没有金标准、自动检测会漏会误报。我们做三件事：分层抽检，按场景风险分配比例，金额、政策、医疗从严甚至全查，闲聊抽查；评测集回归，每次改模型或提示词跑一遍固定评测集，防止改好 A 坏了 B；拒答单独统计，模型说『我不知道』是好行为，混进幻觉率会惩罚诚实。为什么不干脆不统计？因为不统计的后果是风险完全不可见，版本改好改坏也无从判断。健康线按场景分层定，对外知识问答常见的低于百分之二是示例值、需按业务校准。」（含术语：幻觉率、幻觉率口径、基线、指标口径）
---

**面试题 7 · 「采纳率涨了 5 个点，但重试次数翻倍，说明什么？」**（题型：项目深挖）

- **踩分点（4 条）**：① 判定为护栏报警、不是纯利好；② 解释机理「用户多试几次才命中，单次生成质量在降」；③ 关联「基线 / 环比」与「样本构成」两种排查；④ 给动作（查单次质量、看版本变更、别急着发捷报）。
- **追问链**：第 1 层「那采纳率这个数还能用吗？」→ 答「能用，但必须和重试率一起看，单一指标会说谎」；第 2 层「怎么定位原因？」→ 答「按日期切片关联发版，按新 / 老用户切片看样本构成」；第 3 层「成本会怎么变？」→ 答「重试翻两倍单次成本涨，用单次成本护栏交叉验证」。
- **典型失败答法 + 失分原因**：「说明用户更爱用了，重试多代表活跃，是好事。」——把护栏报警读成利好；失分在只看北极星不看护栏。
- **60 秒标准答法**：「这是护栏在报警，不是纯利好。采纳率涨 5 个点，但重试翻倍，最可能的机理是单次生成质量在降——用户得试三次才中一次，那个『涨』是拿次数堆出来的，不是一次就接住。所以第一，我不会急着发捷报，采纳率必须和重试率这条护栏一起看，单一指标都会说谎；第二，按整体→切片→归因排查，按日期切片关联有没有发版、按新老用户切片看是不是样本构成变了；第三，用单次成本交叉验证，重试翻倍成本一定跟着涨；第四，动作是回头查默认模板、提示词或模型版本，而不是继续推采纳率。一句话：北极星决定船往哪开，护栏防止你为了追星把船开翻。」（含术语：采纳率、看板、单次成本、基线）
---

**面试题 8 · 「你怎么给老板讲一条 SQL 跑出来的结论？」**（题型：行为题 / 场景设计）

- **踩分点（4 条）**：① 用「整体 → 切片 → 归因」三步组织；② 结论写成「数字 + 动作」不加形容词；③ 主动标注口径与样本量（分母、待观察）；④ 30 秒内讲完、留一句可复核的查询路径。
- **追问链**：第 1 层「老板说『数据不好看是正常波动』呢？」→ 答「把分母和口径对一遍，按日期切片看是不是单日异常」；第 2 层「结论被质疑可靠吗？」→ 答「小样本先看次数再看比率，标注待观察」；第 3 层「老板要你立刻砍预算呢？」→ 答「给一步可复核的验证动作，先收窄投放再排查落地页，不把相关当因果」。
- **典型失败答法 + 失分原因**：「我把查询结果截图发给老板，让他自己看。」——只给数据不给判断、没有结构、没有动作；失分在「把取数当汇报」。
- **60 秒标准答法**：「我按三步讲，30 秒收口。第一步整体，一句话给判断：『小笔 13 次生成里 7 次被采纳，采纳率 0.54，每次成本不到 4 分钱』——全是数字，不加形容词。第二步切片，找异常：『9 月 5 号采纳率掉到 0.00，但只有两次生成，先标待观察』，这里我主动报口径和样本量，分母是生成次数。第三步归因给动作：『按渠道切开 social 只有 0.33，建议先停 social 投放，排查落地页和新手引导』，并且说明这是相关不是因果，我会再按日期切一刀关联发版时间复核。最后留一句可复现的路径：查询和口径注释都在看板里，您要复核我原样重跑。给老板的结论，永远是数字加动作，不是一堆截图。」（含术语：看板、指标口径、聚合与分组、漏斗）

### 学习目标

> 结论前置：指标的作用不是「好看」，而是**让「这个 AI 产品值不值得继续做」变成一道能算的题**。

1. 画出「北极星 + 四层 + AI 五专有」指标树，说明每层回答什么问题。
2. 读懂 events 表字段定义，说明每个字段支撑哪个指标。
3. 写出 4 段 SQL，并逐段写出「产品怎么读这个数」。

### 核心概念

**结论：先定事件与口径，再写 SQL；SQL 只是把已经想清楚的问题算出来。**

| 层 | 回答什么问题 | 示例指标 |
| --- | --- | --- |
| 北极星指标 | 核心价值有没有长 | 每周成功解决的会话数（教学假设口径） |
| 输入指标 | 来了多少量 | 提问数、DAU |
| 过程指标 | 链路走不走得通 | 答案展示率、命中率 |
| 结果指标 | 价值达没达成 | 标记有用率、次日留存 |
| 护栏指标 | 有没有为增长牺牲底线 | 幻觉率、人工接管率、P95 延迟、Token 成本/次 |

AI 特有五指标（口径均为教学假设定义）：**命中率**（检索到可用依据的会话占比）、**幻觉率**（抽检判为编造的答案占比）、**人工接管率**（转人工会话占比）、**Token 成本/次**（单次调用平均推理花费）、**P95 延迟**（95% 请求在此耗时内完成）。易混点：命中率不等于答对率；幻觉率须靠抽检或评测集，不能由模型自报。

### 方法框架

> 以下指标树、表结构与 4 段 SQL 为按 W4D4 主题补入的教学内容。**以下表结构与数据均为教学假设**，仅用于练习，不代表任何真实系统或企业经营数据；示例数字一律标注「教学假设」。

**框架 1｜指标树模板**：北极星 → 输入/过程/结果/护栏四层 → 挂 AI 五专有 → 每层指定一个「产品动作」（如护栏超线就降级或限流）。

**框架 2｜events 表字段定义（教学假设，以 MySQL 8.0 语法为例）**

| 字段 | 类型 | 含义 | 支撑的指标 |
| --- | --- | --- | --- |
| event_id | BIGINT | 事件唯一 ID | 全表去重 |
| user_id | VARCHAR(64) | 匿名化用户 ID | DAU、次日留存 |
| session_id | VARCHAR(64) | 会话 ID | 漏斗转化 |
| event_name | VARCHAR(32) | `query_submit` / `answer_shown` / `answer_useful` / `human_handoff` | 漏斗、命中率 |
| event_time | TIMESTAMP | 事件时间 | 按天/分位计算 |
| model_id | VARCHAR(32) | 模型标识（教学假设 `model_a` / `model_b`） | 分组成本/延迟 |
| is_ai_answer | TINYINT | 是否由大模型生成（1 是 / 0 规则或人工） | 降级占比 |
| is_hallucination | TINYINT | 抽检是否判为幻觉（1 是 / 0 否） | 幻觉率 |
| is_handoff | TINYINT | 是否转人工（1 是 / 0 否） | 人工接管率 |
| token_in / token_out | INT | 输入/输出 Token 数 | Token 成本/次 |
| cost_rmb | DECIMAL(10,4) | 本次调用成本（教学假设，单位元） | 成本分组 |
| latency_ms | INT | 端到端延迟（毫秒） | P95 延迟 |
| confidence | DECIMAL(4,3) | 置信度 0–1 | 分档展示 |

**框架 3｜4 段 SQL（每段含注释与「产品怎么读这个数」）**

```sql
-- SQL 1【教学假设】目标：按天统计日活跃用户数（DAU）
-- 口径：当天发起过 query_submit 的去重用户数
SELECT DATE(event_time)       AS dt,
       COUNT(DISTINCT user_id) AS dau
FROM events
WHERE event_name = 'query_submit'
GROUP BY DATE(event_time)
ORDER BY dt;
```
**产品怎么读这个数**：DAU 回答「有多少人真的来用」，看趋势不看单日；若 DAU 平稳但北极星（成功解决会话数）下滑，说明「人来了却没办成事」，应查过程指标而非拉新。

```sql
-- SQL 2【教学假设】目标：新用户次日留存（D1 Retention）
-- 口径：首次提问日为 cohort，次日仍发起 query_submit 记为留存
WITH first_day AS (
  SELECT user_id, MIN(DATE(event_time)) AS first_dt
  FROM events
  WHERE event_name = 'query_submit'
  GROUP BY user_id
),
next_day AS (
  SELECT DISTINCT f.user_id, f.first_dt
  FROM first_day f
  JOIN events e
    ON e.user_id = f.user_id
   AND e.event_name = 'query_submit'
   AND DATE(e.event_time) = DATE_ADD(f.first_dt, INTERVAL 1 DAY)
)
SELECT f.first_dt                                     AS cohort_dt,
       COUNT(DISTINCT f.user_id)                       AS new_users,
       COUNT(DISTINCT n.user_id)                       AS retained_d1,
       ROUND(COUNT(DISTINCT n.user_id) * 1.0
             / NULLIF(COUNT(DISTINCT f.user_id), 0), 3) AS d1_retention
FROM first_day f
LEFT JOIN next_day n
  ON n.user_id = f.user_id AND n.first_dt = f.first_dt
GROUP BY f.first_dt
ORDER BY f.first_dt;
```
**产品怎么读这个数**：次日留存回答「第一次用完还愿不愿意回来」。留存低常见根因不是功能少，而是首次就遇到幻觉或答非所问——要回看 D3 兜底与置信度分档，而不是先改界面。

```sql
-- SQL 3【教学假设】目标：主链路漏斗 提交问题 → 看到答案 → 标记有用
-- 口径：以 session_id 去重，逐步骤计数并算逐级转化率
SELECT
  COUNT(DISTINCT CASE WHEN event_name = 'query_submit'  THEN session_id END) AS step_submit,
  COUNT(DISTINCT CASE WHEN event_name = 'answer_shown'  THEN session_id END) AS step_shown,
  COUNT(DISTINCT CASE WHEN event_name = 'answer_useful' THEN session_id END) AS step_useful,
  ROUND(
    COUNT(DISTINCT CASE WHEN event_name='answer_shown' THEN session_id END) * 1.0
    / NULLIF(COUNT(DISTINCT CASE WHEN event_name='query_submit' THEN session_id END), 0)
  , 3) AS submit_to_shown,
  ROUND(
    COUNT(DISTINCT CASE WHEN event_name='answer_useful' THEN session_id END) * 1.0
    / NULLIF(COUNT(DISTINCT CASE WHEN event_name='answer_shown' THEN session_id END), 0)
  , 3) AS shown_to_useful
FROM events;
```
**产品怎么读这个数**：`submit_to_shown` 掉得多，多半是超时、拒答、无答案——查 D3 异常表；`shown_to_useful` 掉得多，说明答案给了但不靠谱——查幻觉率与评测集。用 `NULLIF` 防除零，让报表在空数据日也不报错。

```sql
-- SQL 4【教学假设】目标：按模型分组对比成本、P95 延迟、幻觉率、人工接管率
-- 口径：仅统计 is_ai_answer = 1；P95 用窗口函数按延迟排序取 95% 位置
WITH ranked AS (
  SELECT model_id, latency_ms, cost_rmb, is_hallucination, is_handoff,
         ROW_NUMBER() OVER (PARTITION BY model_id ORDER BY latency_ms) AS rn,
         COUNT(*)     OVER (PARTITION BY model_id)                      AS cnt
  FROM events
  WHERE is_ai_answer = 1
)
SELECT model_id,
       COUNT(*)                                                 AS calls,
       ROUND(AVG(cost_rmb), 4)                                   AS avg_cost_per_call,
       ROUND(AVG(latency_ms), 0)                                 AS avg_latency_ms,
       MAX(CASE WHEN rn <= CEIL(cnt * 0.95) THEN latency_ms END) AS p95_latency_ms,
       ROUND(AVG(is_hallucination), 3)                            AS hallucination_rate,
       ROUND(AVG(is_handoff), 3)                                  AS handoff_rate
FROM ranked
GROUP BY model_id
ORDER BY avg_cost_per_call;
```
**产品怎么读这个数**：这是「换不换模型」的决策依据——便宜但 P95 延迟高、幻觉率高的模型未必真省；护栏指标任一超线，就按 D3 顺序把流量切走。`MAX(CASE WHEN rn <= CEIL(cnt*0.95) ...)` 之所以是 P95，是因为 `rn` 已按延迟升序排好，取前 95% 里最大的延迟值即为分位点。

### 常见问题

1. **结论：先看护栏再看增长。** 幻觉率或 P95 超线时，DAU 涨得越快风险越大。
2. **结论：P95 不能换成平均值。** 平均值会把把用户拖走的长尾慢请求藏起来。
3. **结论：幻觉率靠抽检或评测集，不靠模型自报。** 自报置信度只用于分档展示。
