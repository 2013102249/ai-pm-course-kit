## 二、教学目标（可测量，共 8 条）

1. 能指出一段问题 PRD 片段中的至少 5 处缺陷，并逐条改写成合格表述（验证：对应板块片段改错练习，按 06-分层习题 rubric 判分 ≥60 分）。
2. 能独立按十章骨架写出主项目 PRD V1.0，其中「评测标准」一章必须含指标名 + 数字门槛 + 数据来源三要素（验证：对应板块当堂提交的十章骨架 + 周五答辩）。
3. 能向他人解释 AI 产品 PRD 与传统 PRD 的五处差异（评测标准 / 容错兜底 / 幻觉控制 / 成本预算 / 数据回流），每处各配一个自己的项目实例（验证：对应板块速记表 + 课后 PRD 全文 + 周五答辩）。
4. 【术语目标】能准确说出本日 12 个术语的一句话定义、生活类比与易混辨析，并在句子中正确使用，不混用「验收标准 / 口径」「异常态 / 边界条件」（验证：对应板块术语自测表 12 行全对 ≥10 行，术语小测 ≥80 分）。
5. 【术语目标】能对一段含混需求指出「口径不清」「缺少模型能力假设」并补写，使研发无需二次追问（验证：对应板块改错练习 + 对应板块互评记录）。
6. 【面试目标】能在 60 秒内用「总述 + 五处差异 + 1 个示例」结构回答「AI PRD 和传统 PRD 差在哪」，踩中至少 3 个踩分点（验证：对应板块面试模拟记录表自评 + 同伴评分）。
7. 【面试目标】面对「研发说做不到」类追问，能给出「承认约束 → 拆可验收口径 → 给降级方案 → 写进变更记录」四步应答，不空辩、不甩锅（验证：对应板块追问链模拟 + 06-分层习题第 4 层评分表）。
8. 能把本日产出按「产出物 / 完成度 / 归档位置」三列登记进《本日作品集积木》，并说出每件作品对应面试里哪个问题（验证：对应板块归档动作 + 当堂验收抽查）。

## 三、教学重难点

- **重点一**：五处差异——这是 AI 产品 PRD 区别于传统 PRD 的核心，也是本周五评审大会的评分依据之一，更是面试官判断「你做没做过 AI 产品」的五个探针。
- **重点二**：评测标准可量化三要素（指标名 + 数字门槛 + 数据来源），以及把幻觉控制白纸黑字写进 PRD 的三道防线（引用来源 / 阈值拒答 / 幻觉率红线）。
- **难点一**：评测标准可量化。学员习惯写「效果要好、体验要佳」，需要反复用「指标名 + 数字 + 数据来源」三要素模板矫正。
- **难点二**：逐章写作节奏。10 章内容边讲边写，学员容易在前几章（背景、目标）过度打磨，导致后面 AI 能力需求、评测标准这些 AI 特有章节没时间写。讲师需严格执行计时。
- **难点三【术语混淆】**：零基础学员易把「验收标准」与「口径」、「异常态」与「边界条件」、「降级方案」与「容错兜底」当成同义词混用；「模型能力假设」是 AI 产品特有、传统 PRD 无对应的概念，最易漏写。对应板块须用「易混辨析」逐对拆开，并在对应板块写作时回查。
- **难点四【面试失分】**：学员答「AI PRD 差在哪」时只会背五处名称、举不出可验收例子；答「研发说做不到」时容易陷入争辩或甩锅，缺少「拆口径 + 给降级 + 留变更记录」的闭环。对应板块须用踩分点、追问链、失败答法逐项矫正。

## 五、AI 产品 PRD 与传统 PRD 的五处差异（逐条教学设计）

> 对应板块的教学核心，保留原有全部逐条设计。每条按「传统怎么写 → AI 为什么要改 → 改后长什么样」三步讲，全部示例为教学示例。本课版在每条后补「为什么 / 边界 / 常见误解」一句，详见「02-讲课稿」对应板块。

### 差异一：评测标准——从「功能验收」到「效果验收」

| 层次 | 内容 |
|---|---|
| 传统怎么写 | PRD 附验收标准：功能点逐条打勾即可上线。登录功能「能登录」就算完成，测试用例 = 操作路径是否走通。（教学示例） |
| AI 为什么要改 | AI 产品的输出是概率性的：同一问题两次回答可能不同，「做出来了」不等于「答得对」。没有量化标准，团队对「什么算合格」会产生无休止的争论，且研发无法自证达标。 |
| 改后长什么样 | 「支持用户对课程政策提问，回答须引用知识库原文，引用正确率 ≥90%；无法回答时触发转人工话术，拒答恰当率 ≥85%。评测集 ≥50 条，来源为真实用户问题。」（教学示例）——指标名 + 数字门槛 + 数据来源，三要素缺一不可。 |
| 边界 / 常见误解 | 不是所有指标都要数字门槛；护栏类指标可先定「监测 + 红线」。常见误解：把「上线后再定标准」当灵活，实则是把验收口径拱手让人。 |

### 差异二：容错兜底——从「异常提示」到「四级降级链」

| 层次 | 内容 |
|---|---|
| 传统怎么写 | 异常流程一节：接口超时弹「网络异常请重试」，404 跳错误页。异常 = 系统故障，发生频率低。（教学示例） |
| AI 为什么要改 | AI 产品的「错」不是故障而是常态：检索不到、模型超时、答案低置信都是日常。没有兜底设计，每一次模型失误都直接暴露给用户，信任一次性崩塌。 |
| 改后长什么样 | 「低置信回答 → 先澄清追问；检索无结果 → 明确拒答并推荐入口；连续 2 次拒答 → 引导转人工；模型服务不可用 → 降级为关键词搜索 FAQ。」（教学示例）——澄清、拒答、转人工、降级四级链路，周三兜底设计课将逐级展开。 |
| 边界 / 常见误解 | 澄清与拒答顺序不可颠倒：问题模糊先澄清，问题清楚但无依据须直接拒答。常见误解：把「尽量给个参考答案」当体验好，实则是鼓励编造，与幻觉控制原则根本冲突。 |

### 差异三：幻觉控制——传统 PRD 里不存在的一章

| 层次 | 内容 |
|---|---|
| 传统怎么写 | 传统 PRD 没有这一概念——程序输出是确定性的，不存在「一本正经地编造」。 |
| AI 为什么要改 | 幻觉是概率续写引擎的本能（回扣 W3D3）。用户不区分「模型编的」和「产品说的」，一次编造毁掉全部信任。必须把幻觉从「技术问题」上升为「产品需求」。 |
| 改后长什么样 | 「回答必须基于检索到的知识库内容生成，每个关键结论标注引用来源；相似度低于阈值时不得生成，直接进入拒答流程；每周抽检 badcase ≥20 条，幻觉率 >5% 触发回滚。」（教学示例） |
| 边界 / 常见误解 | 三道防线对应事前约束（引用）、事中拦截（阈值）、事后追责（红线）。常见误解：以为幻觉控制是算法团队的事；产品经理才是把三道防线写进 PRD 的责任人。 |

### 差异四：成本预算——从「服务器粗估」到「单次调用成本」

| 层次 | 内容 |
|---|---|
| 传统怎么写 | 非功能需求一节带过：「预计服务器 4 核 8G × 3 台」，与产品逻辑无关，研发和运维关心即可。（教学示例） |
| AI 为什么要改 | AI 产品每回答一次都在花钱：输入输出按 token 计费，成本随用户量线性增长且与产品设计直接相关——上下文给多少、Top-K 取几、用哪个模型，都是产品决策，写进 PRD 才能约束住。 |
| 改后长什么样 | 「单次问答成本 ≤0.05 元（按输入 2000 token + 输出 500 token、当前模型单价估算）；单用户单日调用上限 50 次；月度 API 预算 5000 元，超 80% 触发预警。」（教学示例） |
| 边界 / 常见误解 | 数字可估算、可修正，「后续评估」式空白不可接受。常见误解：把成本当运维细节；它约束的是产品设计本身（上下文长度、模型选型）。 |

### 差异五：数据回流——从「埋点看数」到「badcase 闭环」

| 层次 | 内容 |
|---|---|
| 传统怎么写 | 数据需求一章：PV、UV、停留时长等埋点清单，供 BI 报表使用，与产品迭代弱关联。（教学示例） |
| AI 为什么要改 | AI 产品的迭代燃料不是功能加法，而是 badcase 修复。线上每一个答错的问题，都应该变成评测集里的新用例——没有回流机制，评测集永远停在上线那天，产品不会变好。 |
| 改后长什么样 | 「用户点踩时必填原因标签（答错 / 答非所问 / 引用错误 / 其他）；点踩样本自动进入待标注队列，每周筛选入评测集；采纳率、解决率、幻觉率每周出报告。」（教学示例） |
| 边界 / 常见误解 | 归因标签宜 ≤4 个，须「互斥、好懂、能指导动作」。常见误解：把「加了埋点」当数据回流；埋点是看数据，回流是喂产品，闭环才算数。 |

## 六、主项目 PRD 十章结构：逐章讲法

> 对应板块精讲蓝本，保留原有逐章设计。每章给出「讲什么 + 学员写什么」；本课版把原对应板块的动笔实操单列，本章只讲写法、正反面案例与边界。示例均标注教学示例。

| 章 | 章名 | 讲法要点 | 学员当堂填写（引导句） |
|---|---|---|---|
| 1 | 背景 | 为什么做：业务痛点 + 立项依据。直接引用昨日调研数据，「我访谈了 6 人，其中 4 人提到……」 | 「根据调研，我们发现……」 |
| 2 | 目标 | 1 个北极星指标 + 2 个护栏指标；目标必须可测量，禁止「提升用户体验」 | 「本项目北极星指标为____，目标值____」 |
| 3 | 用户与场景 | 目标用户画像 + 3 个核心场景，每个场景 = 谁 + 什么时候 + 想完成什么 | 「场景一：____在____时，想要____」 |
| 4 | 功能需求 | 功能列表 + 优先级（P0/P1/P2），每条功能写清输入、处理、输出 | 「P0：用户输入____，系统____，输出____」 |
| 5 | AI 能力需求 | 本产品哪些环节用模型、用什么能力（生成 / 检索 / 结构化）、提示词策略初稿——提示词是需求的一部分 | 「本模块 AI 能力为____，提示词初稿见附录」 |
| 6 | 评测标准 | 三要素模板：指标名 + 数字门槛 + 数据来源；至少含效果与幻觉两类指标 | 「引用正确率 ≥____%，评测集____条，来源____」 |
| 7 | 容错兜底 | 四级链路自检：低置信怎么办 / 无结果怎么办 / 连续失败怎么办 / 服务不可用怎么办 | 「当____时，系统将____」 |
| 8 | 成本预算 | 单次成本公式：输入 token × 单价 + 输出 token × 单价；日调用上限与月预算 | 「单次成本 ≤____元，月预算____元」 |
| 9 | 数据回流 | 点踩归因标签设计 + badcase 入评测集的周期 + 三个周报指标 | 「用户点踩时收集____，每周回流____条」 |
| 10 | 风险 | 技术风险 / 数据风险 / 合规风险各 1 条，每条附应对思路 | 「风险：____；应对：____」 |

**对应板块深化要求（对应「02-讲课稿」对应板块）**：至少 1 个正面案例（十章齐全、评测标准可验收的完整片段）、1 个反面案例（缺第 5–9 章、写「效果要好」的片段），并讲清「为什么十章是这个顺序」「边界：提示词改动走变更流程」「常见误解：把 PRD 当任务说明书越短越好」。

## 八、课堂提问设计（20 问，附预设答案；术语辨析 7 + 面试追问 7 + 原理 6）

| # | 类别 | 提问 | 提问时机 | 预设答案 / 引导方向 |
|---|---|---|---|---|
| T1 | 术语辨析 | 「验收标准」和「口径」是同一件事吗？各自回答谁的疑问？ | 对应板块 | 不是。验收标准是「怎样算合格」的量化条款；口径是「按什么定义 / 什么范围来算」的共识。先有口径，才有验收标准。 |
| T2 | 术语辨析 | 「异常态」和「边界条件」差在哪？各举一个本项目的例子。 | 对应板块 | 异常态是运行时出错的状态（检索无结果、模型超时）；边界条件是输入 / 范围的临界值（问题超出知识库范围、单次输入超长）。一个讲「出错」，一个讲「到边」。 |
| T3 | 术语辨析 | 「降级方案」和「容错兜底」能不能画等号？ | 对应板块 | 不能。容错兜底是整章设计（四级链路）；降级方案是其中「服务不可用时」一级的具体动作（如降级为关键词搜索 FAQ）。整体与局部。 |
| T4 | 术语辨析 | 「PRD」和「需求文档」哪个范围大？为什么面试里要分清楚？ | 对应板块 | 需求文档是统称，PRD 是其中面向研发、含验收与 AI 特有章节的正式文档。混用会显得没写过正式评审件。 |
| T5 | 术语辨析 | 「模型能力假设」为什么传统 PRD 里没有？漏写会怎样？ | 对应板块 | 传统程序能力确定，无需假设；AI 输出概率性，须写明「假设模型能做到 X、做不到 Y」。漏写则评测与兜底无的放矢，研发说做不到时无据可依。 |
| T6 | 术语辨析 | 「评审」和「变更记录」分别在产品的哪个时点起作用？ | 对应板块 | 评审在上线 / 合入前把关（周五评审大会）；变更记录在通过后留痕（提示词改动、V2.0）。一个管准入，一个管可追溯。 |
| T7 | 术语辨析 | 「五处差异」里「幻觉控制」为什么单独成一处，不并入「容错兜底」？ | 对应板块 | 容错兜底处理「答不出 / 服务错」，幻觉控制处理「答得像但编的」。后者是 AI 独有、传统 PRD 无对应章，必须单列才不会被漏写。 |
| Q1 | 原理 | 「研发拿到『支持智能问答』这半句话，能开工吗？」 | 对应板块导入 | 不能——不知道答什么、答到什么程度、答错了怎么办。需求要写到研发无需来问的程度。 |
| Q2 | 原理 | 「『提升用户体验』为什么不是合格的目标？」 | 对应板块 | 不可测量，无法验收；合格目标 = 指标 + 数字 + 截止时间。 |
| Q3 | 原理 | 「用户问了一个知识库里根本没有的问题，产品应该怎么办？」 | 对应板块 | 先澄清确认理解；确认超出范围就明确拒答并给替代入口，绝不能硬编——引出拒答机制。 |
| Q4 | 原理 | 「为什么成本要写进 PRD？不是技术的事吗？」 | 对应板块 | 上下文长度、Top-K、模型选择都是产品决策，直接决定单次成本；成本是产品约束，不是运维细节。 |
| Q5 | 原理 | 「数据回流和普通埋点有什么区别？」 | 对应板块 | 埋点是「看数据」，回流是「喂产品」——badcase 要进入评测集驱动下一轮迭代，形成闭环。 |
| Q6 | 原理 | 「提示词要不要写进 PRD？为什么？」 | 对应板块 | 要——提示词是需求的一部分，改提示词和改 PRD 一样要评审；否则线上提示词会被随意改动且无据可查。 |
| M1 | 面试追问 | 「你说五处差异，能挑一处说说你项目里怎么写、怎么验收吗？」 | 对应板块 | 引导用「指标名 + 数字门槛 + 数据来源」落到一个具体指标，避免只报名称。 |
| M2 | 面试追问 | 「评测标准写 90% 正确率，这个数怎么来的？」 | 对应板块 | 两个来源：同行基准 + 自己评测集小样本试跑；「跳一跳够得着」，拍脑袋的数要么形同虚设要么压垮团队。 |
| M3 | 面试追问 | 「研发说相似度阈值做不到 0.6，你 PRD 怎么改？」 | 对应板块 | 不争辩；先拆可验收口径，问清做不到的是「算不出相似度」还是「达不到某数值」，给降级方案（改为规则拒答 / 转人工），并写进变更记录。 |
| M4 | 面试追问 | 「幻觉怎么约束？只写『引用来源』够不够？」 | 对应板块 | 不够；三道防线：事前引用约束、事中阈值拒答、事后幻觉率红线与回滚，且责任人都是产品经理。 |
| M5 | 面试追问 | 「如果上线三个月后评测集还准吗？」 | 对应板块 | 不准；靠数据回流把线上 badcase 每周筛进评测集，否则评测集停在上线那天、分数虚高。 |
| M6 | 面试追问 | 「你怎么证明这份 PRD 是可验收的，不是写给领导看的？」 | 对应板块 | 每章都能扛住一个问题：背景「数据哪来的」、目标「为什么这个数」、评测「怎么测的」、兜底「错了怎么办」。 |
| M7 | 面试追问 | 「提示词上线后被人改了效果变差，你怎么追责？」 | 对应板块 | 提示词是需求的一部分，改动必须走 PRD 变更流程、留变更记录、回归评测；没有版本管理就是定时炸弹。 |

## 十一、学员易错点预判与应对（12 条）

| 易错点 | 表现 | 应对 |
|---|---|---|
| PRD 写成功能清单 | 第 4 章一句「支持智能问答」完事 | 现场用差 vs 好 PRD 对比改写一次；巡场时要求每条 P0 功能补齐输入、处理、输出 |
| 评测标准写「效果要好」 | 第 6 章全是形容词 | 反复使用三要素模板；巡场发现即要求当场补数字与数据来源，宁可数字保守 |
| 目标堆砌 4 个以上指标 | 第 2 章罗列七八个指标 | 规则明确：1 个北极星 + 2 个护栏；多了说明没想清楚要什么 |
| 兜底设计只写「转人工」 | 第 7 章一行带过 | 发四级链路自检四连问（低置信 / 无结果 / 连续失败 / 不可用）；预告周三课深化 |
| 成本预算空白 | 第 8 章写「后续评估」 | 给单次成本公式现场演算一遍（输入 2000 token + 输出 500 token 例），要求至少给出估算值 |
| 前几章过度打磨挤占写作时间 | 30 分钟还在改背景 | 严格执行逐章计时；超时章节先按导学案引导句写满，课后润色 |
| 【术语混淆】验收标准与口径混用 | 把「按什么算」写成「达到多少算过」 | 对应板块用 T1 辨析；写作回查时要求先写一句口径、再写验收条款 |
| 【术语混淆】异常态与边界条件混用 | 把「输入超长」叫异常、把「模型超时」叫边界 | 用 T2 一对一句式：「运行时出错 = 异常态；输入到临界 = 边界条件」 |
| 【术语混淆】漏写模型能力假设 | 第 5 章只写「用大模型」，不写假设能做到 / 做不到什么 | 强制一句「本产品假设模型能____，不能____」；这是评测与兜底的前提 |
| 【面试失分】只背五处名称 | 答「差在哪」报五个词就被追问卡住 | 每处必须配 1 个「指标 + 数字 + 来源」示例；用 M1 追问链练到能落地 |
| 【面试失分】研发说做不到时空辩 / 甩锅 | 「这是研发的事」「应该能做到」 | 用四步应答：承认约束 → 拆可验收口径 → 给降级方案 → 写进变更记录（M3） |
| 【面试失分】幻觉只答「引用来源」 | 漏掉阈值拒答与幻觉率红线 | 用 M4 逼出三道防线，并点明责任人是产品经理 |
