## 二、教学目标（可测量）

1. 能用「解析 → 分块 → 检索 → 生成」四层漏斗对任意一条 badcase 完成归因，并写出对应的修复动作（对应课堂破案示范 + 测试报告 badcase 清单）。
2. 能独立用《AI 产品评估打分工具》导入评测集、逐条打分、导出 Markdown 测试报告，并读出通过率、badcase 率、维度短板三件事（对应本课实操 + 今晚提交的测试报告）。
3. 能发出 ≥10 人试用邀请，并按「用户画像 / 使用场景 / 原声引用 / 问题分级」四要素回收有效反馈，汇总出 ≥3 条有效改进（对应明天路演验收标准）。

## 三、教学重难点

- **重点**：badcase 四类归因法（解析 / 分块 / 检索 / 生成）——这是 AI 产品经理区别于传统 PM 的标志性硬功，也是明天路演答辩的高频提问区。
- **难点一**：归因顺序的决策。学员遇到 badcase 习惯「先怪模型」，本节课训练「先查数据、再查链路、最后才怪模型」的排查纪律。
- **难点二**：试用反馈的解读。10 个用户会给出互相矛盾的反馈，学员容易「照单全收」或「凭感觉筛选」，本节课给出「问题分级 P0/P1/P2」的判据。

## 六、badcase 四类归因表（本课核心表格）

排查纪律：**从便宜到贵、从数据到模型**。每一层都有明确的「看什么、怎么修、找谁修」。

| 归因类别 | 典型表现（教学化示例） | 快速定位方法 | 修复动作 | 主要责任方 |
|---|---|---|---|---|
| ① 解析问题 | 引用原文本身就是错的：扫描件 OCR 错字、表格错位成乱码、图文混排丢内容 | 点开 badcase 的引用来源，先读原文——原文错，就是解析问题 | 换解析器；扫描件先 OCR 预处理；表格单独结构化抽取 | 数据 / 工程 |
| ② 分块问题 | 「差一点」：答案被从两个块中间切断，或一个块塞了多个主题导致相似度稀释 | 看检索到的 chunk 是否包含完整答案；边界处被腰斩即分块问题 | 调块大小（300–500 字常见区间）、加 10%–20% 重叠、按标题层级切分 | 算法 / 工程 |
| ③ 检索问题 | 资料里明明有，却没捞到；或捞回来的全是无关内容（答非所问） | 拿 badcase 的标准答案在知识库里手工检索一次，看能否召回 | 调 Top-K、换 Embedding 模型、加相似度阈值、上混合检索（关键词 + 向量） | 算法 |
| ④ 生成问题 | 资料正确且已检索到，模型仍答错：编造政策、答非所问、格式错误 | 把「问题 + 正确检索结果」直接贴给裸模型，它仍错即生成问题 | 改提示词（引用约束、拒答指令）、加输出格式校验、升级或更换模型 | 算法 / 产品 |

**四层排查漏斗（板书必画）**：

```
一条 badcase
   │
   ├─ 第 1 层：引用原文对吗？   ── 错 → 解析问题（最便宜，先查）
   ├─ 第 2 层：chunk 完整吗？   ── 断 → 分块问题
   ├─ 第 3 层：正确资料召回了吗？ ── 没 → 检索问题
   └─ 第 4 层：裸模型拿着好资料还错？ ── 错 → 生成问题（最贵，最后认）
```

纪律：**无归因不派单**——没走完四层漏斗，不许把 badcase 甩给下一句「模型不行」。

## 七、课堂提问设计（8 问）

| # | 提问 | 提问时机 | 预设答案 / 引导方向 |
|---|---|---|---|
| 1 | 「评测集 50 条跑完，通过率 62%。你的第一个动作是什么？」 | 环节一导入 | 不是打开代码改模型，是先归因——把 badcase 按四类分好组，看哪类占比最高 |
| 2 | 「用户问退款政策，模型编造了『72 小时无条件退款』。你先查哪里？」 | 破案示范第一层 | 先看引用来源原文。原文是对的，才往下一层走——排除解析问题 |
| 3 | 「用户问『A 模块和 B 模块的区别』，模型只答了 A。可能是哪类问题？」 | 破案示范后 | 两种可能：分块把 B 的内容切碎了，或检索只召回了 A——先看 chunk 再看召回 |
| 4 | 「把正确资料直接贴给模型，它还是编。这说明什么？」 | 破案示范第四层 | 生成问题：模型有「脑补」倾向，缺拒答与引用约束——改提示词，先别换模型 |
| 5 | 「badcase 率 33.3%，工具弹了警戒线。这个数字你希不希望它出现？」 | 环节二演示 | 希望——今天暴露好过明天路演翻车。30% 是工具内置警戒线，超过就暂缓上线先修复 |
| 6 | 「雷达图五个角，三个角凹进去。你先补哪个？」 | 环节二雷达图 | 先补归因后数量占比最大的那类问题对应的维度——补凹点不是补最低分，是补根因 |
| 7 | 「10 个试用用户，9 个说挺好，1 个说找不到入口。听谁的？」 | 环节三示范 | 都听。9 个「挺好」是伪繁荣——试用任务设计得太简单；1 个找不到入口是真实信号，先复盘任务设计 |
| 8 | 「用户原声说『比我用 Excel 还慢』。这属于哪级问题？」 | 环节三示范 | P1 体验问题：记录、排期，不当 P0 修——除非它导致用户直接弃用 |

## 八、板书要点

```
测试验收 = 跑分（工具）+ 归因（脑子）+ 试用（真人）

四层排查漏斗：引用原文 → chunk 完整 → 召回正确 → 裸模型对照
纪律：无归因不派单；先数据后模型，先便宜后贵

三个数字：评测集 ≥50 条 ｜ 试用 ≥10 人 ｜ 上线线 = 通过率 ≥90% 且无 P0
警戒线：badcase 率 30%（工具内置，超线暂缓上线）

反馈分级：P0 当天修（编造/安全）｜ P1 排期修（体验/流程）｜ P2 记录不排（吐槽/美化）
金句：10 个真实用户胜过 100 条自嗨功能
```

## 九、课堂练习参考答案（badcase 归因破案）

破案案例（教学化示例，不指向任何真实产品）：智能客服知识库，用户问「你们支持无理由退款吗」，模型答「我们提供 72 小时无条件退款，2 小时内原路退回」。真实政策是「7 天无理由、激活后不支持」。

| 排查层 | 看到的证据 | 判断 |
|---|---|---|
| 第 1 层 解析 | 引用原文 = 售后政策第 3 条，文字完整无乱码，写的就是「7 天无理由」 | 排除解析问题 |
| 第 2 层 分块 | 检索命中的 chunk 完整包含政策全文，未被切断 | 排除分块问题 |
| 第 3 层 检索 | 正确政策 chunk 相似度 0.91，排在第 1 位，已进提示词 | 排除检索问题 |
| 第 4 层 生成 | 把「问题 + 正确政策」直接贴给裸模型，它仍答「72 小时」 | **定位：生成问题**——模型脑补倾向，缺拒答与引用约束 |
| 修复动作 | 提示词加两条硬约束：「仅依据所给资料回答，资料没有的不许推断」「涉及政策数字必须引用条款」；输出层加数字校验；回归测试该用例 | — |

## 十、学员易错点预判与应对

| 易错点 | 表现 | 应对 |
|---|---|---|
| 跳过归因直接改模型 | badcase 一出现就喊「换更强的模型」 | 用破案示范现场打脸：四层走完，三层排除，最后才是模型——多数 badcase 死在前三层 |
| 只看通过率，不看 badcase 构成 | 「通过率 92%，上线！」——但 1 条编造政策的 P0 藏在里面 | 强调上线双条件：通过率 ≥90% **且** 无 P0 级 badcase；通过率会掩盖 P0 |
| 小样本跑分当结论 | 拿 3 条用例的 33.3% 通过率恐慌，或反过来拿 5 条用例的 100% 开香槟 | 讲清示例数据只是流程演示，真实标准是评测集 ≥50 条；样本量不够，数字只是噪音 |
| 试用反馈照单全收 | 用户说啥改啥，一晚上改了 17 处，第二天全回归挂了 | 强制走「问题分级」：P0 当天修、P1 排期、P2 记录；改完必须回归，不许带伤上路演 |
| 只收「好评式」反馈 | 邀请语写「帮我看看有啥问题」，收回一片「挺好的」 | 环节三纠正：给用户 3 个具体任务 + 1 个必填问题「哪个环节你想放弃？」——原声比好评值钱 |
