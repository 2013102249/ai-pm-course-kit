教案 · W6 周一《Vibe Coding 与 AI 工程提效》

AI 产品经理就业训练营 · 第六周第一天 · 90 分钟（2 课时，中间休息 5 分钟）· 讲师版

一、基本信息

项目 内容
所属阶段 阶段四 · 实战与就业（Week 6）

课时 90 分钟（2 课时，中间休息 5 分钟）

二、教学目标（可测量）

  1. 能独立写出符合「五段式」结构（是什么 / 给谁用 / 包含什么 / 长什么样 / 不能怎样）的 AI 工具开工指令，并在提示词调试台中使五要素评分达到 5 分（对应作业：开工指令评分 ≥5 分）。
  2. 能针对给定的 MVP 任务场景，按「一主两辅」原则选出工具组合，并给出两条以上理由（对应课堂实操第一题 + 习题第二层）。
  3. 能写出主项目规则文件的前三条（项目背景 / 技术约定 / 红线各一条），并说出 AGENTS.md 的四块内容与作用（对应课堂实操第二题 + 习题第二层）。

三、教学重难点

  • 重点：Vibe Coding 方法论的五步循环与能力边界；国产工具选型的「一主两辅」原则与选型四问；规则文件的四块结构。
  • 难点一：能力边界的判断——学员容易把「能跑起来」等同于「能交付」，需用「演示层快跑，核心层慢验」建立分层意识。
  • 难点二：工具选型的论证——五款工具只做客观定位描述，学员易凭印象选工具，需用「四问决策」把选择变成可复用的判断框架。

四、Vibe Coding 能力边界（本课核心表格）

维度 适合做什么 不适合做什么
交付物性质 原型与 Demo：把想法变成可点击、可演示的页面，用于验证与路演 生产级系统：要扛真实流量、有 SLA 要求、要抗攻击的线上服务
使用范围 内部小工具：团队自用的数据整理、报表、自动化脚本，用户量小、容错高 核心链路：支付、登录、权限判断等错一次就是事故的模块
生命周期 一次性交付：路演页、活动页、数据可视化页，用完即弃、不长期维护 长期维护的大型工程：半年后无人说得清每行代码的意图，包括 AI
实验目的 学习与验证：两小时内验证一个技术想法的可行性 强合规场景：需过等保、算法备案评估的正式系统，代码可审计性是硬要求
质量保障 有人工验收关：每次生成后有人逐项对照需求检查 无人验收的全自动流水线：生成即上线、无人 review 的「甩手」模式

边界口诀：演示层快跑，核心层慢验。 主项目 MVP 采用「两层分离」策略——演示层用 Vibe Coding 快速搭建，真实用户试用涉及的核心数据流转必须设置人工验收关（周四测试验收课细讲）。

六、教学步骤与时间拆分

时间 环节 教学内容 教学方法 对应产出
0–5 min 开场：本周任务与今日终点 公布本周五天冲刺日历（每天一个验收点）；明确今日终点 = MVP 技术方案三件套 讲授 —
5–15 min 导入：不会写代码，怎么做 Demo 调查「写过生产代码的人数」；讲往期运营转岗学员用国产工具做 Demo 拿到 offer 的故事；引出 Vibe Coding 故事 + 提问 —
15–28 min 环节一：Vibe Coding 方法论与边界 用流程图讲五步循环（说清楚→生成→跑起来→挑毛病→再说清楚）；用能力边界表划边界；宣布「演示层快跑，核心层慢验」 讲授 + 图示 + 提问 导学案能力边界表填写
28–40 min 环节二：国产工具实战地图 用对比表讲五款工具（WorkBuddy / 豆包 / Trae / 通义灵码 / CodeBuddy）的客观定位；归纳「对话派 vs 工程派」；给选型四问 讲授 + 图示 + 提问 导学案五工具对比记录表
40–55 min 环节三：现场演示——10 分钟搭一个页面 现场用一款国产 AI 工具，按五段式指令生成「本周 MVP 冲刺看板」页面；演示运行、挑毛病、一句话反馈让 AI 改；埋金句「AI PM 的代码是提示词和工作流」 现场演示 + 提问 导学案演示记录
55–62 min 环节四：规则文件编写 讲 AGENTS.md 为什么需要、四块内容（项目背景 / 技术约定 / 输出规范 / 红线）；现场展示真实规则文件并改一条 讲授 + 演示 导学案规则文件笔记
62–70 min 环节五：提示词即代码 打开提示词调试台，五步演示：五要素评分 = 提示词的「编译检查器」；删角色、精简指令看掉分；A/B 对比温度与提示词质量 交互演示 + 提问 导学案评分记录
70–82 min 环节六：课堂实操 学员完成三件事：定「一主两辅」组合、写规则文件前三条、给开工指令评到 5 分；讲师巡视并点 2–3 人汇报 学员实操 + 汇报点评 MVP 技术方案三件套
82–90 min 总结与作业 三句话收束；布置三项作业；预告周二开发冲刺 I 讲授 —

七、课堂提问设计（7 问）

# 提问 提问时机 预设答案 / 引导方向
1 「不会写代码，怎么做 Demo？传统办法有哪几条，各差在哪？」 导入 找程序员合伙（不可控）、外包（沟通成本高）、自学三个月（来不及）；引出第四条路：Vibe Coding
2 「我们的 MVP 属于能力边界表的哪一边——适合还是不适合？」 环节一 MVP 是「原型与 Demo」的加强版（要多接 ≥10 名真实用户）；结论：演示层快跑，核心层慢验
3 「五款工具能分成几派？规律是什么？」 环节二 两派：对话派（WorkBuddy、豆包，零门槛做演示）与工程派（Trae、通义灵码、CodeBuddy，项目级迭代）
4 「AI 生成的页面哪里不合预期？用一句话怎么让它改？」 环节三 合格反馈 = 指出现象 + 给出方向，如「倒计时请改为实时计算，不要写死日期」；不合格反馈 =「不对，重做」
5 「没有规则文件，连续迭代三天会发生什么？」 环节四 每次生成的风格与结构不一致、AI 自行「优化」掉依赖功能、周三周四大规模返工
6 「删掉角色描述，评分卡哪一项变了？这说明什么？」 环节五 角色设定从已覆盖变缺失；提示词「缺一行」就像代码「缺一个 import」——能跑但边界条件下崩
7 「你的主力工具是哪款？一句话理由。」 环节六汇报 用选型四问之一论证即可，如「演示一次选对话派，迭代一周选工程派」

八、板书要点

Vibe Coding = 用自然语言「说清楚」，AI 生成代码，人负责验收
五步循环：说清楚 → 生成 → 跑起来 → 挑毛病 → 再说清楚（循环，通常 3–10 轮）
五段式指令：是什么 / 给谁用 / 包含什么 / 长什么样 / 不能怎样
边界口诀：演示层快跑，核心层慢验
工具：一主两辅；对话派（WorkBuddy / 豆包） vs 工程派（Trae / 通义灵码 / CodeBuddy）
选型四问：演示一次还是迭代一周 / 愿不愿意装环境 / 页面展示还是数据流转 / 出问题谁来救
规则文件（AGENTS.md）四块：项目背景 / 技术约定 / 输出规范 / 红线
金句：AI PM 的代码是提示词和工作流

九、课堂练习参考答案（工具选型 + 规则文件）

9.1 工具选型参考

任务场景 推荐选择 关键理由
周五路演前夜，5 分钟内要看到演示页 WorkBuddy 或豆包 对话派零门槛，一句话到页面，不装环境
周二到周四持续迭代 MVP 页面 Trae AI 原生 IDE，项目级工程可持续迭代
已有编辑器使用习惯、给存量代码提速 通义灵码或 CodeBuddy 插件形态，在熟悉环境里工作
演示层与数据层都要覆盖 一主两辅组合 演示层用对话派，工程层用工程派，忌单打独斗

9.2 规则文件前三条参考（以「社区团购选品助手」为例）

条目 示例 说明
项目背景 「本项目为社区团购选品助手 MVP，服务对象为团长，目标是输入食材清单输出选品建议与成本测算」 一两句话说清是什么、给谁用、做到什么程度
技术约定 「单文件 HTML，不引入外部依赖，配色统一用 #7C3AED」 定框架、定风格、定位置
红线 「不许调用未经验证的第三方接口；不许改动已验收的核心计算逻辑」 用「不许」开头，一条条列

十、学员易错点预判与应对

易错点 表现 应对
把 Vibe Coding 当「许愿机」 说一句话就想直接上线，生成失败就抱怨工具不行 用流程图强调五步是循环不是直线；现场演示「挑毛病—再说清楚」至少两轮
工具集邮 五款全部注册、每个都浅尝，最后一款用不深 讲「一主两辅」原则；实操第一题强制只选一款主力
生成失败就放弃或手工改代码 不会用自然语言描述差距，转而自己 debug 演示合格反馈的公式：指出现象 + 给出方向；让学员现场练一句话反馈
跳过规则文件 直接开工，第二天发现输出风格全变、返工 现场展示「同一项目有无规则文件」两轮生成差异；实操第二题强制写三条
把「能跑」当「能交付」 Demo 能演示就认为完工，不做验收 回扣 W2 评测集与 W6D4 测试验收安排；强调「演示层快跑，核心层慢验」
