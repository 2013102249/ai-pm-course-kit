## 第 0 层 · 术语辨析题（新增层 · 共 14 题）

### 一、选择题（题 0-1 ~ 0-5，每题 8 分，共 40 分）

**0-1. 关于「降级」，理解正确的是：**
A. 降级就是把功能关掉、给用户弹个错
B. 降级是主路走不通时换个方式把事办成，一定有兜底产出
C. 降级就是拿 Mock 假数据顶上，用户看不出来就行
D. 降级只在模型产品里才需要，别的产品不用考虑

**0-2. 关于「超时」，理解正确的是：**
A. 超时是「调用失败」的结果判定
B. 超时是主动设定的等待上限，到点就不再等，是时间边界
C. 超时和重试是同一件事的两种说法
D. 不设超时也没关系，让用户多等一会儿就好

**0-3. 关于「重试」，理解正确的是：**
A. 重试就是多试几次，试到成功为止
B. 401 / 403 最应该多试几次，试到凭证生效
C. 重试应有次数上限（1 次）、带间隔，且只对超时 / 429 / 5xx 等可重试状态码
D. 重试和让用户刷新页面是一回事

**0-4. 关于「状态码」与「日志」，理解正确的是：**
A. 状态码是逐笔流水账，日志是三位数字结论
B. 两者是一回事，都是记请求结果
C. 状态码给简短结论（200 / 401 / 404 / 429 / 5xx），日志给逐笔过程（时间 / token / 耗时）
D. 日志就是给用户看的「服务繁忙」提示

**0-5. 关于「MVP（最小可行产品）」，理解正确的是：**
A. MVP 就是做了一半的半成品
B. MVP 功能最少但完整可跑通，砍的是功能数量不是质量
C. MVP 允许质量差一点，先上线再说
D. MVP 阶段不需要验收标准，看着差不多就行

## 第 1 层 · 基础巩固题（概念层 · 共 10 题，其中新增 ≥2 题）

### 一、选择题（题 1-1 ~ 1-6，每题 10 分，共 60 分）

**1-1. 关于「核心链路」，正确的是：**
A. 核心链路 = 产品的全部功能 + 页面样式
B. 核心链路 = 输入 → 处理 → 输出，一次完整走通、中间不手动搬数据
C. 核心链路只要前端页面能打开就算通
D. 核心链路允许用写死的假数据撑到路演

**1-2. 关于「真」的硬要求，错误的是：**
A. 输入要是真实场景里用户真会输入的东西
B. 输出要是模型真实返回的结果
C. 为了演示稳定，验收时保留 Mock 假数据更保险
D. 中间不能靠截图假装、不能手动搬数据

**1-3. 对应板块三个检查点的正确顺序是：**
A. 模型调用通 → 输入可提交 → 全链路串联
B. 输入可提交 → 模型调用通 → 全链路串联 + 日志可见
C. 全链路串联 → 输入可提交 → 模型调用通
D. 三个检查点同时打卡，不分先后

**1-4. 关于 5 条硬标准与 2 条软标准，正确的是：**
A. 软标准卡通过，硬标准只决定评级
B. 5 条硬标准全过才算跑通；软标准（降级策略 / 日志规范）决定「合格 vs 良好」，不卡通过
C. 只要页面好看，硬标准可以打折
D. 软标准是给进度快的学员的可选项，不写也没关系

**1-5. API 接入三步的正确顺序是：**
A. 写业务代码 → 配 Key → 直连验证
B. 配 Key 到 `.env` → 最小请求直连验证 → 再写业务代码
C. 直连验证 → 写业务代码 → 配 Key
D. 配 Key → 写业务代码 → 看报错再验证

**1-6. 联调报 404 与报 401，处理上正确的是：**
A. 两者都重试几次就好
B. 404 对齐路由表 / 检查路径；401 / 403 查请求头有没有带 Key、Bearer 前缀是否漏了
C. 404 查 Key，401 查路由
D. 两者都先分后合，但都不用看状态码

### 二、简答题（题 1-7 ~ 1-10；1-7、1-8 各 20 分，新增 1-9、1-10 各 15 分，共 70 分）

**1-7.** 用**非技术生活类比**讲清「核心链路」和「MVP」各是什么，并说明 MVP 为什么不是半成品。

**1-8.** 默出「降级四层」，每层写一句「触发条件 + 给用户什么」，并说明兜底文案为什么必须明示。

**1-9.（新增）** 用三个**非技术**生活类比，分别说清「超时」「重试」「状态码」各是什么；要求不出现「接口、请求、参数」这类技术词，纯用生活场面。

**1-10.（新增）** 写出本课七个「≠」，并各配一句大白话辨析：降级≠报错、超时≠失败、重试≠无限重试、状态码≠日志、Mock≠真调用、MVP≠半成品、阻塞点≠普通 Bug。

## 第 3 层 · 求职挑战题（面试层 · 共 4 题，其中新增 ≥2 题）

**3-1.（30 分）面试真题：你怎么跟进开发**
面试官：「你负责一个 AI 产品的开发冲刺，说说你怎么跟进，别只说开会。」
要求：先否定「跟进 = 催进度」，再给检查点、验收标准、blockers 清单三段，最后补一条「显专业」的补充观点。

**3-2.（30 分）面试真题：接口挂了产品怎么办**
面试官：「模型接口今天一直挂，研发在修。作为产品，你这一侧做什么？」
要求：先分「研发修根因 / 产品兜当下」两条线，给 ≥3 条降级层次，补状态码与日志，收一句金句。

**3-3.（新增 · 30 分）面试真题：怎么定义 MVP 验收**
面试官：「你说这个版本是 MVP，怎么证明它能验收？官方演示能算数吗？」
要求：给 MVP 的正确定义、可打勾的硬标准、软标准的作用、Mock 的边界，以及一条收尾。

**3-4.（新增 · 30 分）面试真题：冲刺日怎么排优先级**
面试官：「冲刺日一堆事堆在一起，样式、登录、链路、降级，你先做哪个？老板临时又插一个小需求呢？」
要求：给排序判据、明确不做的边界、进度快者的加时任务，并回答「完美什么时候做」。

## 第 4 层 · 面试实战题（新增层 · 共 7 题）

> 每题自带「踩分点 / 追问链 / 典型失败答法 + 失分原因 / 评分表」四件；**60 秒标准答法（参考答案）**统一放在文末答案区第 4 层，供对完再念。
> 用法：对应板块两两模拟照「追问链」连追 2–3 层；对应板块验收二抽 1 题，按评分表判「优秀 / 良好 / 合格 / 失分」。

**题 4-1｜你怎么跟进开发（题型：项目深挖 / 行为题）**

| 项目 | 内容 |
|---|---|
| 踩分点（20 分） | ① 用 CP1 输入 / CP2 调用 / CP3 串联把大工程拆成可打勾三段，明确否定「跟进 = 催进度」（6 分）；② 验收标准提前公布、可判过不过（5 硬 2 软）（5 分）；③ blockers 每条有责任人 + 状态 + 时限，当天清（5 分）；④ 求助三级制 + 带排查记录提问（4 分） |
| 追问链 | 第 1 层「不问『做到哪了』，你具体看什么？」→ 看检查点打勾、看日志、看 blockers 状态；第 2 层「有人卡 20 分钟不吭声怎么发现？」→ 助教每 15 分钟主动扫场、卡超 5 分钟按预判表代查；第 3 层「快慢差 3 倍怎么管？」→ 快的加做降级与日志，慢的优先保核心链路三步，不统一讲解 |
| 典型失败答法 + 失分原因 | 「我每天开个站会，让大家报进度，卡住了协调资源。」——只有会议、没有可打勾的验收标准与 blockers 责任时限，暴露「跟进 = 催进度」的产品盲区，三层追问一层都接不住 |
| 评分表 | 优秀 17–20：四段齐全 + 被追 3 层不改口；良好 13–16：检查点与验收线清楚、能接 1–2 层；合格 9–12：只说「拆阶段跟进」，无标准无清单；失分 0–8：答「开会催进度」「等研发报」，被追即改口 |

**题 4-2｜接口挂了产品怎么办（题型：场景设计）**

| 项目 | 内容 |
|---|---|
| 踩分点（20 分） | ① 先分「研发修根因 / 产品兜当下」两条线，明确不等研发（5 分）；② 给 ≥3 条降级层次（超时 / 重试 1 次 / 缓存复用 / 静态兜底文案）（6 分）；③ 用状态码定位「没发出 / 被拦 / 报错」，日志留痕（5 分）；④ 加载态、错误提示、兜底结果明示不伪装（4 分） |
| 追问链 | 第 1 层「兜底文案算不算欺骗用户？」→ 不算但要明示「当前为降级结果」，不伪装、不拿 Mock 冒充；第 2 层「重试会不会把接口打得更挂？」→ 会，故限 1 次 + 间隔 + 只对超时 / 429 / 5xx，401 / 403 不重试；第 3 层「怎么验收改好了？」→ 造「接口故障 + 已知兜底」演练记录，看兜底是否触发、日志是否记状态码、用户是否看到提示 |
| 典型失败答法 + 失分原因 | 「找研发修，产品等他修好再测，先弹个『服务异常』。」——产品侧零动作、无降级层次、无状态码与日志意识，把责任全推给研发；一追「用户这半小时怎么办」即卡住 |
| 评分表 | 优秀 17–20：两条线 + ≥3 层降级 + 状态码日志 + 明示边界 + 接住 3 层；良好 13–16：两条线清楚、降级 2–3 层；合格 9–12：只答「加错误提示」，无超时重试层次；失分 0–8：答「等研发修」「接口挂了产品没办法」 |

**题 4-3｜怎么定义 MVP 验收（题型：场景设计 / 技术理解）**

| 项目 | 内容 |
|---|---|
| 踩分点（20 分） | ① 明确 MVP 是「最小但完整可跑通」，否定半成品 / 劣质品（5 分）；② 验收标准是可打勾硬条件（输入真实 / 调用真实 / 输出可见 / 日志可见 / 连续稳定）（6 分）；③ 软标准决定「合格 vs 良好」、不卡通过（5 分）；④ 标准由产品写、研发与讲师双确认，不靠「看着差不多」（4 分） |
| 追问链 | 第 1 层「写死假数据算通过吗？」→ 不算，Mock 是开发期替身，验收换回真实调用；第 2 层「为什么连续提交 3 次也写进标准？」→ 只成功一次可能是偶发，路演经不起第二次点；第 3 层「标准太高慢的学员都过不了怎么办？」→ 硬标准不打折，未过进补救路径，不降标准也不判失败 |
| 典型失败答法 + 失分原因 | 「MVP 验收就是大家看一遍觉得能用就行，功能先做一半。」——把 MVP 当半成品、验收靠主观感觉、无硬标准；一追「谁说了算」即答不上来 |
| 评分表 | 优秀 17–20：定义 + 五硬二软 + Mock 边界 + 补救路径 + 接住 3 层；良好 13–16：定义与硬标准清楚，能答 2 层；合格 9–12：只说「能用就行」，标准模糊；失分 0–8：答「做一半」「看着差不多」 |

**题 4-4｜冲刺日怎么排优先级（题型：行为题 / 场景设计）**

### 第 2 层 · 进阶实操（三档 Rubric · 4 题）

**题 2-1 参考答案**：三步清单示例——输入：① 能提交一条真实场景输入（非「测试测试测试」）② 后端日志能看到收到原话 ③ 用户操作 ≤3 步或有「一键示例」；处理：① Key 在 `.env`、代码读环境变量 ② 最小请求直连验证通过 ③ 拿到一次真实模型响应、调用记录可见；输出：① 结果展示回前端 ② 一次输入到输出全程不断、无手动搬数据 ③ 能当场指出日志位置并说出时间 / token / 耗时中至少两项。① 手动搬数据 = 链路不是「一次完整走通」，路演真人一点就穿；② 日志可见是硬标准，因为「说不清刚才那次请求发生了什么」就无法排查、也无法证明调用真实；③ CP1 165 / CP2 180 / CP3 195 min，均在对应板块（）实操时段，终验在对应板块。

**题 2-2 参考答案**：状态码分流表——CORS：Console 跨域报错 → 后端加跨域响应头、前端对地址端口 → 不涉及重试；404：路径拼错 → 前后端对齐路由表（检查 `/api` 前缀）→ 不重试；401 / 403：请求头没带 Key 或 Bearer 前缀漏了 → 查凭证与请求头 → 不重试；429：触发限流 → 降频或等 1 分钟 → 可重试；5xx：服务端出错 → 记为可重试、走降级 → 可重试。先分后合三步：① 后端用接口调试工具单独验证一次；② 前端确认请求地址、路由、请求头；③ 两边各自通过后合并联调。不能对着黑盒互相怀疑，因为双方各说各话时无法定位「没发出 / 被拦 / 报错」，责任也分不清。

| 良好（30–35 分） | 两档替代动作齐全，覆盖步骤 A / B / C 与长表格 |
| 优秀（36–40 分） | 额外说清结对角色分工与「验收官产出如何计入作品集」，体现「不让设备变成门槛」 |

### 第 3 层 · 求职挑战（三档 Rubric · 4 题）

**题 3-1 参考答案**：否定「跟进 = 催进度」；三段 = ① 检查点（CP1 输入 / CP2 调用 / CP3 串联）把大工程拆成可打勾三段，到点打卡；② 验收标准提前公布、可判过不过（5 硬 2 软）；③ blockers 清单每条写责任人 + 状态 + 时限，当天问题当天清。专业补充 = 「我不问『做到哪了』，我按可打勾的标准逐段验收；还立了求助三级制，升级的问题必须带排查记录。」

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 否定催进度，给出检查点或验收标准之一 |
| 良好（24–27 分） | 三段齐全，含 blockers 责任人与时限 |
| 优秀（28–30 分） | 补「求助三级制 / 带排查记录提问」或「快慢差 3 倍怎么管」 |

**题 3-2 参考答案**：两条线 = 研发修根因、产品兜当下，不等研发。降级层次 ≥3 条：设超时、重试 1 次仅对可重试状态码、缓存复用并明示、静态兜底文案加稍后重试入口。补状态码定位「没发出 / 被拦 / 报错」与日志留痕（时间 / 耗时 / token / 状态码）。收尾金句 = 「研发修的是根因，产品兜的是当下——先让用户有得用，再让日志说得清。」

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 分两条线，给出 2 条降级动作 |
| 良好（24–27 分） | 降级 ≥3 层、区分可重试状态码，有日志意识 |
| 优秀（28–30 分） | 补兜底结果「明示不伪装」、Mock 边界，或以金句收尾 |

**题 3-3 参考答案**（新增，30 分）：MVP 定义 = 最小但完整可跑通，砍功能数量不砍质量，不是半成品；官方演示 / 写死假数据都不算数，Mock 只是开发期替身，验收换回真实调用。硬标准 = 输入真实 / 调用真实 / 输出可见 / 日志可见 / 连续提交 3 次稳定，五条全过才算跑通；软标准 = 降级策略 / 日志规范，决定合格还是良好、不卡通过。收尾 = 「验证是放学之前按同一张清单做完的，不是靠『看着差不多』，更不是留到路演靠嘉宾点一下。」

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 定义正确，列出 ≥3 条硬标准 |
| 良好（24–27 分） | 五硬二软齐全，说清 Mock 边界与软标准作用 |
| 优秀（28–30 分） | 补「标准由产品写、研发与讲师双确认」或收尾金句 |

**题 3-4 参考答案**（新增，30 分）：判据 = 「不做会不会让后面全停、会不会卡住今天的验收线」。第一优先阻塞点（旧沙发卡楼道，后面全停，当天认领责任人与时限），第二优先核心链路三步（输入 / 处理 / 输出逐段打勾）；样式、注册登录、支付、历史记录明确不做，排 W6D3 之后。进度快者不改样式，加做降级策略与日志规范。老板插「容易做」的小需求：先判是否在链路与验收线上，不在就排期到 W6D3 并给一个可看的最小演示替代，不硬顶也不改口。完美不是取消、是排期：W6D3 功能与体验、三态设计，产品定标准、研发实现、讲师终验。

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 给出判据，明确先链路后样式 |
| 良好（24–27 分） | 阻塞点概念 + 边界清单 + 快者加时任务齐全 |
| 优秀（28–30 分） | 回答「老板插需求」与「完美谁负责、何时做」两处追问，体现不改口 |

### 第 4 层 · 面试实战（7 题 · 60 秒标准答法 = 参考答案；评分表见题目区）

> 每题评分表已随题给出（优秀 17–20 / 良好 13–16 / 合格 9–12 / 失分 0–8）；此处补齐每题 60 秒标准答法，供对完踩分点后跟读。**判分通用规则**：被追问时「接住 → 认下 → 补一层」且不改口，可在原档基础上加 1 分；出现「自我推翻 / 啊那我刚才说错了」直接降一档。

**题 4-1 参考答案（60 秒）**：「我跟进开发不靠催，靠一套提前公布、可打勾的验收标准。第一，把核心链路拆成输入、处理、输出三段，每段设一个到点打卡的检查点——提交一条真输入后端能不能收到、能不能拿到真实模型响应、全链路串起来日志能不能指出位置，做完一段勾一段。第二，验收线提前讲清楚：五条硬标准全过才算跑通，降级策略和日志规范两条软标准决定合格还是良好，不靠『看着差不多』。第三，卡点全部进 blockers 清单，每条写责任人、状态、明日动作，当天问题当天清，不允许无人认领。我还立了求助三级制，升级的问题必须带着排查记录来，这既是效率也是职业习惯。所以我的跟进不是问『做到哪了』，是逐段按标准验收、按清单清阻塞。」

**题 4-2 参考答案（60 秒）**：「我先把两件事分开：研发修的是根因什么时候好，产品管的是根因没好之前用户有没有得用，这两条线不能并成一条。产品侧我给四层降级：第一层设超时，主动划一条等待上限，不让页面转圈到死；第二层重试，只试 1 次、带间隔、只对超时、429、5xx 这类可重试的状态码，401 和 403 不重试，那是凭证问题该查请求头；第三层重试仍失败，有上一次真实结果就缓存复用，并明示『当前为缓存结果』；第四层连缓存也没有，就展示静态兜底文案加稍后重试入口，绝不伪装成模型刚算出来的结果。同时用状态码定位是没发出、被拦还是报错，日志把时间、耗时、token、状态码逐笔记下来。一句收口：研发修根因，产品兜当下——先让用户有得用，再让日志说得清。」

**题 4-3 参考答案（60 秒）**：「先纠一个说法：MVP 不是做一半，是最小但完整可跑通——砍的是功能数量，不砍质量和验收标准。验收我提前写成一张可打勾的清单，五条硬标准：输入真实、调用真实、输出可见、日志可见、连续提交 3 次稳定，全过才算『核心链路跑通』；另外两条软标准，降级策略和日志规范，决定评级是合格还是良好，但不卡通过。写死假数据不算数，Mock 只是开发期替身，验收必须换回真实调用，因为路演嘉宾真会点。标准由产品写、研发和讲师双确认，不靠『看着差不多』。没过的也不判失败，进补救路径，指定责任人、当晚复查、明天按同一张清单再验，绝不另起标准也绝不降标准。」

**题 4-4 参考答案（60 秒）**：「我排优先级只有一个判据：不做这件事，会不会让后面全停、会不会卡住今天的验收线。所以第一优先永远是阻塞点——像楼道口卡住的那张旧沙发，不挪开后面箱子全过不去，这类当天必须指定责任人和时限清掉。第二优先是核心链路三步：输入、处理、输出，一段一段打勾。样式美化、注册登录、支付、历史记录，今天明确不做，排到 W6D3 之后，先把边界画死才不会失控。进度快的同学我不让他改样式，让他加做降级策略和日志规范，把 60 分的跑通做到 80 分。纪律就一句：先跑通，再完美。最后补一句防追问：完美不是取消，是排期——W6D3 做功能与体验、三态设计，产品定标准、研发实现、讲师终验。」

**题 4-5 参考答案（60 秒）**：「我不听两边互相描述，先看证据。第一眼开 F12 Network，确认请求到底发出去没有、状态码是多少，先归到『没发出 / 被拦 / 报错』哪一类。然后按状态码分流：CORS 让后端加跨域响应头、前端对地址和端口；404 是路径拼错，前后端对齐路由表；401 / 403 是请求头没带 Key 或 Bearer 前缀漏了，查凭证而不是重试；429 降频或等一分钟；5xx 记为可重试。核心纪律是四个字——先分后合：后端先用调试工具单独验证一遍，前端再接，两边各自通过才合并，不对着黑盒互相猜。全过程记进卡点记录表，按环境、Key、联调三类归档，一类卡点出现第 3 例我全场广播一次解法。这样这次能定位，下次不用再吵。」

**题 4-6 参考答案（60 秒）**：「向不懂技术的老板汇报，我不用术语，用那条核心链路：输入、处理、输出三段，今天走到哪一段、哪一段打了勾。不说写了多少代码，说验收标准过了几条——五条硬标准里已经过了四条，差的是日志可见。进度用检查点说，到点打卡、到点接龙，老板一听就知道在哪儿。最要紧的是主动亮阻塞点：现在卡在模型调用这一环，责任人是谁、今晚 21 点前复查、明天按同一张清单再验，不藏问题，因为当天问题当天清，藏到路演才爆代价更大。证据我用两样：当场演示一条真输入到真输出，加一张日志截图。术语要翻译，比如状态码 429 我说成『模型今天太忙被限流了，我们降频并加了兜底，用户不会白等』——把状态说成对用户的影响，老板才拍得了板。」

**题 4-7 参考答案（60 秒）**：「响应慢我先划一条超时线，主动不等，绝不让页面转圈到死；具体设多少按业务能接受的等待来定，数值我不拍脑袋，由教务补充，但今天必须设。到点之后重试 1 次，带间隔，只对超时、429、5xx 这类可重试的状态码，401 / 403 不重试。再不行往下走降级：有上一次真实结果就缓存复用并明示『当前为缓存结果』；没有就给静态兜底文案加稍后重试入口，绝不伪装成模型刚算出来的结果。全程要有加载态和错误提示，让用户看得到状态、等得到结果或至少等得到说明。最后日志把耗时、token、状态码逐笔记下来，事后才复盘得出是限流还是超时。一句收口：不等、不骗、不干等，留痕可查。」
