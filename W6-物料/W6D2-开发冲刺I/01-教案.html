教案 · W6 周二《开发冲刺 I：核心链路》

AI 产品经理就业训练营 · 第六周第二天 · 90 分钟 · 讲师 + 助教协作版
课型定位：开发冲刺日。本课不讲新知识，讲授让位于实操；讲师与助教的全部动作围绕一件事——让每位学员的核心链路在当天跑通。

一、基本信息

项目 内容
所属阶段 阶段四 · 实战与就业（Week 6 · 主项目实战）
本课主题 开发冲刺 I：核心链路（输入 → 处理 → 输出）
课时 90 分钟（不设课间休息，冲刺日一气呵成）
授课对象 已完成 W6D1 工具选型与环境就绪的学员
前置条件 主项目 MVP 技术方案已定；开发环境就绪；至少 1 个模型 API Key 可用
本课产出 核心链路可运行（一次完整输入 → 输出，日志可见）， checkpoint 打卡表全勾
教学场地 机房 / 直播 + 学员本地开发环境；讲师投屏 + 巡场
人员配置 讲师 1 名（主讲 + 终验）+ 助教 1–2 名（巡场 + 记录），详见 07-助教协作手册

二、教学目标（可测量，对应产出验收清单）

  1. 每位学员在 80 分钟时点前，完成核心链路一次完整跑通：前端提交一条真实输入 → 后端收到并调用模型 → 前端展示输出。验收口径见 06-产出验收清单 5 条硬标准。
  2. 学员能说出自己项目里「哪个环节最容易挂、挂了怎么降级」，至少写出 1 条降级策略（超时重试 / 缓存复用 / 静态兜底文案）。
  3. 当天卡点当天清：下课时 blockers 清单上，每条都有「责任人 + 状态 + 明日动作」，不允许出现无人认领的问题。

三、教学重难点

类型 内容 说明
重点 核心链路的拆解顺序与联调顺序 先通输入、再通调用、最后串输出；每步都有可打勾的验收动作，防止学员「一口吃成胖子」
难点一 模型 API 接入与降级 Key 配置、超时、限流、失败兜底——冲刺日最高频的挂点，预判表见第六节
难点二 进度差异管理 同班学员速度差可达 3 倍；讲师要用 checkpoint 制度让快的往体验走、慢的不掉队，而非统一讲解
纪律要求 「先跑通再完美」 反复强调：今天允许丑、允许慢、不允许没跑通；样式和异常处理留给 W6D3

五、教学步骤与时间拆分（合计 90 分钟）

时间 环节 教学内容与动作 教学方法 对应产出

六、三个最常卡住的点 · 预判表（巡场排查用）

按往年数据，冲刺日约 80% 的卡点集中在这三类。助教巡场发现学员卡住超过 5 分钟，直接按本表步骤代查，不要等学员自己悟。

卡点 1 · 环境配置（依赖装不上 / 起不来 / 端口占用）

排查步骤 操作 通过标准
步骤 1 确认运行环境版本：Node ≥18 或 Python ≥3.10（按 W6D1 定的技术栈） node -v / python -v 输出达标
步骤 2 看报错首行：是「command not found」还是「module not found」 前者重装环境，后者重装依赖
步骤 3 重装依赖：删 node_modules 或 venv 后重跑安装命令，国内网络加镜像源 安装无 error 结尾
步骤 4 端口占用（报 EADDRINUSE）：换端口或杀掉占用进程 服务成功启动，本地地址能打开
步骤 5 仍不行：直接用讲师参考工程目录替换重来，不要恋战 15 分钟内必须恢复可运行状态

卡点 2 · API 密钥（调不通 / 401 / 余额不足）

排查步骤 操作 通过标准
步骤 1 确认 Key 放在环境变量里，代码读的是环境变量不是明文 .env 有值且代码引用正确
步骤 2 用最小请求验证 Key：绕过业务代码，curl 或调试台直连一次 API 返回 200 且有内容
步骤 3 返回 401/403：Key 复制错误（首位末位空格）、未开通该模型、未实名或未充值 控制台看到调用成功记录
步骤 4 返回 429：触发限流，降频或等 1 分钟；确认账户余额与免费额度 限流解除，请求恢复
步骤 5 Key 泄露到代码库或截图外发：立即吊销重发，并宣讲安全纪律 新 Key 生效，旧 Key 作废

卡点 3 · 联调 CORS 与权限（前端能跑、接口不通）

排查步骤 操作 通过标准
步骤 1 浏览器 F12 看 Network：请求发出去了吗？状态码是多少？ 定位到是没发出、被拦、还是报错
步骤 2 报 CORS：后端加跨域响应头（开发期放开来源），前端确认请求地址与端口写对 Console 无 CORS 报错
步骤 3 报 404：路径拼错（少了 /api 前缀或多了一层），前后端对齐路由表 请求打到后端日志
步骤 4 报 401/403：请求头没带 Key 或带错位置（Bearer 前缀缺失） 后端返回业务数据
步骤 5 仍不通：后端先用接口调试工具单独验证，再让前端接——先分后合 单边各自验证通过

七、巡场提问设计（6 问，附预设答案与处理动作）

# 巡场提问 提问对象与时机 预设答案 / 处理动作
1 「你的核心链路是哪三步？给我指一下现在卡在哪一步？」 每位学员开场必问，10–40 分钟 答不出三步的，带他回到检查清单配图逐段过；目标是把「大工程」拆成「三步走」
2 「输入这一端，用户最少操作几步能提交？」 输入环节，问进度快者 超过 3 步的提醒：先做默认示例一键提交，别让输入本身成为门槛
3 「Key 配在环境变量里，还是直接写在代码里？」 调用环节，全员扫一遍 写在代码里的当场改，并讲一句：Key 进代码库等于密码发群里
4 「如果模型 30 秒没返回，你的页面会发生什么？」 调用环节，问已完成调用者 答「转圈到死」的，要求补超时设置与兜底文案——这就是降级意识
5 「这次跑通的记录，你从哪里能看到？」 输出环节，70–80 分钟 指不出日志或控制台记录的，带他打开调用记录页——日志可见是硬标准之一
6 「明天 W6D3 你要打磨的第一件事是什么？」 收尾清算，问 2–3 人 答「样式」的纠偏：先三态（空态/错态/加载态）再美化；答不出的一起看检查清单

八、投屏与板书要点（本课只投 1 张主图）

今天唯一目标：核心链路跑通 = 输入 → 处理 → 输出，一次完整走通

三个检查点（到点打卡，不等讲师催）：
CP1 · 10–40 分钟  输入可提交
CP2 · 40–70 分钟  模型调用通
CP3 · 70–80 分钟  全链路串联 + 日志可见

求助三级制：自己查 5 分钟 → 助教 → 升级讲师（讲师只收「已排查过」的问题）
纪律：先跑通，再完美。今天允许丑，不允许没跑通。

九、学员易错点预判与应对（4 条）

易错点 表现 应对
追求完美迟迟不进入联调 输入页面改了一小时样式，后端还没接 巡场发现立即制止：样式是 W6D3 的活；今天唯一标准是跑通
输入设计过重 要求用户填 8 个字段才肯提交 按提问 2 处理：砍到最少字段 + 提供「一键示例」
忽略日志与调用记录 页面能跑但说不清刚才那次请求发生了什么 按硬标准收作业：指不出调用记录的视为未跑通，现场补
单打独斗不问人 卡了 20 分钟不举手，临近结束才发现 Key 没配 重申求助三级制与「当天问题当天清」；助教每 15 分钟主动扫一遍全场

清算项 动作 产出
