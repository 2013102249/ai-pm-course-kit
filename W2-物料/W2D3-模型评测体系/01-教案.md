## 二、教学目标（可测量）

1. 能说出 Benchmark 的 3 个局限，并解释为什么产品侧必须自建评测集（对应习题基础层第 1–3 题）。
2. 能按「评测集构建四步法」为自己的主项目候选方向设计一份评测集方案：含评测维度（3–8 个）、正例 / 负例 / 边界 case 约 6:2:2 配比、50 条规模规划、通过线定义（对应导学案设计表 + 本周作业）。
3. 能对一条给定的 badcase 按「四类归因框架」（提示词问题 / 模型能力问题 / 资料问题 / 需求问题）完成从现象到假设到验证的归因，并给出对应修复动作与回归测试方案（对应课堂工具实操 + 习题进阶层）。

## 三、教学重难点

- **重点**：评测集构建四步法（定场景维度 → 写用例配比 → 定评分标准 → 试测冻结回流）——这是本周 ≥50 条评测集作业的直接方法论，也是 W6D4 验收的直接依据。
- **难点一**：badcase 归因。学员容易「归因于模型不行」一笔带过，不会做假设—验证的破案式拆解；需要用打分工具把一条 badcase 当堂从头破到尾。
- **难点二**：负例与边界 case 的设计意识。学员天然爱写「模型擅长答」的正例，评测集会变成「自我表扬集」；必须强制 6:2:2 配比并讲清负例的「防翻车」价值。

## 六、课堂提问设计（7 问）

| # | 提问 | 提问时机 | 预设答案 / 引导方向 |
|---|---|---|---|
| 1 | 「你的 AI 产品下周就要上线，你凭什么判断它『行不行』？」 | 导入 | 凭评测：一组预先写好「问题 + 标准答案」的测试集，跑一遍算通过率；没有它就等于开盲盒 |
| 2 | 「Benchmark 榜单第一的模型，为什么做你的客服产品可能不及格？」 | 环节一 | 榜单考的是通用知识，不考你的业务场景、你的格式要求、你的安全红线；且榜单可能被刷榜污染，测不了延迟体验等产品指标 |
| 3 | 「评测集里为什么要专门写模型『应该拒绝或说不知道』的负例？」 | 四步法第二步 | 负例防翻车：幻觉、越权回答、编造政策都发生在模型「不该答却硬答」的时候；不测负例，评测集就成了自我表扬集 |
| 4 | 「50 条里正例、负例、边界 case 各放多少？为什么这么配？」 | 四步法第二步 | 约 6:2:2——30 正例保主流程、10 负例防幻觉、10 边界验鲁棒；正例占比高是因为核心路径优先，但不能没有后两类 |
| 5 | 「一条用例跑到多少分算『通过』？」 | 四步法第三步 | 所有维度均 ≥4 分且未标记 badcase；单条通过率是上线判断的核心指标，建议 ≥80% 再进入灰度 |
| 6 | 「TC-002 编造了『72 小时无条件退款』，你觉得是模型笨，还是别的环节出了问题？」 | 环节三破案 | 不全是模型问题：售后政策文档根本没进知识库（资料问题）+ 提示词缺「资料不足时拒答」的兜底（提示词问题）；换最强模型照样编 |
| 7 | 「让大模型当裁判（LLM-as-Judge）打分，最大的风险是什么？」 | 环节四 | 裁判自己也会偏（偏好长答案 / 自家风格）；对策：人工抽检 10–20% 校准，并给评分锚点描述，不能裸奔 |

## 七、板书要点

```
没评测集 = 开盲盒：上线前不知道行不行，上线后用户替你测

Benchmark ≠ 产品评测：榜单测通用能力，评测集测「我的场景行不行」

评测集构建四步法：
① 定场景定维度（3–8 个：准确性 / 帮助性 / 安全性 / 格式规范性 / 响应体验）
② 写用例：50 条 = 30 正例 + 10 负例 + 10 边界（6:2:2）
③ 定标准：1–5 星锚点；单条通过 = 各维 ≥4 分且非 badcase；上线建议通过率 ≥80%
④ 先试测后冻结；badcase 回流评测集 → 回归测试

badcase 归因四类：提示词问题 / 模型能力问题 / 资料问题 / 需求问题
破案三步：现象 → 假设 → 验证（不许跳步，不许拍脑袋）
```

## 八、课堂练习参考答案（TC-002 归因结论）

| 归因类别 | 是否成立 | 证据 / 验证方式 | 对应修复动作 |
|---|---|---|---|
| 资料问题 | 成立（主因） | 检索知识库无「售后政策」文档，模型只能靠参数知识瞎编 | 政策文档入库并建立更新机制（生效日期 / 责任人） |
| 提示词问题 | 成立（次因） | 系统提示词缺两条约束：仅依据知识库回答；资料不足时明确拒答并转人工 | 补齐拒答兜底指令与回答边界 |
| 模型能力问题 | 不成立 | 同问题换最强模型仍编造——幻觉是概率续写本能，不是换模型能根治的 | 不作为主修复路径 |
| 需求问题 | 部分成立 | 该类问题属高风险敏感场景，应设计「先拒答转人工」的产品策略而非硬答 | 在需求文档中标注高风险清单 |

回归方案：修复后重跑 TC-001 / TC-002 / TC-003 全量 3 条示例，另补 10 条退款类周边用例（含负例「能退我上周激活的耳机吗」），确认 badcase 率回落至 30% 警戒线以下。

## 九、学员易错点预判与应对（5 条）

| 易错点 | 表现 | 应对 |
|---|---|---|
| 评测集全是正例 | 50 条全是「模型擅长答」的问题，通过率 100% 自我安慰 | 现场展示工具里 TC-002：没有负例的评测集抓不住编造政策这类 P0 事故；强制 6:2:2 配比写入作业验收 |
| 期望输出不写或不具体 | 用例只有输入没有「期望输出」，打分时全凭感觉 | 讲工具字段设计：输入 / 期望输出 / 实际输出三栏缺一不可；期望输出是打分的「标准答案」 |
| 归因只会说「模型不行」 | badcase 备注一栏只写「模型太笨」 | 用 TC-002 破案示范：四类假设逐一验证，三问自检——查过提示词吗、查过资料吗、这条需求本身合理吗 |
| 用 Benchmark 分数代替产品评测 | 简历上写「选用榜单第一模型所以效果好」 | 环节一三个局限讲透；补一句面试话术：「榜单是初筛，评测集才是面试官」 |
| 评测一次定终身 | 建完 50 条再也不更新，改版后不回归 | 讲第五步闭环图：badcase 必须回流进评测集，每次改动跑回归；评测集是活的资产，W6D4 验收还要用 |
