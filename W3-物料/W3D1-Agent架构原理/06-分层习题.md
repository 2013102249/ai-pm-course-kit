### 一、选择题（T1–T4，每题 10 分，共 40 分）

**T1. 关于 Agent 与普通 Chatbot（聊天机器人）的分界线，最准确的是：**
A. Agent 用的模型更大、更聪明
B. 交付物从「答案」变成「结果」，责任主体从用户变成产品
C. Agent 只是界面更美观的对话产品
D. Agent 不需要提示词

**T2. 「规划」与「固定工作流」最本质的差别是：**
A. 规划拆出来的步骤更多
B. 工作流由人提前写死、路径固定；规划由 Agent 临场拆，因此必须配步数上限与接管点
C. 规划只用于多 Agent，工作流只用于单 Agent
D. 两者完全是同一件事

**T3. 「可观测性」指的是：**
A. 工程师排查故障用的运行日志
B. 用户能看见 Agent 在干什么、走到第几步
C. 模型内部参数的可解释性
D. 服务器 CPU 与流量监控图表

**T4. 关于「自主性」，正确的理解是：**
A. 越高越好，产品目标就是 100% 全自动
B. 按动作可逆性分档，查询与草稿可放手，不可逆动作必须交还人类
C. 等于模型参数量的大小
D. 只取决于接了多少个工具

## 第 1 层 · 基础巩固题（概念层，原 7 题保留 + 补 3 题）

### 一、选择题（每题 10 分，共 50 分）

**1. 关于 Agent 与普通对话产品的区别，理解最准确的是：**
A. Agent 用的模型更大，所以更聪明
B. Agent 交付的是「办事结果」：拆任务、用工具、拿结果、担责任
C. Agent 就是对话产品加了一个好看的界面
D. Agent 不需要提示词

**2. Agent 四要素中，「规划」的产品职责是：**
A. 让模型回复得更快
B. 定义任务边界与成功标准、设计步数上限与重试策略
C. 负责模型的训练与微调
D. 把长文本压缩成短文本

**3. 关于 Agent 的记忆，说法正确的是：**
A. 记忆越多越好，越多越聪明
B. 长期记忆应全量保存用户所有对话，方便随时调用
C. 记忆需要设计写入与遗忘策略，且用户应能查看和删除
D. 记忆是技术模块，与产品经理无关

**4. 「工具的描述文案是提示词的一部分」，这句话的意思是：**
A. 工具描述要写得像广告文案一样吸引人
B. 模型靠工具描述决定何时调用、传什么参数，描述质量直接影响调用准确率
C. 工具描述越长越好，细节越多越好
D. 工具描述由法务审核即可

**5. 以下哪个动作，Agent 可以不经人工确认直接执行？**
A. 用户授权额度内的支付下单
B. 向客户发送商务邮件
C. 生成一份竞品对比草稿（仅本地保存，可随时修改删除）
D. 删除数据库中的用户记录

## 第 3 层 · 求职挑战题（面试层，原 2 题保留 + 补 2 题）

**10. 面试真题：要不要上 Agent？（30 分）**
面试官：「我们想给内部运营做一个『自动分析销售数据并直接调整投放预算』的系统，你觉得该做成 Agent 吗？为什么？」
要求：先给结论，再给两条理由，最后给出一个替代或折中方案。

**11. 案例分析：Agent 跑飞了（30 分）**
你负责的调研 Agent 上线后，用户投诉集中在两类：① 有用户发现同一个任务花费是平时的 8 倍，查日志发现 Agent 在两步之间反复重试了 40 多次；② 有用户发现 Agent 在未确认的情况下，把报告自动发送到了公司大群。
请给出：问题各自的根因、对应的产品改进动作（至少 3 条），以及如何向业务方解释「为什么不能追求 100% 全自动」。

**3-补①（新增，30 分）多 Agent 方案评审**
某方案把「资料整理 + 成稿」拆成调研、写作、审校、发布、复盘 5 个 Agent。请列出：① 三个隐藏成本 ② 判断该不该拆的三个信号 ③ 你的明确结论 ④ 一句对业务方的表述（不编效果数字）。

**3-补②（新增，30 分）向业务方解释不能全自动**
业务方坚持要 100% 全自动，并拿别家产品压你。请写一段沟通话术：① 不把产品判断包装成「技术做不到」 ② 用「全自动的隐含代价」说清风险 ③ 给出「AI 建议、人类拍板」的折中方案 ④ 说明接管点该写进哪一版需求。

## 第 4 层 · 面试实战题（新增层，6 题，每题含踩分点 / 追问链 / 评分表）

> 使用说明：第 5 节两两模拟时，考官按「踩分点」判分、按「追问链」连追 2–3 层，答者对照「评分表」自评；60 秒标准答法与失败答法见本文件末尾《参考答案与评分标准 · 第 4 层》。

### M1 · Agent 和普通 Chatbot（聊天机器人）到底有什么区别？别用「更智能」这类词
**题型：技术理解**

- **踩分点（3–4 条，可判分）**：① 交付物从「答案 / 信息」变成「结果 / 订单」；② 责任主体从用户变成产品，做错一步是真金白银的损失；③ 说出「拆任务、用工具、拿结果、担责任」中至少两个动作；④ 举一个自己主项目的例子。
- **追问链（3 层）**：① 「带插件的 Chatbot 算 Agent 吗？」→ 看是否自主拆解并循环执行，插件只是工具调用；② 「只需要查一条退款政策呢？」→ 单一知识查询用检索问答即可，引出 M3；③ 「责任主体变了，界面要跟着变什么？」→ 步骤可见、可中断、接管点、不可逆动作人工确认。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 说出交付物或责任主体之一，给一条说得通的理由 | 18–23 |
| 良好 | 交付物 + 责任主体都说清，含「拆任务 / 用工具 / 担责任」至少两个动作 | 24–27 |
| 优秀 | 另举自己主项目例子，并落到边界设计（步数上限 / 接管点 / 人工确认） | 28–30 |

### M2 · ReAct 是怎么工作的？为什么产品经理要关心它？
**题型：技术理解**

- **踩分点**：① 说清四拍循环（思考—行动—观察—再思考）；② 给出全称 Reasoning + Acting，推理与行动交替；③ 落点是「把思考摊开给用户看」，不是背术语；④ 说出信任 / 可中断 / 可纠偏中至少两样。
- **追问链（3 层）**：① 「摊开全部推理会信息过载吗？」→ 分层呈现，默认步骤清单、可展开细节；② 「反思机制算哪一拍、要无限反思吗？」→ 失败后换方式再来的一次推理，仍受步数上限约束；③ 「看不见过程会怎样？」→ 黑箱转圈、用户流失，且 badcase 无从归因。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 说出四拍循环或「摊开给用户看」之一 | 18–23 |
| 良好 | 四拍 + 全称 + 信任 / 可中断 / 可纠偏任两样 | 24–27 |
| 优秀 | 另给出「可展开的透明」的分层呈现设计，并点明不是 debug 界面 | 28–30 |

### M3 · 什么时候不该用 Agent？给我三个判断信号和替代方案
**题型：场景设计**

- **踩分点**：① 说出三类不该用场景（路径完全固定 / 单一知识查询 / 高风险不可逆且要全自动）；② 每类给替代方案（固定工作流、检索问答、AI 建议 + 人类拍板）；③ 给出决策三问顺序；④ 提到「可靠性优先于自动化率」。
- **追问链（3 层）**：① 「业务方就要 100% 全自动怎么说服？」→ 全自动的隐含代价是错误也全自动；② 「只做前半段算半成品吗？」→ 人机分工本就是设计；③ 「怎么度量不该上 Agent？」→ 路径是否可变、是否要自主拆、是否涉及不可逆。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 结论明确（不全自动），说出两类场景 | 18–23 |
| 良好 | 三类场景 + 三类替代方案齐全，含决策三问 | 24–27 |
| 优秀 | 另给出「分析 / 建议 / 决策」三段人机分工与可靠性表述 | 28–30 |

### M4 · 多 Agent 的复杂度怎么控？你们项目为什么用 / 不用多 Agent？
**题型：项目深挖**

- **踩分点**：① 先给「默认不用」结论；② 说出三个隐藏成本（协作协议、消息损耗、失败传播）；③ 说出三个该拆信号（可并行 / 上下文装不下 / 专业或权限需隔离）；④ 落到自己主项目给具体判断。
- **追问链（3 层）**：① 「一定要拆，先定哪三件事？」→ 传话格式、先后顺序、失败定位与兜底；② 「两个能做的事拆五个，问题在哪？」→ 每多一环多一次有损压缩，越往下游越难定位；③ 「单 Agent 上下文不够怎么办？」→ 先做记忆分层与摘要，别急着拆大脑。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 给出「默认不用」结论，说出至少一个隐藏成本 | 18–23 |
| 良好 | 三个隐藏成本 + 三个信号齐全，含决策三问 | 24–27 |
| 优秀 | 另落到自己主项目判断，并给出「真要拆先定三件事」 | 28–30 |

### M5 · Agent 四要素里，哪一个最容易被产品经理漏掉？为什么？
**题型：技术理解**

- **踩分点**：① 给出明确答案（执行或记忆，须自圆其说）；② 说出四要素名称；③ 解释漏掉的具体后果；④ 给一条可落地补法。
- **追问链（2 层）**：① 「补上之后怎么验收？」→ 草图四框齐全 + 不可逆动作清单；② 「执行和工具调用是一回事吗？」→ 工具是接上能力，执行是真正动手发起调用。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 给出明确答案并说出一个后果 | 18–23 |
| 良好 | 四要素名称齐全 + 后果具体（无确认闸门 / 无留痕 / 无回滚） | 24–27 |
| 优秀 | 另给可落地补法（强制四框 + 不可逆动作清单）并区分「工具 vs 执行」 | 28–30 |

### M6 · 用户让 Agent 帮他订机票并付款，你怎么设计接管点？
**题型：场景设计**

- **踩分点**：① 说出三种交还时刻（置信度低 / 预算触顶 / 不可逆动作前）；② 接管呈现用「暂停 + 选项」而非弹窗打断；③ 配合最大步数与单任务成本上限；④ 有执行日志留痕、可回滚补偿。
- **追问链（3 层）**：① 「上限设多少、凭什么？」→ 给数字与依据，且超限即暂停交还人类；② 「用户嫌老确认太烦怎么办？」→ 自主性按动作可逆性分档；③ 「订错城市怎么补救？」→ 回滚补偿、人工接管后重跑，靠日志定位。
- **评分表**：

| 档位 | 标准 | 分值 |
|---|---|---|
| 合格 | 说出付款前需人工确认，给出一种交还时刻 | 18–23 |
| 良好 | 三种交还时刻 + 「暂停 + 选项」呈现 + 步数与成本上限 | 24–27 |
| 优秀 | 另给出可逆性分档、执行日志与回滚补偿，并回应「太烦」的体验权衡 | 28–30 |

### 第 2 层 · 进阶实操（原三档 Rubric 保留 + 补题）

**第 8 题参考答案**：
① 固定工作流——路径完全固定、无需自主决策，Agent 反而增加成本与不确定性；
② Agent——需求开放、路径不固定，需要自主拆解与工具调用；
③ 都不用 Agent——知识问答用 RAG（Retrieval-Augmented Generation，检索增强生成）即可（衔接 W3D3），不需要自主执行；
④ 不该直接放手——涉及支付不可逆动作，必须人工确认闸门；顶多做「准备好订单，等用户一键确认」。

| 档位 | 标准 |
|---|---|
| 合格（30–39 分） | 4 个判断中 3 个正确，每题至少 1 条理由 |
| 良好（40–44 分） | 4 个判断全对，理由体现「路径是否固定 / 是否不可逆」两个框架 |
| 优秀（45–50 分） | 额外指出「③ 应联想到 RAG」「④ 给出订单确认的折中设计」等方案层思考 |

**第 9 题参考答案（要点）**：工具清单具体到名称与权限（如「只读知识库、可写草稿箱、不可直接对外发送」）；步数上限给出具体数字（如 15–25 步）并说明超限后交还人类；接管点至少含「置信度低 / 预算触顶 / 不可逆动作前」中的两类；不可逆动作与确认方式一一对应。

| 档位 | 标准 |
|---|---|
| 合格（30–39 分） | 5 项齐全，数字与清单具体 |
| 良好（40–44 分） | 工具有权限说明，接管点能对应到自己项目的真实场景 |
| 优秀（45–50 分） | 额外设计回滚 / 补偿机制、执行日志留痕，或给出接管点的交互呈现方式 |

**2-补①参考答案**：① 默认只展示一行一句的步骤清单，完成一步打一个勾；② 想看细节的用户点开某一步看完整推理与工具返回，即「可展开的透明」；③ 失败重试与反思以「正在换一种方式重试（第 N 次，上限 M 次）」呈现，超出即暂停交还人类；④ 技术一点没变，改的是把本来就存在的思考过程翻译给用户看，所以是产品改进（信任与可中断），不是技术改进。

| 档位 | 标准 |
|---|---|
| 合格（30–39 分） | 写出默认步骤清单与可展开细节两项 |
| 良好（40–44 分） | 四项齐全，含反思次数上限与超限交还 |
| 优秀（45–50 分） | 另说明「默认清单 / 点开细节」的分层理由，或点明可观测性 ≠ 运行日志 |

**2-补②参考答案**：① search：当需要查询实时信息（股价、汇率、新闻）时调用，输入为自然语言关键词；② db：当需要读取企业内部结构化数据（订单、库存）时调用，输入为查询条件，只读、不写；③ mail：仅当用户在确认界面点击「确认发送」后才调用，输入为收件范围与正文，且须先经人工确认。最小工具集 3 个：只读知识库、只读数据库、可写草稿箱；权限逐项写清，对外发送类工具不进默认集。

### 第 3 层 · 求职挑战（原三档 Rubric 保留 + 补题）

**第 10 题参考答案**：结论=不直接做全自动 Agent。理由 1：「调整预算」是高风险不可逆动作，直接影响真金白银，必须有人工确认；理由 2：任务结构其实可拆为「数据分析（固定）+ 建议生成（AI）+ 决策执行（人类）」，不需要端到端自主。折中方案：Agent 只做分析与建议输出，预算调整由运营一键确认执行——即「AI 建议、人类拍板」。

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 结论正确（不全自动），有两条说得通的理由 |
| 良好（24–27 分） | 理由包含「不可逆动作需人工确认」框架，方案可落地 |
| 优秀（28–30 分） | 把任务拆成「分析 / 建议 / 决策」三段并明确人机分工，或提到成本上限与审计日志 |

**第 11 题参考答案**：根因 1：无步数上限与重试策略（失败后无脑重试）；改进：设 max steps、失败 N 次即暂停交还、单任务成本上限熔断。根因 2：对外发送动作无人工确认闸门；改进：发送类动作强制确认 + 执行日志留痕可审计。向业务方的解释：全自动的隐含代价是「错误也全自动」，接管点不是能力不足，而是把责任留在该在的位置——可靠性优先于自动化率。

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 两个根因定位正确，改进动作至少 3 条 |
| 良好（24–27 分） | 改进动作具体到参数（步数上限、熔断阈值、确认交互） |
| 优秀（28–30 分） | 额外给出「可靠性 vs 自动化率」的表述框架，或设计 badcase 回流与监控指标（单任务成本、重试率） |

**3-补①参考答案**：① 三个隐藏成本：协作协议（怎么传话、传什么格式、谁先谁后）、消息损耗（每传一次都是有损压缩）、失败传播（一环出错往下游传染且越往下越难定位）；② 三个信号：任务真能并行、单 Agent 上下文真装不下、专业能力或权限真需隔离；③ 结论：默认不用，本方案路径串行、上下文塞得下，用单 Agent；④ 对业务方表述：「多 Agent 是复杂度黑洞，两个 Agent 能做的事别用五个，我先把接管点和步数上限做扎实。」

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 三个隐藏成本写出两个，结论为「默认不用」 |
| 良好（24–27 分） | 三个隐藏成本 + 三个信号齐全，结论有理由 |
| 优秀（28–30 分） | 另给「真要拆先定传话格式 / 先后顺序 / 失败兜底」，或落到自己主项目 |

**3-补②参考答案**：话术要点——不说「技术做不到」，改说「把任务拆三段给你看：分析固定、建议可用 AI、改预算是不可逆动作」；点明「全自动的隐含代价是错误也全自动，接管点不是能力不足，是把责任留在该在的位置」；折中「AI 出建议、运营一键拍板」；并说明接管点要写进第一版需求，别等上线后补。

| 档位 | 标准 |
|---|---|
| 合格（18–23 分） | 不说技术做不到，给出折中方案 |
| 良好（24–27 分） | 含「全自动的隐含代价」表述与三段人机分工 |
| 优秀（28–30 分） | 另给出「可靠性优先于自动化率」框架，或说明接管点写进第一版需求 |

### 第 4 层 · 面试实战（60 秒标准答法 + 典型失败答法）

> 踩分点、追问链与评分表见各题上方；此处给「60 秒标准答法」与「典型失败答法 + 失分原因」，供两两模拟后对照。

**M1 · 60 秒标准答法**：「我不用『更智能』来答，因为那是程度词，不是分界线。分界线是交付物和责任主体：Chatbot 你问一句它答一句，交付的是答案，对错你自己把关；Agent 你给一个目标，它自己拆任务、调工具、把结果拿回来，做错一步是真金白银的损失，责任在产品这边。所以我做这类产品，第一件事不是选模型，是画边界——任务边界、步数上限、人工接管点。比如我主项目里『对外发送』这一步，我一定设成暂停加确认，而不是让它自己发出去。这就是从答题到办事。」
**典型失败答法**：「Agent 更智能、能自主决策、会自己思考。」失分原因：全是无法判分的空话，没碰交付物与责任，一追「怎么落地」就露馅。

**M2 · 60 秒标准答法**：「ReAct 全称 Reasoning + Acting，推理与行动交替，循环是四拍：思考我该做什么、行动调工具、观察返回结果、再思考调整下一步。但产品经理关心的不是循环本身，而是把它摊开给用户看。可观测性带来三样东西：用户知道它在干嘛，这是信任；跑偏了能随时叫停，这是可中断；出了错能定位到第几步，这是可纠偏。呈现上我会分层，默认只给一行一句的步骤清单，想看细节再点开，这叫可展开的透明——它不是给工程师看的 debug 界面，是 Agent 产品的信任地基。」
**典型失败答法**：「ReAct 就是让模型一边想一边做，是个技术框架，产品不用管。」失分原因：把最值钱的差异化答案拱手让人，且暴露没意识到可观测性是信任设计。

**M3 · 60 秒标准答法**：「三类场景我会先踩刹车。第一，路径完全固定、每周重复的事，用固定工作流更稳更便宜，不必让 Agent 临场拆；第二，只查一条政策、一个数据，用检索问答就够；第三，涉及支付、发送、删除这类不可逆动作，我不做端到端全自动，而是拆成『分析 / 建议 / 决策』三段，AI 出建议、人类一键拍板。我的决策顺序是三问：先问单 Agent 能不能解决，再问要不要 Agent，最后才问要不要多个。跟业务方我会讲一句实话——全自动的隐含代价是错误也全自动，接管点不是能力不足，是把责任留在该在的位置，可靠性优先于自动化率。」
**典型失败答法**：「Agent 这么强，什么场景都能上，就看模型够不够好。」失分原因：没有判断框架，把选型问题甩给模型能力，直接判「没做过」。

**M4 · 60 秒标准答法**：「我的默认答案是不用。多 Agent 是复杂度黑洞：两个 Agent 能做的事，别用五个。它多出三个隐藏成本——Agent 之间怎么传话的协作协议、每传一次都有损耗的消息压缩、还有一环出错往下游传染且越往下游越难定位的失败传播。只有三个信号占其一我才考虑拆：任务真能并行、单 Agent 上下文真装不下、不同环节的专业能力或权限真需要隔离。我主项目是路径串行、上下文也塞得下的场景，所以用单 Agent，把省下来的复杂度花在接管点和步数上限上。真要拆，我先定传话格式、先后顺序和失败兜底这三件事。」
**典型失败答法**：「我们项目拆了五个 Agent，调研、写作、审校、发布、复盘各管一段，显得架构很完整。」失分原因：把「拆得多」当能力，正踩复杂度黑洞，一追协作协议就问倒。

**M5 · 60 秒标准答法**：「最容易漏的是执行。四要素是规划、记忆、工具、执行，大家画架构图常画成『大模型 + 工具』两个框，因为觉得调了工具就算办事了。但工具只是接上能力，执行是真正发起调用、跟环境发生交互的那一步——没有它，前面三个要素都在『想』，产品就还是答题。漏了它的后果很具体：不可逆动作没人设人工确认闸门、没有回滚与补偿、也没有执行日志留痕，出了问题无从审计。我的补法很土但有效：草图强制四框齐全，再单独列一张『支付 / 发送 / 删除 / 对外承诺』清单，逐条写明确认方式。」
**典型失败答法**：「都挺重要的，一个都不能少。」失分原因：没判断、没优先级，等于没答；面试官要的是踩过坑的经验。

**M6 · 60 秒标准答法**：「我会把付款这一步设成硬接管点。三种时刻必须交还人类：模型对下一步没把握、步数或预算触顶、碰到不可逆动作——付款正属于第三种。呈现上不是弹窗打断，而是『暂停 + 选项』：把航班、总价、乘机人摆出来，给『确认支付』和『我要改』两个按钮，用户保有控制感。前面还要配两道闸：最大步数和单任务成本上限，超了就暂停交还，不是让它无限重试。查询航班、比价这类可逆动作可以放手跑，支付、出票、对外承诺必须停下来。全程执行日志留痕，订错了能回滚、能补偿。一句话，自主性要按动作可逆性分档，不能一刀切全自动。」
**典型失败答法**：「全部让它自动跑完，最后给用户一个订单确认页就行。」失分原因：把不可逆动作放到事后确认，钱已经付了；也没有「暂停 + 选项」的控制感设计。

> 第 4 层统一提醒：所有标准答法都遵守「先结论 → 三条踩分点 → 一个当日术语 → 一个自己项目的例子」；被追问「那怎么落地」时，一律落回接管点 / 步数上限 / 人工确认。
