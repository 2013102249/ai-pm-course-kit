# 讲课稿 · W3 周一《Agent 架构原理》

## 术语精讲与零层入口

### 讲师话术

大家好，今天是第三周的周一。先帮大家把坐标定位一下：上个星期，你们完成了模型选型、微调原理、评测体系和合规四件事，周五每个人都把主项目立了项——选题、目标用户、核心场景、成功指标，全部锁定。从今天起，训练营进入一个新阶段：把你立项的那个产品，做成真的。

第三周的产出是三件套：Agent（智能体）架构图、工作流原型、知识库原型。今天这 今天（6 节课），就为第一件打地基。也提醒一句：这一周的技术内容，不再是为学而学——每讲完一个东西，都要立刻回答「我的项目里用不用它、怎么用」。所以今天上课时，请你们脑子里始终装着自己立项的那个产品，每讲完一个要素，就问自己一句：我的产品里，这个要素长什么样？

先说今天的终点，下课的时候你要能做成三件事：第一，画出你自己主项目的 Agent 架构草图，四要素一个不少；第二，能用一句话给别人讲清楚「Agent 和普通对话产品的区别」；第三，面对一个场景，你能初步判断该不该上 Agent。这三个能力，直接决定你周五的架构图长什么样，也决定面试里「讲一个你做的 AI 产品」你能讲多深。

今天比原来多出五节课的时间，多在哪？多在两个地方：专门把名词嚼碎，专门把名词换成面试得分点。中间三节还是把 Agent 这件事讲透、练熟。你们不用担心听不懂——今天一个代码字都不写，一张架构图的内部细节都不抠，全用做饭、点菜、搬家、叫水电工这种生活里的事打比方。

今天课里技术名词最多，先垫三个最核心的，每个记一句话就够。

**第一个词，Agent，中文叫智能体。**普通的 AI 产品是「你问我答」——你给一句，它回一句。Agent 是「你交办、它去办」：你给它一个目标，它自己拆解步骤、自己动手、最后把事办完。一句话记住：**会办事的 AI。**今天整节课，讲的就是「让它会办事」需要哪几样东西。

**第二个词，API，Application Programming Interface，应用程序接口。**听着唬人，事情很朴素。你去餐厅点菜，不会自己冲进厨房炒，你对着服务员说就行——服务员把你的话带给后厨，把菜带出来。API 就是软件世界里的服务员：你的产品想查地图、查订单、发邮件，不用自己会干这些事，通过 API「点菜」就行。今天课上，Agent 办的每一件事，几乎都是通过 API 去办的。

**第三个词，MCP，Model Context Protocol，模型上下文协议。**名字最唬人，事最简单。过去每家 AI 和每个工具的接口都不一样，接一个就得单独适配一次，又贵又慢。MCP 就是给它们统一了插头标准——像家里墙上的国标插座，不管哪个牌子的电器，插上就能用。今天会专门讲它，先记住：**MCP = 给 AI 和工具定的统一插头标准。**

好，三个词垫完：Agent 是会办事的 AI，API 是软件的服务员，MCP 是统一插头标准。我们进入今天的术语精讲。

**术语 1 · Agent（智能体）**
- 一句话定义：会自己拆任务、用工具、把事办完的 AI。
- 生活类比：你交办给助理「帮我安排下周出差」，他自己去查、去订，回你一句「办好了」——你不用一步步盯着。
- 易混辨析：最容易和普通 Chatbot（聊天机器人）混。Chatbot 你问一句它答一句，交付「答案」；Agent 你给目标它交付「结果」，还要担责任。差别不是聪不聪明。
- 面试说法：「Agent 和对话产品的本质区别，是从答题走向办事——交付物从信息变成结果，责任主体从用户变成产品。」
- 术语卡：`03-配图素材/术语卡/Agent.md`（待制，已在 05-配图清单 登记）。

**术语 2 · 四要素（规划 / 记忆 / 工具 / 执行）**
- 一句话定义：让大模型能办事的四样零件。
- 生活类比：开一家小餐馆：规划是排好做菜顺序，记忆是记住老客口味，工具是锅碗灶具，执行是真正把菜端上桌。
- 易混辨析：容易和「模型能力」混。四要素不是更聪明的模型，是围着模型搭的产品设计——模型只是大脑，四要素是四肢。
- 面试说法：「Agent 的难点从来不在模型，而在四要素的产品设计，每个要素产品经理都有一块自留地。」
- 术语卡：`03-配图素材/术语卡/四要素.md`（待制）。

**术语 3 · ReAct（Reasoning + Acting，推理与行动交替）**
- 一句话定义：模型「想一步、做一步、看一眼、再想」的循环。
- 生活类比：照着菜谱做没做过的菜：先看一步说明、动手、尝一口咸淡、再决定要不要加盐。
- 易混辨析：容易和「一次性给答案」混。普通问答是一锤子买卖，ReAct 是「做一步看一步」的循环，跑偏了能中途调头。
- 面试说法：「ReAct 对产品经理的意义，是把模型的思考过程摊开给用户看——换来信任、可中断、可纠偏。」
- 术语卡：`03-配图素材/术语卡/ReAct.md`（待制）。

**术语 4 · 规划（Planning）**
- 一句话定义：把大目标拆成一串可执行的小步骤。
- 生活类比：搬家前先列清单：装箱、叫车、搬运、拆箱，而不是想到哪件搬哪件。
- 易混辨析：容易和「固定工作流」混。工作流是人提前把步骤写死、路径不变；规划是 Agent 自己临场拆，所以更要设步数上限。
- 面试说法：「规划模块我一定配三样：任务边界、步数上限、重试策略——没有最大步数（max steps）的 Agent 是在拿用户 token（用量计费单位）赌运气。」
- 术语卡：`03-配图素材/术语卡/规划.md`（待制）。

**术语 5 · 记忆（Memory）**
- 一句话定义：Agent 记下的上下文与跨会话经验。
- 生活类比：常去的理发店师傅记得你「两边推短、上面留长」，你不用每次重讲一遍。
- 易混辨析：容易和「聊天记录」混。聊天记录是流水账全存；记忆要设计「记什么、忘什么」，用户还能查看和删除。
- 面试说法：「记忆不是越多越好——会遗忘才是产品设计，长期记忆要白名单化、用户可见可删。」
- 术语卡：`03-配图素材/术语卡/记忆.md`（待制）。

**术语 6 · 工具调用（Tool Use / Tool Calling）**
- 一句话定义：Agent 借用外部能力去查数据、办事情。
- 生活类比：自己不会修水管，但会打电话叫水电工——你不必会干，知道叫谁就行。
- 易混辨析：容易和「模型自己算」混。模型硬答汇率往往是编的；调了查询工具拿回的才是真数据。
- 面试说法：「工具给最小集、权限最小化，而且工具描述文案就是提示词的一部分——模型靠它决定何时调用、传什么参数。」
- 术语卡：`03-配图素材/术语卡/工具调用.md`（待制）。

**术语 7 · MCP（Model Context Protocol，模型上下文协议）**
- 一句话定义：给模型和工具定统一插口，让接入即插即用。
- 生活类比：以前打印机、鼠标、键盘各一种线；有了 USB，什么设备插上就能用。
- 易混辨析：容易和「某一个工具或插件」混。MCP 不是工具本身，是工具与模型之间的接口标准，把 M×N 套适配降到 M+N。
- 面试说法：「工具侧有 MCP、Agent 互联侧有 A2A（Agent-to-Agent，Agent 之间的协作协议）——接入成本下降后，工具生态成了我选平台的正式考量项。」
- 术语卡：`03-配图素材/术语卡/MCP.md`（待制）。

**术语 8 · Multi-Agent（多智能体）**
- 一句话定义：多个 Agent 分工协作，各管一段任务。
- 生活类比：办一场婚礼，请了策划、摄影、司仪各管一摊——人多了，就得多一个人专门协调。
- 易混辨析：容易和「把一个 Agent 拆成多个步骤」混。那是同一个 Agent 的规划；多 Agent 是多个独立大脑，会多出传话、损耗、失败传播的代价。
- 面试说法：「多 Agent 是复杂度黑洞：两个 Agent 能做的事，别用五个；先问单 Agent 能不能解决。」
- 术语卡：`03-配图素材/术语卡/Multi-Agent.md`（待制）。

**术语 9 · 自主性（Autonomy）**
- 一句话定义：不用人一步步指挥、自己往下跑的程度。
- 生活类比：定好目的地的代驾，你不用告诉他每个路口怎么拐；但过收费口、停车付钱，他还得问你一句。
- 易混辨析：容易和「全自动」混。自主性要分档，不是越高越好；不可逆动作那一档，必须收回来交还人类。
- 面试说法：「自主性我按动作可逆性分档：查询、草稿放手做；支付、发送、删除必须停下来等人点头。」
- 术语卡：`03-配图素材/术语卡/自主性.md`（待制）。

**术语 10 · 边界（Boundary，产品边界）**
- 一句话定义：划清 Agent 该做什么、做到哪、何时停。
- 生活类比：给家政阿姨列一张单子：打扫哪些房间、哪些柜子别动、拿不准的先打电话问。
- 易混辨析：容易和「功能清单」混。功能清单说「能做什么」；边界更要说「不做什么」和「什么时候停」——任务边界、步数上限、接管点都算。
- 面试说法：「我设计 Agent 先画边界：任务边界、最大步数、成本上限、人工接管点，四样缺一不可。」
- 术语卡：`03-配图素材/术语卡/边界.md`（待制）。

**术语 11 · 幻觉（Hallucination）**
- 一句话定义：模型一本正经地编出不存在的内容。
- 生活类比：问路碰到不熟路的人，他不好意思说不知道，随口给你指了个方向，听着还挺肯定。
- 易混辨析：容易和「答错」混。答错是记岔了，幻觉是凭空造；Agent 里靠工具调用查证、靠执行日志留痕兜底，正好对上「办事要担责任」。
- 面试说法：「答题型产品幻觉顶多被吐槽，办事型产品幻觉是真金白银的损失——关键数据必须工具查证、不可逆动作必须人工确认。」
- 术语卡：`03-配图素材/术语卡/幻觉.md`（待制）。

**术语 12 · 可观测性（Observability）**
- 一句话定义：用户能看见 Agent 在干什么、走到第几步。
- 生活类比：外卖 App 上的「骑手已取餐、距您 1.2 公里」——看不见进度，你才会一遍遍刷新。
- 易混辨析：容易和「运行日志」混。日志是给工程师排错用的；可观测性是给用户看的步骤清单，是信任设计，不是调试界面。
- 面试说法：「可观测性不是 debug 界面，是信任地基：默认展示步骤清单，想看细节再点开——这叫可展开的透明。」
- 术语卡：`03-配图素材/术语卡/可观测性.md`（待制）。

好，12 个词过完了。现在别急着往下走，我们先把最容易糊的三组拆开。我说一个，你们齐声答「谁拆步骤」「给谁看」「责任在谁」。

第一组：Agent 和 Chatbot。我问一句——一个带插件的聊天机器人，是不是就算 Agent？对，不算。插件只是给了它手，关键是它会不会自己拆任务、做一步看一步、最后把结果拿回来。分界线不是聪不聪明，是交付物和责任主体。

第二组：规划和固定工作流。都是把事拆成步骤，差在哪？差在「谁拆」。工作流是人事先写死的，路径每周都一样；规划是 Agent 临场自己拆的，所以它才必须配步数上限和接管点——自己拆的，才可能拆飞。

第三组：可观测性和运行日志。日志是给工程师排错看的；步骤清单是给用户看的，目的是让他敢等、敢叫停。一个是调试，一个是信任，别混。

再做两道改错题，写在答题纸上。第一句：「Agent 的记忆越多越好。」错。要设计记什么、忘什么，用户还要能查看和删除——会遗忘才是产品设计。第二句：「可观测性就是给工程师看的运行日志。」错，理由刚才齐读过了。

最后八分钟，一张答题纸：三道缩写全称连线（ReAct、MCP、API），两道改错，三道一句话定义。不记分排名，只给自己打个勾——哪一行没写上，就在《术语自测表》那行旁边画个圈，面试课之前补掉。

核对答案时提醒一句：ReAct 是 Reasoning + Acting，推理与行动交替；MCP 是 Model Context Protocol，模型上下文协议；API 是 Application Programming Interface，应用程序接口。面试里说得出全称，考官就知道你不是只会背字母。

## 核心原理讲授 A

### 讲师话术

正式开讲之前，我先请大家想一个对比。

上个星期你们天天在用对话产品：问它一个问题，它回你一段话。比如你问它「帮我写一份三天的东京旅游攻略」，它唰唰唰写出来了，航班信息可能是编的，酒店价格可能是过时的，但没关系——它交付的是一份「答案」，用不用、怎么用、出了错算谁的，都是你自己的事。

现在换一件事：你说「帮我订下周三去东京的机票和酒店，预算五千」。注意，这次它要交付的不是攻略，是订单。要拆任务——先查航班再比价再下单；要用工具——真的去调订票接口；要拿结果——你手机上得出现一条真实的订单；还要担责任——订错了城市、买贵了两千，这个责任是它的。

这就是今天第一个要记住的框架：**答题是给答案，办事是拆任务、用工具、拿结果、担责任。Agent 就是从「答题」走向「办事」的那一步。**

那我先问大家：这两件事，对产品经理来说，最本质的差别是什么？

有同学说到点子上了——交付物变了，责任主体也变了。答题型产品，模型说错了顶多被吐槽；办事型产品，模型做错一步是真金白银的损失。所以 Agent 产品的设计难度，不在技术多复杂，而在「责任」两个字上。这个点我们今天最后会回到它那里。

市面上已经有产品把「办事」这件事做成了形态。比如 Manus，它的公开定位就是通用 Agent：你给它一个目标，它自己拆解任务、调用浏览器和代码等工具去执行，整个过程以任务列表和步骤的形式展示给用户。再比如扣子，是字节跳动推出的 Agent 开发平台，提供插件、工作流、知识库这些能力，让你自己搭一个能干活的 Agent。注意，我今天只描述它们的公开形态，不评价优劣——你们 W1D4 做产品拆解时已经练过怎么客观地看一个产品。

再往深一层想：责任主体变了，产品的每一个设计决策都要跟着变。答题型产品，错一个字改一下提示词就行；办事型产品，你要回答一连串新问题——它每一步要不要给用户看？哪一步开始要收费？做错了怎么补救？哪些事绝对不能让它自作主张？这一串问题，没有一个是「技术问题」，全部是产品问题。今天就是教你们把这串问题一个一个回答掉。

那 Agent 到底是什么？我给大家一个不用背的定义：

**Agent 就是长着四肢的大模型。**模型是大脑，四肢是四要素：规划、记忆、工具、执行。

回忆一下 W1D2，我们讲过大模型是一个「看懂指令、续写答案」的概率引擎——那是大脑。大脑再聪明，它也只动嘴不动手。你让它「去查一下今天的汇率」，它只能编一个像汇率的数字，因为它没有手。Agent 要解决的就是这个问题：给大脑装上四肢，让它从「能说」变成「能做」。

看这张图。中间是 Agent 核心，也就是那个大脑，负责规划和调度。左边和右边、上面和下面，是四个器官：

上面两个：规划，把大目标拆成一步一步；记忆，记住发生过的事。
下面两个：工具，接上外部能力；执行，真正动手干活。

这张图今天会陪我们一整节课，大家先在导学案上把骨架画下来——中间一个核心，四周四个要素，连上线。细节我们马上一个一个过。

先泼一盆冷水：不是所有产品都需要 Agent。你们的主项目里，有些环节用固定的流程跑反而更稳、更便宜。什么时候用 Agent、什么时候用固定工作流，明天 W3D2 会专门练这个判断。今天你先把 Agent 的原理吃透，明天才有资格决定「不用它」。

接下来这段时间，是这一节的核心。我们用这个交互工具，四个要素逐个点开讲。每讲一个，你们在导学案的「四要素笔记表」里填一行：是什么、产品经理管什么、常见坑。

**第一个要素：规划。**

规划，就是把一个大目标拆成可执行的步骤序列。用户说「帮我调研这三个竞品并写成报告」，规划模块要把这句话拆成：先搜集资料、再对比整理、再生成报告、最后自查——四步，每一步可执行。

产品经理管什么？三件事。第一，任务边界：哪些事这个 Agent 该干、干到什么程度算完成，必须先定义清楚，不然它会拿着模糊的目标瞎跑。第二，可观测：用户要能看到它拆成了哪几步、现在进行到第几步——Manus 把任务列表直接展示出来，就是这个设计。第三，重试策略：某一步失败了，重试几次？什么时候放弃并交还人类？这些不是技术细节，是产品规则。

现在问大家：Agent 拆完任务之后，为什么还是会一步错、步步错？

对——没有步数上限。第一步的理解就偏了，后面每一步都在错误的轨道上狂奔，而且不设上限地跑。所以我给你们今天的第一句核心金句：

**没有步数上限的 Agent，是在拿用户的 token（用量计费单位）赌运气。**

记住，做 Agent 产品，最大步数是必填项，不是可选项。

规划的常见坑就一个：只画流程，不定边界和上限。你面试的时候画出「max steps = 20，超出即暂停并交还人类」，面试官立刻知道你真做过。

**第二个要素：记忆。**

记忆分两层。短期记忆，就是当前这轮任务里的上下文——用户的目标、已经完成的步骤、中间结果，都在模型的上下文窗口里。长期记忆，是跨会话的存取——上次用户告诉过它「我偏好靠窗的座位」，下次不用再说一遍。

产品经理管什么？第一，写入与遗忘策略：什么值得记、什么必须忘。第二，隐私边界：长期记忆里存了用户什么，用户有权看到、有权删除——这在合规上不是加分项，是底线。第三，记忆的调用时机：什么场景该把哪些经验翻出来用。

给大家一个具体例子感受一下。一个差旅 Agent，用户第一次用的时候随口说过「经济舱就好，尽量靠过道」。三个月后它帮用户订票，要不要还记得这条偏好？应该记——这是高价值、低风险的偏好，记住它，体验立刻不一样。但假设用户某次任务里提过一句公司的预算数字，这条该不该进长期记忆？大概率不该——涉密，而且过期极快。你看，「记什么、忘什么」根本不是技术参数，是产品规则，得一条一条设计出来。

那我问一句：Agent 的记忆，是不是越多越好？

有同学犹豫了。答案是：不是。记忆塞得越满，噪声越多，判断越差；而且记的都是用户的隐私，多记一分，风险多一分。这里有第二句金句：

**记忆不是越多越好——会遗忘，才是产品设计。**

常见坑：把记忆做成「什么都记」，既贵又不安全。正确做法是给记忆设计分层：任务内的短期记忆用完即弃，跨会话的长期记忆白名单化管理。

**第三个要素：工具。**

工具是 Agent 的手和脚：搜索、计算器、数据库查询、企业系统 API。大脑再强，没有工具就还是只能答题。

产品经理管什么？第一，工具清单：给这个 Agent 配哪几个工具——注意是最小集，不是全家桶，每多一个工具，出错面就大一分。第二，权限最小化：这个 Agent 能读哪些数据、能动哪些系统，必须逐个授权，不能一上来就给它全部 API 的钥匙。第三，也是最容易忽略的：工具的描述文案。

为什么说工具的描述文案，是提示词的一部分？

因为模型是靠读工具的描述来决定「什么时候用这个工具、传什么参数」的。你写「search：搜索」，模型根本不知道什么时候该用它；你写「search：当需要查询实时信息（股价、汇率、新闻）时调用，输入为自然语言关键词」，模型就用得很准。所以写工具描述，本质上是在写提示词——这是产品经理可以直接上手、直接见效的工作，明天实操你们就会体会到。

**第四个要素：执行。**

执行，就是真正发起调用、和环境发生交互：真的下单、真的发邮件、真的改数据库。前面三个要素都在「想」，这一个在「做」。

产品经理管什么？第一，人工确认闸门：高风险动作必须停下来等用户点头。第二，回滚与补偿：做了之后发现错了，能不能撤销、怎么补救。第三，执行日志：每一步动了什么，全程留痕，出了问题能审计。

哪些动作必须有人工确认？

对，判断标准就一条：不可逆。支付、发送、删除、对外承诺——做了就收不回来的，必须有人工闸门；查询、草稿、预览这类可逆动作，可以让它放手去做。

到这里，四要素讲完了。但注意图上还有一条虚线：执行完之后，环境的结果会反馈回大脑。Agent 不是一条道跑到黑，它是「做一步、看一眼、再决定下一步」的循环。这个循环，就是我们下一节要讲的 ReAct（Reasoning + Acting，推理与行动交替）。

讲一个把四要素用对的样子。有个设计背景学员做「会议纪要助手」，她没有堆功能，只把四要素各管了一件事：规划把「听录音 → 提炼结论 → 列待办 → 生成草稿」定成四步并设了步数上限；记忆只记参会人偏好的纪要格式，不记会议内容，用完即弃；工具只给了转写和日历两个，权限都是只读加写草稿；执行里「把纪要发到公司群」这一步设成暂停加确认。她没换模型、没加功能，只是把每个要素的「产品经理管什么」写清楚了。这个例子你们记一下：四要素不是技术清单，是四张产品决策卡。

反过来看一个翻车的。另一个方案把记忆做成「所有对话全量长期保存」，工具一口气接了十几个、权限全开，执行环节没有任何人工确认，规划也没有上限。结果用户最不放心的是「它会不会把我随口说的话一直记着、还替我发出去」。注意，问题不在模型不够好，而在四要素里三处边界都没画。这类方案在评审里最容易被一句话问倒：「这件事什么时候交还给人类？」——答不上来，就说明边界没设计。

这里补一个大家最容易误解的点：四要素不是「越全越好」，而是「每个要素都要配一条刹车」。规划配步数上限，记忆配遗忘策略，工具配权限最小化，执行配人工确认。为什么？因为 Agent 和答题产品最大的不同，是它会自己往下跑——能自己跑的东西，就必须有能停下来的地方。常见误解是把这四条当成「技术参数」，其实全是产品规则，是产品经理能直接拍板、也最该拍板的东西。

面试官问「你怎么做 Agent 架构设计」，别背 Planning / Memory / Tools / Action 四个英文词。标准答法是：先说「Agent 是长着四肢的大模型」，再按四要素各给一句「产品经理管什么」——规划管步数上限、记忆管遗忘与隐私、工具管最小集与描述文案、执行管不可逆动作的人工确认，最后落到一句「边界比能力更重要」。

## 核心原理讲授 B + 案例

### 讲师话术

ReAct，两个词的缩写：Reasoning + Acting，思考和行动交替进行。完整循环是四拍：思考——我该做什么；行动——调用工具；观察——看返回结果；再思考——根据结果调整下一步。

这个循环本身不难。今天我要教你们的是一个产品经理的讲法，也是面试时的差异化答案：

**ReAct 对产品经理的意义，是把模型的思考过程摊开给用户看。**

为什么要摊开？三个理由，层层递进。

第一，信任。黑箱转圈和「正在执行第 3 步：查询航班价格」，是两种完全不同的心理体验。前者用户等 30 秒就开始焦虑，后者用户愿意等 3 分钟。可观测，是 Agent 产品信任感的第一来源。

第二，可中断。用户看得到步骤，才能在它跑偏的那一刻叫停。你想象一个 Agent 在第 7 步开始反复搜索同一个关键词——用户看得见，就能及时干预；看不见，它就把预算烧完了你才知道。

第三，可纠偏。出了错，用户和客服能定位到具体哪一步错了——是搜索词不对，还是下单参数传错。没有过程展示，badcase（坏案例）就是「它最后给我的结果是错的」，无从归因。

我讲一个反面案例。有个团队做行程规划 Agent，技术做得不错，但界面只有一个转圈的动画。内测的时候，用户平均等待 40 秒就开始重复点击、刷新，很多人直接关掉——哪怕最后结果是对的，用户也觉得「它是不是死机了」。后来他们只做了一个改动：把 ReAct 的每一步以清单形式展示出来，完成一步打一个勾。同样的技术，同样的等待时间，内测满意度完全是两个量级。你看，这不是技术改进，是产品改进——把本来就存在的思考过程，翻译给用户看。

还要补一个词：反思机制。Agent 执行失败之后，不应该傻乎乎地原样重试，而是要「想一想」——刚才哪一步出了问题，换个方式再来。这个反思本身也是模型的一次推理，产品经理要关心的是：反思几次、反思不出办法时是不是交还人类。这就又回到了步数上限和接管点。

好，那我再追问一句：把思考过程全部摊开，会不会信息过载？

问得好——所以呈现要分层：默认只展示步骤清单，一行一句；想看细节的用户，点开某一步看完整的推理和工具返回。这就是「可展开的透明」，不是「事无巨细的汇报」。这个设计，你们主项目的架构图里可以直接用。

接下来讲一个这两年工具生态里最重要的词：MCP，Model Context Protocol，模型上下文协议。

先讲它解决什么问题。一个 Agent 平台上，假设有 3 个模型、10 个工具。没有统一协议的时代，每个模型接每个工具，都要单独写一套适配——3 乘 10，30 套适配代码。每上一个新模型，重写 10 套；每上一个新工具，重写 3 套。工具生态越大，这个乘法越恐怖。

MCP 干的事，就是给所有模型和工具定一个统一的插口。模型只要实现一次 MCP 客户端，工具只要实现一次 MCP 服务端，两边即插即用。3 加 10，13 份工作就够了。M 乘 N 变成 M 加 N。

我问大家一个生活类比：这个思路你在哪儿见过？

对——USB。没有 USB 的年代，打印机一个口、鼠标一个口、键盘一个口，每个设备一种线。USB 统一之后，任何设备插上就能用。所以记住这个类比：

**MCP 就是 AI 时代的 USB 接口——工具接入从「每个都单独适配」变成「即插即用」。**

再给你们一个更贴近工作的算法。假设你们主项目要用三个工具：日历、企业数据库、邮件。没有 MCP 的做法是什么？你们选的模型厂商每家都有自己的一套调用格式，A 模型一套写法，B 模型一套写法，换模型，三个工具全部重接。有了 MCP，工具侧实现一次 MCP 服务端，任何支持协议的模型都能直接用——明天你们在扣子或 Dify 里加插件的时候，可以留意一下，添加一个工具的配置成本已经低到分钟级，这就是标准化带来的变化。

客观背景补充一句：MCP 是 Anthropic 在 2024 年 11 月发布的开放协议，之后被多家主流模型厂商和开发平台跟进支持。像扣子、Dify 这类开发平台，都在提供自己的插件与工具接入体系，MCP 正在成为跨平台通用的连接标准。这里我不展开技术细节，你们只需要站在产品视角记住一件事——

工具接入的标准化，是产品经理的新杠杆。以前接一个新工具，要评估「开发排期两周」；协议统一之后，接一个新工具的成本大幅下降，意味着你设计 Agent 时的工具选择空间变大了、试错变快了。做竞品分析和方案评审时，「这个平台工具生态怎么样、接新工具多快」，会成为你方案里的一个正式考量项。

最后 30 秒前瞻一个词：A2A，Agent-to-Agent，Agent 之间的协作协议，Google 在 2025 年发布。它想解决的是「不同家的 Agent 怎么互相沟通」。今天不展开，你们记住这个名字就行——面试聊到 Agent 生态，能提一句「工具侧有 MCP，Agent 互联侧有 A2A」，就够显专业了。

最后一个技术话题：Multi-Agent，多个 Agent 分工协同。比如一个「调研 Agent」负责搜集资料，交给「写作 Agent」成稿，再交给「审校 Agent」查错——各管一段。

听起来很美好，对吧？但我今天这一段的主要任务，是给你们泼冷水。

多 Agent 有三个隐藏成本。第一，协作协议：Agent 和 Agent 之间怎么传话？传什么格式？谁先谁后？这些本身就是新的设计对象，而且比单个 Agent 的设计更难。第二，消息损耗：A 传给 B 的每一句话，都是一次有损压缩——A 觉得说清楚了，B 理解偏了，错误就这么进来了。第三，失败传播：链条上任何一环出错，都会往下游传染，而且越往下游，越难定位是哪一环出的错。

所以，记住这个判断：

**多 Agent 是复杂度黑洞：两个 Agent 能做的事，别用五个。**

那什么时候才真的需要多 Agent？

三个信号，满足其一再考虑：任务真的可以并行，串行太慢；单个 Agent 的上下文装不下整个任务，必须分段；不同环节需要隔离的专业能力或权限。如果三个信号一个都不占，老老实实用单 Agent。

给大家一个决策顺序，也是明天课堂会反复用的：先问「单 Agent 能不能解决」，再问「要不要 Agent」，最后才问「要不要多个 Agent」。把这三个问题倒着问的人，做出来的产品一定复杂到没法维护。

技术讲完了，这一段回到产品，也回到你们自己的项目。Agent 产品经理有三道必设的闸门。

第一道：人工接管点。回顾今天开头那句话——答题的责任在你，办事的责任在它。但一个负责任的 Agent 产品，必须明确回答：

**Agent 产品经理的第一问题：这件事什么时候交还给人类？**

哪些时刻交还？三种：模型对下一步没把握的时候（置信度低）；步数或预算触顶的时候；碰到不可逆动作的时候。这三个时刻，就是你在架构图上要标注的接管点。

接管点在界面上怎么呈现？也给大家一句参考设计：接管不是「弹窗打断」，而是「暂停 + 选项」。比如执行到「即将向一批客户发送邮件」这一步，正确的做法是停下来，把收件范围、正文摘要、发送时间摆出来，给用户「确认发送」和「我要改」两个按钮——用户保有控制感，Agent 保住了效率。接管点设计得好不好，直接决定用户敢不敢把大事交给你的产品。

第二道：步数与成本上限。前面讲过了，max steps 是必填项。再补一个维度：单次任务成本上限。每一步都调工具、调模型，钱是按步累加的，上限就是你的刹车。

第三道：安全闸门。不可逆动作前强制人工确认——这是红线，不是建议。

看一个把 ReAct 用对的。某差旅助手把每一步都写成一行清单：「查航班 ✓ / 比价 ✓ / 待确认支付…」，用户想看某一步为什么这么选，点开才展开细节；遇到支付就暂停，摆出航班和总价给两个按钮。它没改模型，只是把「可展开的透明」和「暂停 + 选项」做进了界面。这个例子的可取之处是：技术一点没变，信任感是靠产品呈现挣来的——正好对上那个词，可观测性。

再看一个把多 Agent 用歪的。有个方案把一个本可以单 Agent 跑完的「资料整理 + 成稿」需求，拆成调研、写作、审校、发布、复盘五个 Agent，评审时被问「它们之间传什么格式、谁先谁后、哪一环错了怎么定位」，三个问题一个答不上来。这不是架构完整，是复杂度黑洞：每多一个 Agent，就多一次有损传话和一处失败传播的入口。记住那句决策顺序——先问单 Agent 能不能解决，别倒着问。

补一处最常见的误解：很多人把 MCP 理解成「让模型更聪明」，把多 Agent 理解成「更厉害的架构」。都不是。MCP 降的是接入成本，是杠杆不是智力；多 Agent 增的是协作成本，是负担不是能力。为什么产品经理必须分清？因为这两件事都会让方案看起来更「高级」，从而掩盖一个更该先回答的问题：这个场景到底要不要 Agent、要几个。边界就一句话——先定「要不要、要几个」，再谈「用什么协议、接几个工具」。

面试官问「ReAct / MCP / 多 Agent 你怎么看」，别逐个背定义。标准答法是三句连起来：ReAct 的产品意义是把思考摊开给用户看、换来信任与可中断；MCP 是工具的 USB 接口、M×N 变 M+N、让工具生态进选型考量；多 Agent 是复杂度黑洞、先问单 Agent 能不能解决。最后补一句决策三问，把话题收回产品判断。

## 实操演练与巡场

### 讲师话术

现在轮到你们了。打开导学案的「主项目 Agent 架构草图区」，任务分五步，一步一步来，不用一次画完：

第一步，读场景。把你上周五立项的那句话抄在纸角上——目标用户、核心场景、成功指标，先看清你要替谁办什么事。
第二步，画四框。中间一个 Agent 核心，四周四个框：规划、记忆、工具、执行。先有骨架，再填血肉。
第三步，标两样硬东西：至少一个「交还人类」的接管点，一个最大步数或成本上限的数字。这两样没有，图就不算完成。
第四步，列工具清单。写 3–5 个具体工具的名字，每个后面注明权限——只读、可写草稿、还是能对外发送。
第五步，自查。对照导学案那四条清单逐项打勾：四要素标全、接管点明确、上限标注、工具清单具体。

把你立项的那个产品画出来：中间 Agent 核心，四周四要素，另外三样东西必须有——至少一个接管点、一个步数上限、一个具体工具清单。开始。

- 走到只画了两个框的学员旁：「先别急着美化。你把『记忆』和『执行』两个框补上——执行是唯一真正动手的环节，没有它就不叫 Agent。」
- 走到画成全自动闭环的学员旁：「找一件事问自己：这一步做错了，收得回来吗？收不回来的那一步，就是你的接管点，画个三角标上去。」
- 走到没写上限的学员旁：「给它一个数字。不用精确到个位，写『最多 20 步，超出暂停交还人类』就行——有数字，说明你想过刹车。」
- 走到工具只写「调用工具」四个字的学员旁：「换成名字：日历只读、知识库只读、草稿箱可写、邮件不可直接发送。写具体，评审才问得下去。」
- 走到只有手机的学员旁：「不用打开任何工具。纸上画四个框、一个三角、一个数字，拍张照就是作品，和电脑上画的一样算数。」

巡视时我看到几个共性问题，现场纠正：有同学只画了「LLM 加工具」两个框，记忆和执行不见了——回忆一下，执行是唯一动手的环节，没有执行就不叫 Agent。还有同学的图是全自动闭环，一个交还人类的点都没有——你想让它在你的产品里替用户承担全部责任吗？现在改。

1. **卡在「画不出完整图」**：先只摆四个空框，哪怕里面暂时空着也行——先有骨架，再有血肉；填不出的那一格，正好是你课后要补的问题。
2. **卡在「不知道哪个算不可逆」**：用一句生活判断——「这动作做完，能撤回吗？」支付、发送、删除、对外承诺都撤不回，一律标接管点；查询、草稿、预览能撤回，可以放手。
3. **卡在「工具清单写不具体」**：把工具想成你打电话叫来的人，写下他的名字和「能干什么、不能干什么」，别写「调用工具」这种四个字的占位。

| 原任务 | 电脑做法 | 手机 / 平板替代动作 |
|---|---|---|
| 交互工具点节点看三段式 | 自己点「规划 / 记忆 / 工具 / 执行」节点 | 看讲师投屏，节点讲解由讲师代点；在纸质四要素笔记表填空即可 |
| 画正式架构草图 | 画图工具拖拽 | 纸上画「中间核心 + 四周四框 + 三角接管点 + 上限数字」，手写工具清单，拍照归档 |
| 填导学案电子表格 | 在线填表 | 全部纸质手写，课后拍照发群；草图自查清单在纸上逐项打勾 |
| 当堂做第 0 层术语辨析题 | 在线答题 | 讲师念题、学员举手或纸上写 A/B/C，口头核对 |
| 两两模拟（预告） | 同屏看追问卡 | 面对面口述，或用手机语音条互问互答 |

挑两张草图讲评，一张四要素齐全、一张漏了执行，不点名、只讲图。然后带全班做第 0 层术语辨析里最易错的两题：改错「Agent 的记忆越多越好」、连线「可观测性 ≠ 运行日志」。做完，把草图自查清单四项当堂打勾，没打勾的课后补。

## 面试讲解与追问防御

### 讲师话术

先说清楚面试官在考什么。今天这 8 道题分四类：**技术理解**（会不会把概念说准）、**项目深挖**（是不是真做过）、**场景设计**（有没有判断力）、**行为题**（怎么沟通、怎么权衡）。四类的共同评分逻辑只有一条：能不能判分。「更智能」「能自主决策」「架构很完整」这些词都没法判分，一律算空话。

给大家一个统一骨架，今天所有题都套它：**先给结论 → 三条踩分点 → 一个当日术语 → 一个自己项目的例子。** 为什么要有「一个当日术语」？因为它证明你这节课真学了；为什么要有「一个自己项目的例子」？因为面试官招的是做过事的人，不是背过书的人。被追问「那怎么落地」时，一律落回三样东西：接管点、步数上限、人工确认——这三样是今天全部内容的收敛点。
---

#### 题 1 · Agent 和普通 Chatbot（聊天机器人）到底有什么区别？别用「更智能」这类词
**题型：技术理解**

- **踩分点（3–4 条，可判分）**：① 交付物从「答案 / 信息」变成「结果 / 订单」；② 责任主体从用户变成产品，做错一步是真金白银的损失；③ 说出「拆任务、用工具、拿结果、担责任」中至少两个动作；④ 能举一个自己主项目的例子。
- **追问链（3 层）**：
- 第 1 层「那按你这说法，带插件的 Chatbot 算 Agent 吗？」→ 看是否自主拆解并循环执行；插件只是工具调用，不等于办事闭环。
- 第 2 层「如果这个场景只需要查一条退款政策呢？」→ 单一知识查询用检索问答即可，顺势引出题 3「什么时候不该用 Agent」。
- 第 3 层「责任主体变了，界面设计要跟着变什么？」→ 步骤可见、可中断、接管点、不可逆动作人工确认。
- **典型失败答法 + 失分原因**：「Agent 更智能、能自主决策、会自己思考。」全是无法判分的程度词，没碰交付物与责任；且「自主决策」没说边界，一追「怎么落地」就露馅，直接暴露没做过闸门设计。
- **60 秒标准答法**：「我不用『更智能』来答，因为那是程度词，不是分界线。分界线是交付物和责任主体：Chatbot 你问一句它答一句，交付的是答案，对错你自己把关；Agent 你给一个目标，它自己拆任务、调工具、把结果拿回来，做错一步是真金白银的损失，责任在产品这边。所以我做这类产品，第一件事不是选模型，是画边界——任务边界、步数上限、人工接管点。比如我主项目里『对外发送』这一步，我一定设成暂停加确认，而不是让它自己发出去。这就是从答题到办事。」
---

#### 题 2 · ReAct 是怎么工作的？为什么产品经理要关心它？
**题型：技术理解**

- **踩分点**：① 说清四拍循环（思考—行动—观察—再思考）；② 给出全称 Reasoning + Acting，推理与行动交替；③ 落点是「把思考摊开给用户看」，不是背术语；④ 说出信任 / 可中断 / 可纠偏三样中至少两样。
- **追问链（3 层）**：
- 第 1 层「摊开全部推理，会不会信息过载？」→ 分层呈现：默认步骤清单、想看细节再点开，即「可展开的透明」。
- 第 2 层「反思机制算哪一拍？要无限反思吗？」→ 失败后换方式再来的一次推理，仍受步数上限与接管点约束。
- 第 3 层「用户看不见过程会怎样？」→ 黑箱转圈、用户等不住就刷新关掉，且出了问题无从归因。
- **典型失败答法 + 失分原因**：「ReAct 就是让模型一边想一边做，是个技术框架，产品不用管。」把最值钱的差异化答案拱手让人，「产品不用管」直接暴露没意识到可观测性是信任设计。
- **60 秒标准答法**：「ReAct 全称 Reasoning + Acting，推理与行动交替，循环是四拍：思考我该做什么、行动调工具、观察返回结果、再思考调整下一步。但产品经理关心的不是循环本身，而是把它摊开给用户看。可观测性带来三样东西：用户知道它在干嘛，这是信任；跑偏了能随时叫停，这是可中断；出了错能定位到第几步，这是可纠偏。呈现上我会分层，默认只给一行一句的步骤清单，想看细节再点开，这叫可展开的透明——它不是给工程师看的 debug 界面，是 Agent 产品的信任地基。」
---

#### 题 3 · 什么时候不该用 Agent？给我三个判断信号和替代方案
**题型：场景设计**

- **踩分点**：① 明确说出三类不该用的场景（路径完全固定 / 单一知识查询 / 高风险不可逆且要全自动）；② 每类给替代方案（固定工作流、检索问答、AI 建议 + 人类拍板）；③ 给出决策三问的顺序；④ 提到「可靠性优先于自动化率」。
- **追问链（3 层）**：
- 第 1 层「业务方就要 100% 全自动，你怎么说服？」→ 全自动的隐含代价是「错误也全自动」，接管点不是能力不足。
- 第 2 层「那 Agent 只做前半段算不算半成品？」→ 不算，人机分工本来就是设计，不是能力打折。
- 第 3 层「你怎么度量『不该上 Agent』？」→ 看路径是否可变、是否要自主拆步骤、是否涉及不可逆动作。
- **典型失败答法 + 失分原因**：「Agent 这么强，什么场景都能上，就看模型够不够好。」没有判断框架，把选型问题甩给模型能力；面试官要的正是产品判断力，这句直接判「没做过」。
- **60 秒标准答法**：「三类场景我会先踩刹车。第一，路径完全固定、每周重复的事，用固定工作流更稳更便宜，不必让 Agent 临场拆；第二，只查一条政策、一个数据，用检索问答就够；第三，涉及支付、发送、删除这类不可逆动作，我不做端到端全自动，而是拆成『分析 / 建议 / 决策』三段，AI 出建议、人类一键拍板。我的决策顺序是三问：先问单 Agent 能不能解决，再问要不要 Agent，最后才问要不要多个。跟业务方我会讲一句实话——全自动的隐含代价是错误也全自动，接管点不是能力不足，是把责任留在该在的位置，可靠性优先于自动化率。」
---

#### 题 4 · 多 Agent 的复杂度怎么控？你们项目为什么用 / 不用多 Agent？
**题型：项目深挖**

- **踩分点**：① 先给「默认不用」的结论；② 说出三个隐藏成本（协作协议、消息损耗、失败传播）；③ 说出真该拆的三个信号（可并行 / 上下文装不下 / 专业或权限需隔离）；④ 落到自己主项目给出具体判断。
- **追问链（3 层）**：
- 第 1 层「如果一定要拆，你先定哪三件事？」→ 传话格式、先后顺序、失败定位与兜底。
- 第 2 层「两个 Agent 能做的事拆成五个，问题出在哪？」→ 每多一环多一次有损压缩，越往下游越难定位。
- 第 3 层「单 Agent 上下文不够怎么办？」→ 先做记忆分层与摘要，别急着拆大脑。
- **典型失败答法 + 失分原因**：「我们项目拆了五个 Agent，调研、写作、审校、发布、复盘各管一段，显得架构很完整。」把「拆得多」当能力，正踩复杂度黑洞；没提成本、没提「先问单 Agent」，面试官一追协作协议就问倒。
- **60 秒标准答法**：「我的默认答案是不用。多 Agent 是复杂度黑洞：两个 Agent 能做的事，别用五个。它多出三个隐藏成本——Agent 之间怎么传话的协作协议、每传一次都有损耗的消息压缩、还有一环出错往下游传染且越往下游越难定位的失败传播。只有三个信号占其一我才考虑拆：任务真能并行、单 Agent 上下文真装不下、不同环节的专业能力或权限真需要隔离。我主项目是路径串行、上下文也塞得下的场景，所以用单 Agent，把省下来的复杂度花在接管点和步数上限上。真要拆，我先定传话格式、先后顺序和失败兜底这三件事。」
---

#### 题 5 · Agent 四要素里，哪一个最容易被产品经理漏掉？为什么？
**题型：技术理解**

- **踩分点**：① 给出明确答案（执行或记忆，二选一但须自圆其说）；② 说出四要素名称；③ 解释漏掉的具体后果；④ 给一条可落地的补法。
- **追问链（2 层）**：
- 第 1 层「补上之后怎么验收？」→ 草图四框齐全 + 一张不可逆动作清单。
- 第 2 层「执行和工具调用是不是一回事？」→ 不是：工具是接上能力，执行是真正动手发起调用。
- **典型失败答法 + 失分原因**：「都挺重要的，一个都不能少。」没判断、没优先级，等于没答；面试官要的是踩过坑的经验，不是和稀泥。
- **60 秒标准答法**：「最容易漏的是执行。四要素是规划、记忆、工具、执行，大家画架构图常画成『大模型 + 工具』两个框，因为觉得调了工具就算办事了。但工具只是接上能力，执行是真正发起调用、跟环境发生交互的那一步——没有它，前面三个要素都在『想』，产品就还是答题。漏了它的后果很具体：不可逆动作没人设人工确认闸门、没有回滚与补偿、也没有执行日志留痕，出了问题无从审计。我的补法很土但有效：草图强制四框齐全，再单独列一张『支付 / 发送 / 删除 / 对外承诺』清单，逐条写明确认方式。」
---

#### 题 6 · 用户让 Agent 帮他订机票并付款，你怎么设计接管点？
**题型：场景设计**

- **踩分点**：① 说出三种交还时刻（置信度低 / 预算触顶 / 不可逆动作前）；② 接管呈现用「暂停 + 选项」而非弹窗打断；③ 配合最大步数与单任务成本上限；④ 有执行日志留痕、可回滚补偿。
- **追问链（3 层）**：
- 第 1 层「上限设多少？凭什么？」→ 给数字与依据（任务复杂度、单步成本），且「超限即暂停交还人类」。
- 第 2 层「用户嫌老确认、太烦怎么办？」→ 自主性按动作可逆性分档：查询草稿放手，不可逆才拦。
- 第 3 层「如果它订错城市了怎么补救？」→ 回滚与补偿、人工接管后重跑，靠执行日志定位。
- **典型失败答法 + 失分原因**：「全部让它自动跑完，最后给用户一个订单确认页就行。」把不可逆动作放到事后确认，钱已经付了；也没有「暂停 + 选项」的控制感设计。
- **60 秒标准答法**：「我会把付款这一步设成硬接管点。三种时刻必须交还人类：模型对下一步没把握、步数或预算触顶、碰到不可逆动作——付款正属于第三种。呈现上不是弹窗打断，而是『暂停 + 选项』：把航班、总价、乘机人摆出来，给『确认支付』和『我要改』两个按钮，用户保有控制感。前面还要配两道闸：最大步数和单任务成本上限，超了就暂停交还，不是让它无限重试。查询航班、比价这类可逆动作可以放手跑，支付、出票、对外承诺必须停下来。全程执行日志留痕，订错了能回滚、能补偿。一句话，自主性要按动作可逆性分档，不能一刀切全自动。」
---

#### 题 7 · MCP 到底是什么？它对产品经理意味着什么？
**题型：技术理解**

- **踩分点**：① 全称 Model Context Protocol，模型上下文协议；② 说清 M×N → M+N 的适配问题；③ 给出 USB 生活类比；④ 落到「工具接入成本下降、工具生态成为选型考量」这个产品结论。
- **追问链（3 层）**：
- 第 1 层「MCP 是某个工具或插件吗？」→ 不是，是接口标准，不是工具本身。
- 第 2 层「接新工具便宜了，你会因此多接吗？」→ 不会，仍守最小工具集与权限最小化。
- 第 3 层「Agent 之间互联呢？」→ 工具侧有 MCP、Agent 互联侧有 A2A（Agent-to-Agent），一句带过不展开。
- **典型失败答法 + 失分原因**：「MCP 是一个能让 Agent 变聪明的协议，底层通信格式很复杂。」既说错定位（不是让模型变聪明），又钻进协议实现细节；咱们学员零编程，面试官要的是产品含义，不是规范课。
- **60 秒标准答法**：「MCP 全称 Model Context Protocol，模型上下文协议，Anthropic 在 2024 年 11 月发布的开放标准。它解决的不是『让模型更聪明』，而是适配爆炸：没有统一协议时，M 个模型接 N 个工具要写 M×N 套适配；统一之后模型实现一次客户端、工具实现一次服务端，M+N 份就够。类比就是 AI 时代的 USB 接口，以前每个设备一种线，现在即插即用。对产品经理的意义是杠杆：接一个新工具的成本大幅下降，设计方案时工具选择空间变大、试错变快，『这个平台工具生态怎么样、接新工具多快』会正式进选型考量。但便宜不等于多接，最小工具集和权限最小化我照样守。聊生态时补一句工具侧有 MCP、Agent 互联侧有 A2A，就够了。」
---

#### 题 8 · 讲一次你判断「这里不该上 Agent」的经历，或你怎么向业务方解释不能全自动
**题型：行为题**

- **踩分点**：① 有具体场景与明确结论；② 用了「路径固定 / 单一查询 / 不可逆」任一框架；③ 说的是沟通话术而不是硬顶；④ 有做法与复盘（只讲做法，不编效果数字）。
- **追问链（3 层）**：
- 第 1 层「业务方不服，拿别家全自动产品压你呢？」→ 回到责任主体与不可逆动作，不比功能比风险。
- 第 2 层「后来有没有部分放开自动化？」→ 有，按可逆性分档逐步放，查询草稿先放。
- 第 3 层「如果重来你会改哪一步？」→ 更早把接管点写进第一版需求，而不是上线后补。
- **典型失败答法 + 失分原因**：「我跟他们说技术做不到，所以先不做。」把产品判断包装成技术限制，既不准也显得没有话语权，且没给折中方案。
- **60 秒标准答法**：「我主项目里有个『自动分析数据并直接调整投放预算』的诉求，业务方一开始要全自动。我没说技术做不到，而是先把任务拆成三段给他看：数据分析是固定的、建议生成可以用 AI、真正改预算是不可逆动作、动的是真金白银。所以我给的折中是『AI 建议、人类拍板』——Agent 只出分析和建议，运营一键确认才执行。沟通时我用了一句话：全自动的隐含代价是错误也全自动，接管点不是能力不足，是把责任留在该在的位置。后来我们按动作可逆性分档，查询和草稿放手跑，涉及钱和对外发送的一律暂停确认。复盘我记了一条：接管点要写进第一版需求，别等上线后补。」

## 附：不懂技术也能问出口的 3 个问题（学员与研发对话专用）

**问题一：「这个 Agent 一次任务最多走多少步、最多花多少钱？上限设在哪？」**
- 什么时候问：看任何 Agent 方案时，先要这两个数。
- 为什么好：没有步数上限的 Agent 是在拿用户的 token 赌运气——要得到出这两个数的产品经理，面试官都知道你做过。

**问题二：「哪些动作在执行前必须停下来等用户确认？」**
- 什么时候问：画产品流程图的时候，跟着「支付、发送、删除、对外承诺」一起问。
- 为什么好：判断标准就一条——不可逆的动作必须有人工闸门；这是红线意识，不是技术细节。

**问题三：「如果它跑偏了，用户在第几步能看到、能叫停？」**
- 什么时候问：评审任何「全自动」方案时。
- 为什么好：可观测带来信任、可中断带来安全感；这一问逼着方案把思考过程摊开给用户看。

## 补充素材

### 理论知识手册 · 定义、架构与工具调用

你们先记住一个基本判断：普通的 LLM 只能「说」，不能「做」，而 Agent 等于 Plan 加 Tool 加 Memory 加 Act。接着看 Lilian Weng 架构，出自《LLM Powered Autonomous Agents》，也叫「螃蟹图」：Agent，也就是 LLM，居中当大脑，四周分别是 Planning 规划、Memory 记忆、Tools 工具、Action 行动；它的执行链是规划、调工具、观察、纠错、完成。这里有个关键结论你们一定要记牢：模型并不会真的执行代码，它只是输出一段结构化文字，真正解析并执行的是框架代码，所以叫「模型只负责说，代码负责做」。再说工具调用，一共六步：System Prompt 先告知有哪些工具，接着用户提问，模型输出 JSON，注意这只是文字预测、不是真的调用，然后框架解析并执行，把 tool_result 注回上下文，最后给出回答。Function Calling 就是这样，用户看到的只有 1 条回复，背后其实跑着 5 条 API 消息。落到能力上，你们要懂模型和框架的边界，能点破本质、说清框架怎么接管、结果怎么注回，也能回答责任问题。

### 理论知识手册 · ReAct、故障模式与脚手架

- **概念 / 术语**：**ReAct 循环**「思考 → 行动 → 观察，循环往复」；Reasoning + Acting，Agent 靠循环完成任务，一问一答只是其中一轮。
- **关键结论**：「如果模型对参数格式不了解，它会反复猜测，卡在同一个地方打转」，这正是脚手架的价值。
- **框架 / 模型**：五种故障模式——参数格式错误、幻觉工具、无限递归、信息不足、API 异常；对应防护——参数校验、工具验证、循环检测、主动提问机制、超时兜底。
- **概念 / 术语**：**Skill = 流程说明 + 工具调用指引**，「Skill 本质是经验封装」，写好 Skill 就是「把你的经验变成 AI 的能力」；一份 SKILL.md = 一项技能，字段含技能名称、触发条件、执行步骤、允许工具、安全约束；「条件不满足时 Skill 静默退出」。
- **关键结论**：差的循环是「每做一步就停下来确认 → 多轮对话 → Token 费用高」，好的循环是「出发前规划好 → 一次执行 → Token 费用低」。
- **关键结论**：「没有脚手架的 Agent 在生产环境不可靠」。

| 脚手架 5 大能力 | 原文 |
|-|-|
| 超时与重试 | 工具调用设 timeout + 指数退避重试；优雅地返回当前进度 |
| 迭代上限 | max_iterations 防止死循环 |
| 参数校验 | JSON Schema 拦截非法参数；返回格式化错误让模型自我纠正 |
| 检查点恢复 | 失败不从头来，从最近检查点恢复 |
| 全链路记录 | 生产环境 90% 的问题靠日志排查 |

- **框架 / 模型**：五道护栏——迭代上限、输出截断、超时控制、中断恢复、上下文急救，「没有护栏的 Agent = 没有刹车的跑车」；可观测性含事件流可视化、Token 追踪，「每个事件类型都是一个产品决策点」。

### 理论知识手册 · 多 Agent、权限与责任

大家先看多 Agent 怎么分工：主 Agent 拆任务，子 Agent 各司其职，最后汇总交付；只读任务并行加速，写入任务串行保安全。这里要注意，如果同时有两个写入 Agent，可能互相覆盖代码，所以原则是「可逆操作自动化，不可逆操作要确认」。对你们的能力要求是，能回答「什么时候需要多 Agent？」，能核算子 Agent 的 Token 成本，还能回答责任问题。
