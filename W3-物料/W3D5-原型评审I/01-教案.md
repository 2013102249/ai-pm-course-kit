## 二、教学目标（可测量）

1. 能按「用户价值 / 技术可行 / 体验」三维给其他小组原型打分，每组至少写出 1 条有依据的追问和 1 条一句话建议（对应课堂评审记录表，课后回收检查）。
2. 本组能在 3 分钟内完成结构化演示：问题 → 方案 → 演示 → 下一步，四段齐全不超时。
3. 能产出 V1.5 迭代计划：推翻项 ≥1 条、本周改 ≤3 条、每条带具体时间点（对应导学案迭代计划模板）。

## 三、教学重难点

- **重点**：三维点评法的产品视角——用户价值、技术可行、体验三个维度各自的判断标准与追问清单，这是学员未来带团队评审、面试讲项目的通用方法论。
- **难点一**：学员互评易打「礼貌分」（清一色 4–5 分、追问空白），不敢提真问题。应对：规则强制 + 记录表回收检查。
- **难点二**：迭代计划易写成愿望清单（罗列 10 条全要改、无取舍、无时间点）。应对：硬性要求推翻项 ≥1 条、本周改 ≤3 条。

## 五、教学步骤与时间拆分

| 时间 | 环节 | 教学内容 | 教学方法 | 对应产出 |
|---|---|---|---|---|
| 0–10 min | 规则宣讲 | 评审规则（每组 3 分钟演示 + 4 分钟质询 + 3 分钟点评）；三维点评法示范 1 轮；往届问题集锦「丑话说在前面」 | 讲授 + 示范 | — |
| 10–65 min | 分组评审（核心） | 以 5 组为基准：每组 10 分钟（3+4+3），共 50 分钟，余 5 分钟机动；打分与追问记录同步进行，不占口播时间 | 小组演示 + 全组质询 + 讲师三维点评 | 每人评审记录表填满 4 份 |
| 65–85 min | 迭代清单清算 | 各组按均分与追问填迭代计划（保留 / 推翻 / 本周改）；讲师逐组 2 分钟快检：推翻项有没有、时间点真不真 | 小组填写 + 讲师巡检 | V1.5 迭代计划初稿 |
| 85–90 min | 收尾与作业 | 里程碑 ② 确认口径、周末综合输出清单、预告 W4 需求分析 | 讲授 | — |

**组数弹性规则**：4 组时每组延至 12 分钟（演示 3 + 质询 5 + 点评 4）；6 组时每组压至 8 分钟（演示 3 + 质询 3 + 点评 2），讲师点评只讲「最该推翻的一条」。

## 六、课堂提问设计（7 问，附预设答案）

| # | 提问 | 提问时机 | 预设答案 / 引导方向 |
|---|---|---|---|
| 1 | 「你们这个产品，谁在用？解决他什么问题？」 | 每组质询第 1 问 | 必须答出具体人群 + 高频场景；若答「所有人都能用」，追问「V1 只先服务谁」——考察取舍意识 |
| 2 | 「用户现在没有你的产品，是怎么解决这个问题的？」 | 价值维度追问 | 预设：Excel / 人工 / 现有工具；答不出 = 价值假设未验证，明确告知下周 W4 用户访谈要解决的就是它 |
| 3 | 「这个功能的数据从哪来？」 | 可行维度追问 | 预设：列得出具体数据源与获取方式；若答「先爬了再说」，提示合规风险与稳定性风险（呼应 W2 数据意识） |
| 4 | 「这个能力是调现成 API 还是自研？多久能做出来？」 | 可行维度追问 | 预设：多数应答「调 API + 提示词 + 工作流编排」；估时按「天」计而非按「月」计——学员是产品经理不是算法团队 |
| 5 | 「第一次用这个产品的人，打开页面会不会懵？」 | 体验维度追问 | 预设：有引导语 / 默认值 / 示例输入；三样都没有 = 体验维度打 2 分以下 |
| 6 | 「模型答错了怎么办？用户能发现它错了吗？」 | 体验维度追问 | 预设：有兜底话术 + 溯源引用；直接回扣 W3D3 知识库三要素（更新 / 权限 / 溯源） |
| 7 | 「这版你自己最想推翻的是什么？」 | 迭代清算环节 | 预设：至少说出 1 条；答「都想保留」= 没有取舍，讲师代问「如果只能留一半功能，砍哪半」 |

## 七、板书要点

```
三维点评法 = 用户价值 × 技术可行 × 体验

价值三问：谁在用 / 解决什么 / 现在怎么解决
可行三问：数据从哪来 / 调什么能力 / 多久能做
体验两问：第一次用会不会懵 / 错了怎么办

金句：原型是拿来被推翻的——被推翻得越早，改起来越便宜
迭代计划 = 保留 + 推翻 + 本周改（每条带时间点）
```

## 八、讲师点评示范摘要（完整逐字稿见 02-讲课稿）

| 示例 | 原型表现 | 点评结论 |
|---|---|---|
| 反例示范 | 架构图把界面截图加箭头拼成「功能清单」，无四要素标注；工作流只在 Demo 数据下跑通 | 三维得分：价值 3 / 可行 2 / 体验 2；最该推翻的一条：把「功能展示」改成「一条真实任务从头跑到尾」 |
| 正例示范 | 演示从真实用户问题出发，工作流现场跑通，知识库答错时主动展示兜底与溯源 | 三维得分：价值 4 / 可行 4 / 体验 4；保留判断依据 + 本周补权限设计，迭代计划可作范本 |

## 九、学员易错点预判与应对

| 易错点 | 表现 | 应对 |
|---|---|---|
| 演示超时或变成产品宣讲 | 只放彩排过的亮点，不回应质询；3 分钟讲不完 | 计时器硬切，宣讲话术：「超时部分留给质询，那 4 分钟价值更高」；演示脚本四段式提前收上来检查 |
| 互评打礼貌分 | 全场 4–5 分，追问记录空白 | 规则宣讲明示：每组必须写 1 条追问 + 1 条一句话建议；记录表未填满 4 份不得离场；「全员满分 = 评审失败」 |
| 点评只说主观感受 | 「我觉得不好用」「界面有点丑」，无依据 | 三维追问清单兜底：按问题清单问，不问感觉；「有依据的追问比正确的答案值钱」 |
| 迭代计划写成愿望清单 | 罗列 10 条全要改，无推翻项、无时间点 | 清算环节硬性要求：推翻项 ≥1、本周改 ≤3、每条带具体日期；讲师逐组快检不达标者当场砍 |
| 演示设备故障慌场 | Dify 打不开、网络超时，演示者卡住 | 预习清单强制要求截图备份或录屏兜底；故障预案话术：「正好验证了一条体验原则——线上必有兜底」 |
| 把评审当「比谁做得好」 | 组间气氛紧张，被打低分情绪化 | 宣讲口径：评的是原型不是人；「今天被推翻的每一条，都是面试时能讲出的取舍故事」 |
