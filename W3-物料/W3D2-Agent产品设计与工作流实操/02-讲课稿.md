# 讲课稿 · W3 周二《Agent 产品设计与工作流实操》（完整逐字稿）

## 术语精讲与零层入口

**时间轴**

大家好，今天这一整天：术语、原理 A、原理 B、实操、面试、验收。别被时长吓到——主线只有一件事：把你主项目的工作流原型搭出来，再把它讲成面试能得分的话。

先花 30 秒补零层。昨天讲了 Agent 四要素——规划、记忆、工具、执行，还有 ReAct 循环（Reasoning + Acting，推理与行动循环）：思考、行动、观察，转圈直到完成任务。完全没接触过技术的同学，讲术语那段跟着我走一遍就够了，课后可以再补 `W1-物料/W1D2-大模型原理通识/00-技术零层.md`。齐了，往下走。

为什么先讲术语？因为今天所有争论——「这需求做 Agent 还是工作流」「失败了怎么办」「要不要上多 Agent」——输赢都在几个词上。词分不清，方案就一定说不清。下面 12 个词，每个给五样东西：一句话定义、生活类比、易混辨析、面试说法、术语卡链接。抄进导学案《术语自测表》。

**术语 1 · 工作流（Workflow）**
- 一句话定义：步骤与顺序预先定死、照着固定路径跑的流程。
- 生活类比：照菜谱做菜，先热锅、再下油、再下菜，顺序写死，换个人做也一个味。
- 易混辨析：最易和 Agent 混——工作流是路径事先画得出来的；别把「能自动跑」一律叫 Agent。
- 面试说法：「我先用三刻度尺量，能画出完整流程图的，就做成固定工作流。」
- 术语卡：`03-配图素材/术语卡/工作流`（见 05-配图清单，待制）

**术语 2 · Agent（智能体，又译代理）**
- 一句话定义：只给目标、由模型自主规划路径去完成的任务形态。
- 生活类比：派一个靠谱同事出差，只说「把事办妥」，路线他自己定。
- 易混辨析：最易被当成「工作流的升级版」——它不是更聪明，是拿可控性换灵活性；和工作流的区别是「谁决定下一步」，不是「难不难」。
- 面试说法：「Agent 用自主性换灵活性，我不会为路径可预测的任务上 Agent。」
- 术语卡：`03-配图素材/术语卡/Agent智能体`（见 05-配图清单，待制）

**术语 3 · 三刻度尺**
- 一句话定义：判断用 Agent 还是工作流的三个维度合称。
- 生活类比：买鞋量脚长、脚宽、脚背高三个数，不是只看「好不好看」。
- 易混辨析：最易被简化成「看任务复不复杂」——必须三维一起量：任务确定性、步骤数、容错要求。
- 面试说法：「我先量确定性、步骤数、容错要求，三维都指向路径不定才考虑 Agent。」
- 术语卡：`03-配图素材/术语卡/三刻度尺`（见 05-配图清单，待制）

**术语 4 · 确定性（Determinism）**
- 一句话定义：输入相同、步骤与输出可预期、可复现的程度。
- 生活类比：自动售货机投币必出同一款饮料，不会今天可乐明天矿泉水。
- 易混辨析：最易和「准确率」混——确定性说的是路径可预期，不是结果一定对。
- 面试说法：「能用工作流解决的事，别用 Agent——确定性是产品的好朋友。」
- 术语卡：`03-配图素材/术语卡/确定性`（见 05-配图清单，待制）

**术语 5 · 容错（Fault Tolerance）**
- 一句话定义：出错代价高低，以及允许多轮试错的程度。
- 生活类比：草稿纸写错能撕掉重来，签好的合同写错不能撕——代价不同。
- 易混辨析：最易和「兜底」混——容错是判断「错得起吗」的尺度，兜底是错之后的具体动作。
- 面试说法：「涉及钱、信任、不可逆操作就是低容错，走工作流加人工把关。」
- 术语卡：`03-配图素材/术语卡/容错`（见 05-配图清单，待制）

**术语 6 · 人机协同（Human-in-the-loop，人在回路）**
- 一句话定义：把人安排在流程关键节点参与判断与兜底的设计。
- 生活类比：自助结账机旁边总有收银员，机器扫码、人处理异常。
- 易混辨析：最易和「人工确认」混——人机协同是整体分工，人工确认只是其中一种接管动作。
- 面试说法：「我不是全自动也不是全人工，而是在高风险点上设人机协同。」
- 术语卡：`03-配图素材/术语卡/人机协同`（见 05-配图清单，待制）

**术语 7 · 人工确认（Human Approval，审批型接管点）**
- 一句话定义：高风险动作执行前，展示依据并等人一键确认。
- 生活类比：网银转账前弹窗「收款人、金额」，让你再按一次确认。
- 易混辨析：最易和「转人工」混——人工确认是事前拦一道，转人工是事后接盘，时点正好相反。
- 面试说法：「退款、发邮件、删数据这类不可逆操作，我一定加执行前人工确认。」
- 术语卡：`03-配图素材/术语卡/人工确认`（见 05-配图清单，待制）

**术语 8 · 兜底（Fallback）**
- 一句话定义：主路径失败后，仍能让用户得到明确结果的备用设计。
- 生活类比：招牌菜卖完了，服务员递上备选菜单并说清楚，而不是让你干等。
- 易混辨析：最易和「失败重试」混——重试是同一种办法再来一次，兜底是换一条路；兜底是总称，三件套是它的做法。
- 面试说法：「每个节点我都会问：失败之后，用户看到的最后一条消息是什么。」
- 术语卡：`03-配图素材/术语卡/兜底`（见 05-配图清单，待制）

**术语 9 · 节点（Node）**
- 一句话定义：工作流里承担一步处理的最小单元，如开始、LLM、输出。
- 生活类比：流水线上的工位，每个工位只做一道工序。
- 易混辨析：最易和「分支」混——节点是做事的点，分支是决定往哪走的岔路。
- 面试说法：「我把它拆成开始、LLM、工具、条件分支、输出五类节点。」
- 术语卡：`03-配图素材/术语卡/节点`（见 05-配图清单，待制）

**术语 10 · 分支（Branch，条件分支）**
- 一句话定义：按条件把流程引向不同路径的判断节点。
- 生活类比：高速路岔口，看指示牌决定往左还是往右。
- 易混辨析：最易和「失败分支」混——条件分支按业务条件走正常路，失败分支专门接异常；两条都要画，不能只画一条。
- 面试说法：「主链路之外我必留一条失败分支，异常输入不崩才算 V1。」
- 术语卡：`03-配图素材/术语卡/分支`（见 05-配图清单，待制）

**术语 11 · 失败重试（Retry）**
- 一句话定义：瞬时失败后自动再执行一到两次，前提是幂等。
- 生活类比：电话没打通，隔几秒再拨一次，而不是立刻换个人。
- 易混辨析：最易和「降级」混——重试治瞬时抖动，降级治持续不可用；顺序先重试、再降级，不能反。
- 面试说法：「重试管超时抖动，但要先问一句：重试会不会重复扣款、重复发消息？」
- 术语卡：`03-配图素材/术语卡/失败重试`（见 05-配图清单，待制）

**术语 12 · 边界条件（Edge Case，边界输入）**
- 一句话定义：超长、空值、无关问题等非常规输入及其处理。
- 生活类比：电梯限载，偏偏来了超宽货物或一窝蜂挤进人——得有个说法。
- 易混辨析：最易和「异常」混——边界条件是输入端的极端取值，异常是链路中途的失败；测运行三类输入（正常 / 边界 / 异常）都要覆盖。
- 面试说法：「验收必须跑正常、边界、异常三类输入，只跑正常不算完成。」
- 术语卡：`03-配图素材/术语卡/边界条件`（见 05-配图清单，待制）

好，12 个词过完了。现在做**重点辨析：Agent vs 工作流**。我把最容易说错的话摆出来，你们判断对错。

第一句：「Agent 是工作流的高级版，任务难就上 Agent。」——错。难点在「路径能不能预先定义」，不在难度。一个很难但规则确定的报销审核，照样是工作流。第二句：「工作流没有智能，Agent 才有智能。」——错。工作流里可以有 LLM（Large Language Model，大语言模型）节点，智能不智能和形态无关。第三句：「Agent 更灵活，所以什么时候都更好。」——错。灵活是用可控性换的，出错代价高的地方换不起。

记住这个对照，六组易混一起收：

| 别再混 | 正确分法 |
|---|---|
| Agent / 工作流 | 谁决定下一步：模型自主 / 路径预定义 |
| 确定性 / 准确率 | 路径可预期 / 结果对不对 |
| 容错 / 兜底 | 尺子（错得起吗）/ 动作（错后怎么办） |
| 人工确认 / 转人工 | 事前拦截 / 事后接盘 |
| 节点 / 分支 | 做事的工位 / 选路的岔口 |
| 失败重试 / 降级 | 治瞬时抖动 / 治持续不可用 |

做错的别急着改答案，先说出「我把哪两个词混了」——说得出混在哪，就真分清了。

讲原理这段收成一句：**能用工作流解决的事，别用 Agent——确定性是产品的好朋友。** 这句话讲核心原理 A 那会儿会展开，到面试讲解那部分会变成你的面试答案。

## 核心原理讲授 A

**时间轴**

上课先抛一个两难案例：同样是「帮用户安排出差」，为什么有的产品做成 Agent，让模型自己规划；有的产品做成固定流程，一步步点下一步？

有同学说到自由度，有同学说到可控——都对，但都不完整。今天第一个任务，就是把这个「感觉」变成一把可以量化的尺子。

这就是一条最典型的工作流：五个节点，一条主链路，每一步做什么、输入输出是什么，事先全部定死。而 Agent 呢，只有一个起点和一个目标，中间怎么走，模型自己决定。

那产品经理怎么选？三个维度，一个一个过。

**第一维，任务确定性。** 问自己一个问题：这个任务的流程图，你画得出来吗？画得出、步骤和顺序都能预先定义——用工作流。画不出、路径要模型现场规划——才考虑 Agent。

**第二维，步骤数。** 数得出来的，常见三到八步，固定有限——工作流。数不出来、随输入动态伸缩的——Agent。

**第三维，容错要求。** 出错的代价是什么？如果是钱、信任、不可逆操作，低容错，用工作流，而且要加人工把关。如果是可以重来、试错成本低的事，Agent 的多轮自我修正反而是优势。

用这把尺子判断：让 AI 自由规划一次旅行行程可以放手，为什么让它审核报销单就不行？

对——行程错了代价低，重跑就是；报销涉及钱和合规，错一步有真实损失。这就是容错维度在说话。

好，现场快判四个场景，我说场景，你们喊答案。

每天定时抓取五个指定网站新闻，摘要后发邮件——工作流，步骤固定可数。用户一句话「帮我安排下周去上海出差」，要查日程、订票、订酒店、写行程——Agent，步骤数不定，路径依赖用户日程。客服工单按固定字段分类打标、路由到对应团队——工作流，规则明确，要求稳定可审计。开放式「帮我调研一个竞品并写分析报告」——Agent，子任务要动态拆解，事先无法穷举。

把这四题的判断逻辑收成一句话，今天最重要的一句：**能用工作流解决的事，别用 Agent——确定性是产品的好朋友。** 面试被问「什么场景该用 Agent」，先反问确定性，你就赢了一半。

**正面案例（新增）**。某企业的费用报销审核：要识别发票真伪、核对标准、匹配预算科目、判断是否超标，规则很细、很「难」。设计背景学员第一反应是「这么复杂，上 Agent」。但用尺子一量：流程图画得出（四步固定）、步骤数得清、出错代价是钱和合规（低容错）——三维全部指向工作流。最后做成固定工作流 + 超标单据人工确认，结果稳定、可审计、可回溯。**难，不等于路径不定。**

**反面案例（新增）**。另一个团队把「客服工单按四类打标路由」做成了 Agent，理由是「以后好扩展」。上线后同一张工单两次分类结果不一致，路由到不同团队，运营无法对账。复盘一句话：**为了一个还没发生的灵活性，先丢掉了确定的可控性。** 这就是讲术语那段说的「别把 Agent 当升级版」。

**「为什么 / 边界 / 常见误解」深化**。为什么是这三把尺子，不是别的？因为产品经理真正要交出去的是「可承诺的结果」：确定性回答「能不能画出来」，步骤数回答「能不能数完」，容错回答「错了赔不赔得起」——分别对应可设计、可预估、可负责。边界在哪？三刻度尺是**首选判断**，不是永久判决：业务规则变了，能穷举就扩分支，穷举不了再重评 Agent。常见误解有三个：一是「Agent 更高级」，二是「工作流不含智能」，三是「一次选定不用改」——今天先把前两个破掉，第三个在实操演练那段用失败分支、到面试追问那部分用追问链补。

**这段在面试里怎么答**：被问「这个需求做 Agent 还是工作流」，别急着选。先说「我用三刻度尺量：确定性、步骤数、容错要求」，再逐维给结论，最后补一句风险提示「Agent 是用可控性换灵活性，出错代价高的环节我会保留工作流和人工确认」。给框架、给判断、给风险，三层齐全就是高分。

## 核心原理讲授 B + 案例

**时间轴**

选好了形态，下一个问题：哪些环节交给机器，哪些环节留给人？

人机接管点分三类，按时间轴记。

**第一类，审批型，事前。** 高风险、不可逆操作执行之前——对外发邮件、下单付款、删除数据。产品上要展示「AI 准备做什么、依据是什么」，人一键确认或修改。

如果让 Agent 直接给用户发退款，你会在哪个点设人工接管？

对，审批型：执行前展示金额和依据，人工确认；金额超阈值强制人审。

**第二类，纠错型，事中。** 模型输出置信度低、两次输出不一致的时候，转人工复核队列。设定一个置信度阈值，低于它就走人。

**第三类，兜底型，事后。** 重试和降级都失败了，转人工。注意一个细节：转人工必须携带完整上下文，不能让用户把问题重新描述一遍——那是最伤体验的一刀。

设计原则一句话：接管成本要对冲风险损失。每个接管点都要回答三个问题：人工来了看什么、能改什么、改完流程怎么继续。

再说失败兜底，三件套，顺序不能乱。

**第一件，重试，管瞬时失败。** 超时、网络抖动、限流，自动重试一到两次，前提是节点幂等——重跑不产生副作用。

**第二件，降级，管持续失败。** 主模型、主工具持续不可用，切备用模型、退化为简化逻辑、返回缓存结果，或者礼貌拒答，但要明确告知「结果可能不完整」。

**第三件，转人工，是最终出口。** 前两件都失败，或涉及高风险决策，生成工单，带上对话上下文和已执行步骤，承诺响应时限。

现在讲一个反面案例。某团队做了一个客服工作流：用户提问，LLM 节点理解意图，工具节点查订单系统，输出节点回复。上线第一天跑得挺好。第三天，订单系统升级，接口超时。工作流里没有失败分支——工具节点一挂，整条链路中断，用户端的表现是：无限转圈。当天下午投诉翻倍，晚上产品被紧急下线。复盘报告就一句话：**我们设计了所有顺利的路径，没有设计任何一条不顺利的。**

工具调用超时，自动重试两次还失败，产品上用户应该看到什么？

对——降级或转人工，给明确反馈，不能无限转圈。

记住这句：**兜底设计不是技术问题，是产品承诺——用户不在乎错在哪个节点，只在乎坏了之后谁负责。**

**正面案例（新增）**。同样是退款场景，另一版设计把三型接管点全落了位：金额超阈值走审批型人工确认；LLM 意图理解置信度低于阈值进纠错型复核队列；订单系统连续超时，先重试、再降级为「已创建人工工单，结果可能不完整」、最后兜底型转人工，工单带着对话记录和已执行步骤。用户每一步都看得到明确反馈，转过去不用重新讲一遍。**接管点不是加个按钮，是给每个失败都写好了下一句台词。**

**反面案例（新增）**。还有一版给「自动退款」节点加了重试，但没做幂等：接口超时后重试两次，同一笔订单退了两次钱。复盘一句话：**重试能救瞬时失败，但救不了没想清楚副作用的设计。** 所以术语精讲里那个词——失败重试——永远要配一句「重跑无副作用吗」。

**「为什么 / 边界 / 常见误解」深化**。为什么顺序必须是重试 → 降级 → 转人工？因为成本与体验递进：重试用户几乎无感，降级要牺牲完整度并明确告知，转人工最贵，放最后。边界在哪？降级不是「随便给个结果」，必须明确告知「结果可能不完整」；转人工不是终点，还要承诺响应时限。常见误解：一是「兜底等于转人工」（其实转人工只是三件套最后一件），二是「人工确认等于转人工」（时点相反），三是「重试越多越稳」（不幂等就出事）。

**这段在面试里怎么答**：被问「工作流失败怎么办」，按三层答：先定位失败类型（瞬时 / 持续 / 高风险），再给三件套顺序（重试 → 降级 → 转人工），最后补产品呈现「每一级用户看到什么、转人工必带完整上下文」。能主动补一句「重试要幂等」，面试官就知道你真搭过。

## 实操演练与巡场

**时间轴**

先说规矩：我投屏，大家跟做；每一步我演示两分钟，然后你们动手，助教巡场；每一步都有完成标志，卡住了举手，别自己耗。五步：建应用、加节点、配工具、调提示词、测运行。界面细节以你们手上当前版本为准，我讲的是节点类型和连线逻辑，产品思路不挑版本。

**先选路径，两条都通向下课要交的同一份 V1。**

- **路径 A · Dify 云端版 / Coze 境外版**：原有版本实操主路径，功能齐、画布完整，适合电脑 + 可访问境外服务的学员；沿用下面五步通用化演示。
- **路径 B · 扣子国内版 / 豆包**：国内网络可直接访问，节点类型、连线逻辑、LLM 节点提示词、条件分支、工具挂载与路径 A 一一对应；教室网络不便访问境外服务时，全体统一走这条。界面文案可能不同，统一口径「以当前版本界面为准」。

两条路径的完成标志完全一致：主链路跑通、失败分支存在、接管点明确。**不比较、不承诺任何额度、价格与响应表现，涉及这些一律「以官方当前说明为准」。**

选路径这一步的典型卡点是账号登录；路径 A 登不上的直接转路径 B，单人处理不超过 3 分钟。

### 第①步 建应用

看投屏：新建一个应用，类型选工作流——注意，不是聊天助手、不是 Agent，选工作流。命名建议用「主项目名-workflow-v1」，比如「售后助手-workflow-v1」。创建成功后进入编排画布。

这一步的典型卡点是找不到「工作流」类型入口，助教直接指，不代做。

完成标志：你的画布打开了。打开的举手，我扫一眼——好，全军过线，我们进第二步。

### 第②步 加节点

现在搭主链路，四类节点。开始节点，定义这条工作流的输入——比如用户的问题。LLM 节点，接大模型，理解和生成。条件分支节点，按条件走向不同路径。输出节点，把结果交给用户。

连线逻辑就一条：下游节点的输入，来自上游节点的输出变量。你在画布上连的每根线，本质都是一次「变量传递」。

大家边连边想：如果 LLM 节点的输出格式乱掉，下游会发生什么？

对——下游解析失败，全链路中断。所以这一步就埋下伏笔：等会儿第④步，我们会用提示词强约束输出格式，再补一条失败分支。

学员任务：按导学案的设计表，搭出主链路四类节点。硬性要求：至少一个条件分支；**并且把「条件分支」和「失败分支」在设计表里分两行填**——讲术语那段刚辨析过，别又混成一条。失败分支不急着连，第⑤步专门处理。

完成标志：画布上出现完整主链路连线。

### 第③步 配工具

光有 LLM 不够，工作流的价值在「能干活」。给节点挂工具：联网搜索、知识库检索，或者你自己接的 API。通用配置四件事：选工具、填凭证或启用插件、把上游变量映射到工具的输入参数、单节点试运行一次。

这一步报错最集中：凭证没填、参数没映射。助教优先处理「红色报错」，其次处理「跑通了但结果不对」。凭证类演示用讲师预置账号，不展示任何密钥。

学员任务：至少给一个节点配上工具调用。

完成标志：工具节点单独测试通过。

### 第④步 调提示词

现在回到第②步埋的伏笔。LLM 节点的提示词，三段式：角色、任务、输出格式约束。格式约束怎么写？给它模板——「严格按以下 JSON（JavaScript Object Notation，一种结构化数据格式）结构输出，不要输出任何其他内容」，字段名列清楚。

看到了吗？输出是自由文本，条件分支读不懂字段，直接断。改完之后——跑通了。这就是「先制造失败，再修复失败」，比背十条最佳姿势都管用。

学员任务：完成自己 LLM 节点的提示词，明确输出格式。

完成标志：单节点试运行，输出符合你定义的格式。

### 第⑤步 测运行

最后一步，也是最容易被跳过的一步：测异常。跑三类输入——正常输入，验主链路；边界条件输入，比如超长文本、空字段；异常输入，比如完全无关的问题、故意断工具。硬性要求：补上失败分支，异常输入不崩，用户端要有明确反馈。

如果你的工具节点超时、自动重试两次还失败，你的失败分支应该把用户引到哪？

对，降级或转人工——就是核心原理 B 那段讲的兜底三件套，现在落到你自己的画布上。

完成标志：整条链路，三类输入均可运行。

**讲师巡场话术（三步固定）**：第 1 圈问「谁还没开始」——解决启动卡点；第 2 圈问「你这根线传的是哪个变量」「你的失败分支用户最后看到什么」——只指路不代做；每步结束前 1 分钟统计完成率，低于六成就延长该步 2 分钟，从讲评段压缩补回。举手求救超过 2 人，停下统一讲，不一个人一个人耗。

**常见卡点 3 条**：① 找不到「工作流」类型入口或账号登不上——助教直接指路径 / 转路径 B / 换备用账号；② 连线后下游读不到变量，或工具报错「参数未映射」——回到「输出变量 → 输入参数」检查映射；③ 提示词不限格式导致条件分支报错——用第④步的三段式和反面演示对照修，先制造失败再修复。

**手机 / 平板替代动作**：只有平板或手机的学员，实操演练这段走「轻量线」，不掉队也不空坐。平板：浏览器登录路径 B，完成建应用与命名，在纸质《工作流编排示意图》上手画主链路与失败分支，与电脑学员结对、口述节点设计由对方操作，拍照归档。手机：登录扣子国内版 / 豆包移动端，浏览 3 个官方模板，完成《工作流设计表》纸面版（含节点、变量、失败分支三列），并录一段 60 秒面试口播（用面试追问那部分第 1 题的标准答法）；术语自测表与面试模拟记录表照填。课后借电脑补实操，补完的截图计入复盘归档那段的作品集积木。**受限任务明确标注**：画布拖拽连线、多窗口参数映射、单节点试运行，手机 / 平板不勉强做。

## 面试讲解与追问防御

**时间轴**

先说规则：面试官不考你背定义，考你能不能在被追问时不改口。所以每道题都练四件套——**踩分点**告诉你得分在哪，**追问链**提前把三层追问走一遍，**失败答法**让你知道坑在哪，**60 秒标准答法**是你能直接说出口的稿子。四个主题：做 Agent 还是工作流、工作流失败怎么办、人机协同怎么设计、要不要上多 Agent。

**第 1 题 · 「这个需求，你做 Agent 还是工作流？」（场景设计题）**
- 踩分点：① 不直接选，先亮三刻度尺（任务确定性 / 步骤数 / 容错要求）；② 逐维给判断依据，至少两条；③ 说出「路径能否预先定义」才是分界，不是难度；④ 补风险提示（可控性代价、调用量差异或「工作流为主、Agent 局部嵌入」）。
- 追问链：追问 1「业务下周要加三种新情况呢？」→ 能穷举就扩条件分支，穷举不了再重评 Agent，说清改造成本；追问 2「你怎么说服一心要上 Agent 的同事？」→ 拿出错代价说话，低容错环节保留工作流 + 人工确认；追问 3「成本怎么算？」→ 工作流步骤固定、消耗可预估，Agent 多轮规划调用量更高，具体口径「以官方当前说明为准」。
- 典型失败答法：「当然上 Agent，越智能越好。」失分原因：一开口就交出可控性，暴露没有判断框架，且被追问成本立刻改口。
- 60 秒标准答法：「我不会直接选。先用三刻度尺量这个需求：任务确定性、步骤数、容错要求。如果流程图画得出、步骤数得清、出错代价高，我就做固定工作流，因为**确定性是产品的好朋友**；只有路径要模型现场规划、错了能重来，才考虑 Agent。比如客服里的工单分类是工作流，开放式竞品调研才是 Agent。最后我会补一句风险：Agent 是用可控性换灵活性，涉及钱和信任的环节，我会保留工作流和人工确认。真要扩展，先加条件分支，穷举不了再重评。」

**第 2 题 · 「工作流跑失败了你怎么办？」（项目深挖题）**
- 踩分点：① 先分失败类型（瞬时 / 持续 / 高风险）；② 给全兜底三件套且顺序正确（重试 → 降级 → 转人工）；③ 说清每级用户看到什么；④ 主动补「重试要幂等」「转人工必带完整上下文」。
- 追问链：追问 1「重试两次还失败呢？」→ 走降级，明确告知结果可能不完整，再转人工；追问 2「降级降成什么样算合格？」→ 宁可「不完整但明确告知」，不要「漂亮但可能出错」；追问 3「转人工用户要重新描述吗？」→ 不能，工单携带对话记录与已执行步骤，并承诺响应时限。
- 典型失败答法：「报错了就提示用户稍后再试。」失分原因：没有失败分支、没有产品承诺，正是「无限转圈」事故的口头版。
- 60 秒标准答法：「先分类型。工具超时这类瞬时失败，自动**失败重试**一到两次，前提是节点幂等、重跑不产生副作用；主工具持续不可用就走降级，切备用方案或礼貌拒答，并明确告诉用户结果可能不完整；前两件都失败或涉及高风险，最后**转人工**兜底，工单带上完整上下文和已执行步骤，承诺响应时限。产品上每一级都要有明确反馈，绝不能无限转圈。我设计时会问自己一句：**兜底设计不是技术问题，是产品承诺**——用户不在乎错在哪个节点，只在乎坏了之后谁负责。」

**第 3 题 · 「人机协同你怎么设计？」（场景设计题）**
- 踩分点：① 给全三型接管点（审批型事前 / 纠错型事中 / 兜底型事后）；② 每型给触发时机；③ 讲「接管成本要对冲风险损失」；④ 答全「人工来了看什么、能改什么、改完怎么继续」。
- 追问链：追问 1「人工成本谁扛？」→ 按出错代价分档设阈值，高风险强审、低风险抽检；追问 2「阈值怎么定？」→ 由风险损失倒推，宁可多拦一道不可逆操作；追问 3「这不就是加个审核按钮吗？」→ 不是，三型是不同时点的分工，且人工确认是事前、转人工是事后。
- 典型失败答法：「在高风险步骤加个审核按钮让人点一下。」失分原因：只说了一型、没有阈值与上下文，把人机协同说成一个控件。
- 60 秒标准答法：「我把**人机协同**按时间轴拆成三型。审批型放在事前：对外发邮件、退款、删数据这类不可逆操作，执行前展示 AI 准备做什么、依据是什么，人工确认，金额超阈值强制人审；纠错型放在事中：模型置信度低于阈值或两次输出不一致，进人工复核队列；兜底型放在事后：重试和降级都失败才转人工，且必须携带完整上下文，不让用户重讲一遍。原则是**接管成本要对冲风险损失**，每个接管点都回答三件事：人工来了看什么、能改什么、改完流程怎么继续。」

**第 4 题 · 「怎么判断要不要上多 Agent？」（技术理解 / 场景设计题）**
- 踩分点：① 不神化多 Agent，先用三刻度尺量现有需求；② 说明多数需求「单 Agent + 工作流」已够；③ 指出多 Agent 是复杂度跃升，不是能力升级；④ 用可控性、接管成本、失败路径作为是否上的判据。
- 追问链：追问 1「单 Agent 加工作流不够吗？」→ 够，先把可确定的部分固化成工作流，只把真正路径不定的子任务交给一个 Agent；追问 2「什么信号才说明该加？」→ 子任务确实需要不同目标与动态拆解、且失败可隔离，才评估；追问 3「上了之后最大的风险？」→ 失败路径成倍变复杂、接管点难定位，所以更要兜底三件套和上下文传递。
- 典型失败答法：「任务复杂就多上几个 Agent 分工，效果肯定更好。」失分原因：把复杂度当能力，没有判断框架，也没答可控性代价。
- 60 秒标准答法：「我不会因为『复杂』就上多 Agent。还是先拿三刻度尺量：确定性、步骤数、容错要求。多数需求把能画成流程图的部分固化成**工作流**，只把真正路径不定的子任务交给一个 Agent 就够了。多 Agent 是复杂度的跃升，不是能力升级——它会让**分支**和失败路径都变多、接管点更难定位。真到要评估，我只看三件事：子任务是不是确实目标不同且需动态拆解、失败能不能隔离、可控性和接管成本还扛不扛得住。扛不住就先别上，把兜底和**人工确认**补扎实更值。」

**第 5 题 · 「你搭的工作流，重试会不会重复扣款？」（项目深挖题）**
- 踩分点：① 识别「自动退款不幂等」；② 解释幂等 = 重跑无副作用；③ 给出唯一单号或改状态查询两种方案；④ 把风险前置到设计阶段。
- 追问链：追问 1「哪些节点最危险？」→ 一切写操作：付款、发消息、删数据；追问 2「怎么验证？」→ 故意制造失败并重试，核对是否只执行一次；追问 3「边界条件怎么测？」→ 超长、空值、无关问题三类输入一起跑。
- 典型失败答法：「重试几次应该没事吧，平台会处理。」失分原因：把工程底线推给平台，暴露没搭过、没测过。
- 60 秒标准答法：「会，所以**失败重试**的前提是幂等——重跑不产生副作用。自动退款这类写操作不是幂等的，重试可能重复打款。我的做法是给每个请求带唯一退款单号，同一单号只执行一次；或者把重试改成先做状态查询，确认没退过再退。设计阶段就把付款、发消息、删数据这些写节点标成高风险，验收时故意制造一次失败再重试，核对只执行一次，并跑正常、**边界 / 异常**三类输入。能问出『重试安全吗』，比跑通主链路更说明搭过。」

**第 6 题 · 「业务方坚持要一个『全能 Agent』，你怎么沟通？」（行为题）**
- 踩分点：① 不硬顶，先接住诉求；② 用三刻度尺把需求拆成子任务；③ 给出「工作流为主、Agent 局部嵌入」的折中；④ 用风险与成本说话，不用术语压人。
- 追问链：追问 1「对方说你太保守？」→ 用出错代价举例：报销、退款错了赔不起；追问 2「那灵活性怎么留？」→ 可确定的固化，路径不定的留 Agent 分支，并预留重评；追问 3「上线后怎么证明选对了？」→ 看三类输入通过率、失败分支触发与转人工是否带上下文。
- 典型失败答法：「Agent 成本高、不可控，做不了。」失分原因：只否定不给方案，沟通题最忌没有替代路径。
- 60 秒标准答法：「我先接住诉求——要灵活、要能扩展，这没错。然后拿三刻度尺和他一起拆：哪些子任务流程图画得出、错了代价高，这些做成**固定工作流**加**人工确认**；哪些路径真不定，才交给 Agent。给一个『工作流为主、Agent 局部嵌入』的方案，而不是二选一。沟通时我不说术语，说风险：涉及钱和信任的环节错一步是真实损失，灵活要用可控性换。最后留个口子：规则变了能穷举就扩**分支**，穷举不了再重评，不是一次定死。」

**第 7 题 · 「一条工作流上线前，你怎么验收？」（项目深挖 / 场景设计题）**
- 踩分点：① 明确三条线（主链路跑通 / 失败分支存在 / 接管点明确）；② 跑全正常 / 边界 / 异常三类输入；③ 区分单节点试运行与整条运行；④ 回答「任何节点失败，用户看到的最后一条消息是什么」。
- 追问链：追问 1「只测正常输入行不行？」→ 不行，边界条件与异常输入才暴露失败分支；追问 2「怎么算异常不崩？」→ 有降级或转人工的明确反馈，不是无限转圈；追问 3「接管点怎么验？」→ 高风险步骤执行前有人确认，且携带完整上下文。
- 典型失败答法：「点一下运行，能出结果就上线。」失分原因：把「跑通」当「验收」，没有失败路径意识。
- 60 秒标准答法：「我按三条线验收：主链路跑通、失败分支存在、接管点明确。输入必须跑三类——正常输入验主链路，**边界条件**比如超长文本、空字段，异常输入比如无关问题、故意断工具；单节点试运行和整条运行都要测，输出符合格式不等于整条链路可运行。每一级失败都要有明确反馈，异常不崩才算 V1。最后我一定问自己那句：任何**节点**失败之后，用户看到的最后一条消息是什么？答不上来就不上线。高风险步骤再确认一遍执行前有没有**人工确认**。」

**本日面试金句（3 条，抄进导学案）**
1. 能用工作流解决的事，别用 Agent——确定性是产品的好朋友。
2. Agent 用自主性换灵活性，工作流用确定性换可控性——产品经理的活儿，就是替用户选对这一边。
3. 兜底设计不是技术问题，是产品承诺——用户不在乎错在哪个节点，只在乎坏了之后谁负责。

## 补充素材

### 理论知识手册 · Workflow vs Agent 与复杂度阶梯

- **概念 / 术语**：Anthropic 定义的两大类 Agent 系统——**Workflow**（预定义的代码路径）与 **Agent**（模型自主决策）。
- **关键结论**：「最成功的 AI 实现，往往不是最复杂的那个」；「用一个 Agent 框架来做本质上一个 Prompt 加一次搜索就能解决的问题，框架引入的延迟、成本、不确定性远大于它带来的收益」；「不是所有问题都需要 Agent，很多时候 Workflow 就够了，甚至一个精调的 Prompt 就够了」。

| 复杂度阶梯 | 1 | 2 | 3 | 4 |
|-|-|-|-|-|
| 方案 | 先试单次 LLM 调用 | 检索增强（RAG） | Workflow | Agent |

- **框架 / 模型**：五种 Workflow 编排模式——**Prompt Chaining 提示链**（把大任务拆成多个顺序步骤）、**Routing 路由**、**Parallelization 并行化**（Sectioning 拆分并行 / Voting 多次投票）、**Orchestrator-Workers 编排者-工人**（动态拆解任务）、**Evaluator-Optimizer 评估-优化**；「不追求最复杂的，追求最合适的」。

### 理论知识手册 · ACI：工具设计与 MCP

先说 ACI，全称 Agent-Computer Interface，你们记住一句话：工具是 Agent 和世界之间的契约；而工具的名字、参数、描述，就是 Agent 的用户界面。这里有个对比要留意，传统 API 是确定性的，Agent 工具却是非确定性的。所以工具设计的质量，直接决定了 Agent 的能力上限。

再往下一层看几个结论。同样一个功能，描述写得好和写得坏，成功率能差 3 倍。所以你们做产品经理，应该像写 PRD 一样去写工具描述，这不只是工程问题，它直接影响用户体验，也直接影响 Token 成本；工具设计上该投的精力，应该和 Prompt 设计一样多。

那工具描述具体写什么？就三行。第一行写清楚什么时候该用，也要写清楚什么时候不该用；第二行写每个参数的含义、格式、示例值；第三行写返回什么，以及拿到之后该怎么用。这里要注意，模型只凭这三行字决定怎么调用，它看不到你的代码。真要挑第一个工具上手，按三个标准来：高频、低风险，优先只读，还有输入输出要清楚。

接着说 MCP，你们可以把它理解成工具的 USB 接口：任何工具只需要实现一次，就能被任何支持 MCP 的框架调用。它的传输方式有三种，stdio、SSE，还有 Streamable HTTP。

再说 Think Tool。它是一个只接受一段文字、什么都不做的工具，真正的价值在于长链路里让 Agent 中途暂停一下。它适合复杂工具链、策略密集的环境、串行依赖的决策，还有多轮信息聚合；反过来，简单工具调用、非序列任务、已经有 Extended Thinking 的场景，以及纯生成任务，都不适合用它。

最后一层，是用 Agent 去优化 Agent 的工具，走 Prototype、Evaluate、Optimize 这三步。评测的时候盯住几个维度：Agent 有没有选对工具，参数填得对不对，返回结果有没有被正确理解，端到端的任务完成率怎么样。归根到底还是那句话，工具质量，决定 Agent 质量的上限。

### 理论知识手册 · 原理、流程与决策框架

- **概念 / 术语**：**知识库 / RAG = 开卷考试的书架**——把公司文件切成小块、建好索引，回答前找出相关几段塞进对话再作答，出处也能标给你看；「喂资料」是让它开卷考试、随用随查。
- **框架 / 模型**：两步流程——**知识库构建阶段**（离线一次性）：原始文档 → 切块 → 建索引；**查询阶段**（每次对话实时）：用户问题 → 问题向量（Embedding）→ 向量数据库搜索 Top-K 最相关片段 → 拼进 Prompt → 生成回答（含来源）。关键是问题向量与文档块向量使用同一个 Embedding 模型。
- **关键结论**：无 RAG（闭卷）前文只有问题本身；有 RAG（开卷）检索到的文档成为前文一部分，直接影响每步 Token 的概率分布；「模型没有变聪明，只是有了一个更好的起点」；知识实时（更新知识库即可更新答案，无需重训）、范围可控、引用来源可核查。
- **关键结论**：知识库软肋——分辨真伪能力有限，文件过时照着旧文件答，两份矛盾可能各抄一半；保证「有据可查」管不了「据是否靠谱」，文件质量决定答案质量、与训练无关。
- **能力要求**：判断什么场景必须上 RAG（私有知识库、答错代价高）、如何设计检索流程、落地的坑在哪里。

### 理论知识手册 · 向量检索与心智模型

- **概念 / 术语**：「模型把含义变成坐标，向量数据库负责在海量坐标中快速找到『意思最接近』的内容」；数据链「原始内容 → Embedding（固定长度的浮点向量）→ ANN 搜索（近似最近邻，用少量精度换取数量级更高的速度）→ 返回 Top-K 文档」。
- **关键结论**：「Embedding 捕捉的是统计语义，不是可靠的事实判断」；ANN 索引先缩小候选集再计算距离，因此需要用 **Recall 与延迟共同评测**；「索引选型不是越高级越好」。

| 操作 | 原文 |
|-|-|
| Search | 按距离返回 Top-K，答案是「语义上谁最像」 |
| Query | 按主键或标量表达式取数据，答案是「哪些记录满足条件」 |
| Load | 创建成功不代表已经可搜 |

- **框架 / 模型**：**在线链路**——Embed Query（写入时同一个模型）→ Retrieve（租户 / 权限过滤 + Top-K）→ Rerank（精排去重、控制上下文 Token）→ Generate（只依据证据回答并给出来源）；**离线摄取**——切分（按标题、段落和语义边界切 chunk，保留少量 overlap；太大噪声多、太小上下文断裂）、元数据（source_id、版本、章节、租户、ACL、更新时间）、版本（蓝绿 collection 切换避免新旧向量混用）。
- **关键结论**：「Search 返回『可能相关的片段』，RAG 还要把它们变成有来源、有边界、能被评测的回答依据」。
- **框架 / 模型**：**Contextual Retrieval**——「RAG 的核心假设是『检索到正确的 Chunk 就能给出正确的答案』，但切 Chunk 的过程本身就会丢失关键信息」；三层递进 Contextual Embeddings / Contextual BM25 / Reranking，代价是预处理成本增加，可用 Prompt Caching 降低成本，适合高准确率场景。
- **框架 / 模型**：**记忆分层**——company_knowledge（审核过的制度、产品文档、FAQ，按文档版本更新，权限由组织和角色决定）与 user_memory（用户偏好、历史选择与任务状态，按 user_id 强制过滤；需同意、可查看、可删除并设置保留期）；「知识与记忆不要混成一锅」；知识库工具应「返回片段、来源与分数，不直接编答案」「引用证据；不足时说明无法确认」，且必须同时测试「调用」和「不调用」。

### 理论知识手册 · RAG 的代价与优化

| 额外成本项 | 量级 / 说明 |
|-|-|
| 文档向量化 | 低（一次性）：Embedding 入库时跑一次，之后复用 |
| 问题向量化 | 低：每次查询约 0.1 元 / 百万 Token |
| 向量检索 | 中：大规模知识库时延迟显著 |
| Prompt 增大 | 高：每次多注入 500–2000 Token，LLM 费用倍增 |

- **框架 / 模型**：四种优化策略——关键词触发（过滤）、模型路由（分级处理）、语义缓存、精准切块（Chunking 策略）；最佳实践：建立检索命中率评测、引用来源强制显示、定期清洗知识库；「RAG ≠ 全量检索」。

## 知识库课件补充

> 来源：AI 产品经理培训中文知识库（github.com/2013102249/ai-pm-knowledge-base，校验日 2026-11-13）· 课件原文照录，保留表格与问答结构，供课堂讲授与课后查阅；提示词模板代码块内保留原有方括号字段标记，属提示词工程常见写法，照抄使用。

### 学习目标
1. 写出工具契约四要素并填出一张契约卡。
2. 按 6 步实操流程搭出含人工确认点、可中断恢复的工作流。
3. 判断在哪三个位置必须写日志，并为每个失败给出兜底动作。

### 核心概念
结论前置：Agent 产品设计不是「让模型更聪明」，而是「把不确定性关进契约、状态与兜底里」。六要点按「先拆、再约、再记、再刹车」递进。

六要点表（要点 / 结论 / 交付物）：

| 要点 | 结论 | 交付物 |
| --- | --- | --- |
| 任务分解 | 拆成可独立失败的步骤 | 步骤清单 |
| 工具契约 | 写清输入、输出、失败、权限 | 契约卡 |
| 状态与中断恢复 | 每步存状态，可续跑或回滚 | 状态字段表 |
| 人工确认点 | 高代价动作前暂停 | 确认点清单 |
| 可观测与日志 | 记录谁何时调了什么 | 日志字段表 |
| 失败兜底 | 每个失败都有去向 | 兜底映射表 |

工具契约四要素表（要素 / 要写什么 / 反例）：

| 要素 | 要写什么 | 反例 |
| --- | --- | --- |
| 输入 | 字段名、类型、必填、取值范围 | 只写传一个 query |
| 输出 | 成功与空结果结构 | 只写返回 JSON |
| 失败 | 超时、限流、越权、无数据四类码 | 只写报错 |
| 权限 | 谁能调、能读哪些、能否写删 | 共用一把钥匙 |

结论：先有步骤才有约定，有约定才有状态，有状态才谈得上刹车。工具契约像插座与插头——接口、电压、保险丝、谁有权合闸，四样缺一就烧设备。

### 方法框架
结论前置：本讲给出「工作流画布字段表」与 6 步实操流程两套模板。为大纲「工作流实操」的展开模板。

工作流画布字段表：

| 字段 | 含义 | 填写要求 | 示例（（教学假设）） |
| --- | --- | --- | --- |
| 节点 ID | 唯一标识 | 全局不重复 | N03 |
| 节点类型 | 开始 / 模型 / 工具 / 判断 / 人工 / 结束 | 六选一 | 工具 |
| 输入映射 | 上游字段 | 写「来源节点.字段」 | N02.summary |
| 输出映射 | 产出给谁 | 写目标字段 | N04.draft |
| 工具契约 ID | 引用的契约卡编号 | 必填 | TC-02 |
| 成功出口 | 下一节点 | 单一 | N04 |
| 失败出口 | 兜底节点 | 必填，不得空 | N09 转人工 |
| 确认点 | 是否暂停待人 | 是 / 否 + 角色 | 是 / 业务主管 |
| 状态快照 | 是否存断点 | 是 / 否 | 是 |
| 日志级别 | 记录粒度 | 简要 / 详细 | 详细 |
| 超时与重试 | 上限值 | 标（教学假设） | 10 秒 / 2 次 |

结论：这张表就是 AI PM 交给工程的需求；「失败出口不得空」最常被漏掉。

6 步实操流程：
1. 写目标与验收口径：说明「什么算做完」，列 1 条成功与 1 条失败样例。
2. 拆步骤画骨架：拆成 5–8 个节点，只连成功出口。
3. 为每个工具节点填契约卡：补齐四要素。
4. 补三条横向设计：高代价节点加确认点、全部节点加状态快照、失败出口连兜底；[R16 langchain-ai/langgraph](https://github.com/langchain-ai/langgraph) 的状态检查点正是「可续跑」的实现。
5. 配可观测：定义日志字段（时间戳、节点 ID、输入输出摘要、Token 用量、耗时、结果码），定留存与可见角色。
6. 用评测样例走一遍：跑通正常路径、超时、越权各 1 条，确认都有去向，再冻结画布进入里程碑 ②。

模板——契约卡：工具名 / 契约 ID / 输入 / 输出 / 失败四类 / 权限 / 负责人 / 版本号。

### 案例拆解
案例一：[R15 langgenius/dify](https://github.com/langgenius/dify)。场景：一下午做出「报名信息抽取 + 自动回复」演示。决策：用可视化画布承载节点、分支与失败出口，确认点做成显式节点。结果（定性）：评审讨论「确认点该不该前移」，而非翻代码。可迁移点：把「刹车」画进图里，最易被认可。

案例二：[R40 shaxiu/XianyuAutoAgent](https://github.com/shaxiu/XianyuAutoAgent)。场景：客服议价与承诺属高代价动作。决策：多专家协同加上下文感知，议价类输出保留人工约束。结果（定性）：上下文不丢、越界动作被拦住。可迁移点：越贴近交易，越要把确认点与兜底前置；[R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe) 中文实战可照着搭最小链路，验证第 6 步样例。

### 课堂讲解要点
课堂节奏：

| 环节 | 内容 |
| --- | --- |
| 导入 | 快递中转分拣讲状态与中断 |
| 讲授 | 六要点、契约四要素、画布字段表 |
| 演示 | 按 6 步搭链路，制造超时看兜底 |
| 练习 | 填契约卡，标 3 个日志位置 |
| 总结 | 收口：不确定性靠契约与兜底关住 |

板书：画 6 节点链，红三角标确认点、虚线标失败出口。
生活类比：办家宴——先列菜单（分解），跟帮工说清「拿什么、交什么、做坏了怎么办、谁能开燃气」（契约），每道菜做到哪步记便签（状态），上桌前尝一口（确认点），烧糊了有备选菜（兜底）。

### 练习与讨论题
个人练习 1：为「查询订单」填四要素契约卡。要点：四类失败齐全、权限区分读写、输出含空结果，共 4 分。
个人练习 2：给 5 节点链路标 1 个确认点与 3 个日志位置。要点：确认点在高代价节点、日志覆盖输入输出与结果码，共 3 分。
小组研讨 3：设计「工具超时 + 上游无数据」同时发生的兜底顺序与文案。rubric：兜底有去向 2 分、文案不推责不编造 2 分、有转人工 2 分、记日志 1 分、结论明确 1 分，共 8 分。

### 常见问题
1. Q：工具契约工程写 API 文档就行？A：不是，AI PM 必须定义失败四类与权限，这两项决定兜底与合规边界。
2. Q：确认点越多越安全？A：不是，过多会把 L1 拖成人工流程，按失败代价布点即可。
3. Q：日志记详细有隐私风险吗？A：会，AI PM 要定义「摘要不记原文、可见角色、留存期限」，延续 W2 合规要求。

### 本讲术语

| 术语 | 英文/缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 工具契约 | Tool Contract | 输入、输出、失败、权限四要素 | 不等于 API 文档 |
| 中断恢复 | Checkpoint / Resume | 存断点后续跑或回滚 | 不等于报错重试 |
| 人工确认点 | Human-in-the-loop | 强制暂停待确认的节点 | 不等于事后抽检 |
| 失败兜底 | Fallback | 每个失败对应的明确去向 | 不等于提示稍后再试 |
| 可观测 | Observability | 通过日志还原一次完整调用 | 不等于看控制台打印 |
